app.py — vis fil og forklaring

Kildefil: labs/containers/app.py

"""Small, deliberately local workshop API; no external Python dependencies."""
# Gjør Python-data om til JSON i HTTP-svaret.
import json
# Les appkonfigurasjon fra miljøvariabler i containeren.
import os
# Bruk en liten HTTP-server og en handler for hver forespørsel.
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
# Skill URL-stien fra eventuelle spørringsparametere.
from urllib.parse import urlsplit


# Samle behandlingen av HTTP-forespørsler i en handlerklasse.
class Handler(BaseHTTPRequestHandler):
    # HTTP-serveren kaller denne metoden for GET-forespørsler.
    def do_GET(self):
        # Hent bare stien, for eksempel /health.
        path = urlsplit(self.path).path
        # Helsesjekken gir 200; alle andre stier gir 404.
        status = 200 if path == "/health" else 404
        # Vis versjonen fra miljøet, med v1 som standard.
        payload = {"status": "ok", "version": os.getenv("APP_VERSION", "v1"),
                   # Vis konfigurasjonen uten at vi trenger å bygge et nytt image.
                   "mode": os.getenv("WORKSHOP_MODE", "practice"),
                   # Vis bare om en hemmelighet finnes. Selve verdien sendes aldri til klienten.
                   # For andre stier brukes en enkel feilmelding i stedet.
                   "secret_configured": bool(os.getenv("DEMO_SECRET"))} if status == 200 else {"error": "not found"}
        # Serialiser JSON og kod teksten som byte til nettverksforbindelsen.
        body = json.dumps(payload).encode("utf-8")
        # Start HTTP-svaret med statuskoden.
        self.send_response(status)
        # Fortell klienten at innholdet er JSON i UTF-8.
        self.send_header("Content-Type", "application/json; charset=utf-8")
        # Oppgi lengden på svaret i byte.
        self.send_header("Content-Length", str(len(body)))
        # Avslutt headerne før selve innholdet sendes.
        self.end_headers()
        # Skriv JSON-innholdet til HTTP-svaret.
        self.wfile.write(body)


# Start serveren bare når filen kjøres som et program.
if __name__ == "__main__":
    # Skriv en oppstartsmelding direkte til containerloggen.
    print("Workshop API listening on port 8080", flush=True)
    # Lytt på port 8080 på alle containerens nettverksgrensesnitt.
    ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

1. Bygg et image

Dockerfile-en under har kommentarer til hver instruksjon. Kildefilen ligger i labs/containers/Dockerfile.

Dockerfile — vis fil og forklaring

Kildefil: labs/containers/Dockerfile

# Bruk et ferdig Linux-image med Python 3.12.
# slim-varianten har færre forhåndsinstallerte pakker enn standardimaget.
FROM python:3.12-slim

# Sett /app som arbeidsmappe i imaget. Mappen opprettes hvis den mangler.
WORKDIR /app

# Kopier app.py fra byggkonteksten til /app/app.py i imaget.
COPY app.py .

# Opprett brukeren appuser med UID 10001 under byggingen, uten hjemmemappe.
RUN useradd --uid 10001 --no-create-home appuser

# Kjør påfølgende instruksjoner og appens startkommando som UID 10001.
# Appen kjører dermed uten root-rettigheter.
USER 10001

# Dokumenter at appen lytter på TCP-port 8080 inne i containeren.
# Bruk docker run --publish for å gjøre porten tilgjengelig på verten.
EXPOSE 8080

# Start app.py med Python når containeren starter.
# -u slår av bufring av stdout/stderr, slik at loggene kommer fortløpende.
# Listeformen starter Python direkte, uten et mellomliggende shell.
CMD ["python", "-u", "app.py"]

# Bygg v1-imaget fra Dockerfile-en og filene i den gjeldende mappen.
docker build -t ai200-api:v1 .
# Vis de lokale image-versjonene av ai200-api.
docker image ls ai200-api

Finn base-image, arbeidsmappe, COPY, bruker og CMD i Dockerfile. Forklar hvilke filer som bygges inn. Forventet: en lokal tag ai200-api:v1.

2. Kjør og feilsøk

# Start valgt image i bakgrunnen og koble lokal port 8080 til containerport 8080.
docker run --detach --name ai200-api --publish 127.0.0.1:8080:8080 ai200-api:v1
# Kall den lokale containerens helsesjekk for å se versjon og konfigurasjon.
Invoke-RestMethod http://localhost:8080/health
# Kall en rute som mangler og vis HTTP-statusen 404 sammen med responsen.
curl.exe -i http://localhost:8080/missing
# Les de 20 siste logglinjene fra den lokale API-containeren.
docker logs --tail 20 ai200-api

Forventet: 200 fra /health og 404 fra /missing. Prosessen fortsetter å kjøre. Forklar hvorfor EXPOSE og portbindingen har ulike oppgaver.

3. Versjoner og tilbakerulling

Endre standardverdien for APP_VERSION fra v1 til v2 i labs/containers/app.py. Den gamle containeren beholder sin kopi til den erstattes.

# Bygg v2-imaget med de endrede filene fra den gjeldende mappen.
docker build -t ai200-api:v2 .
# Stopp den lokale API-containeren før den erstattes eller fjernes.
docker stop ai200-api
# Fjern den stoppede API-containeren; imagene beholdes.
docker rm ai200-api
# Start valgt image i bakgrunnen og koble lokal port 8080 til containerport 8080.
docker run --detach --name ai200-api --publish 127.0.0.1:8080:8080 ai200-api:v2
# Kall den lokale containerens helsesjekk for å se versjon og konfigurasjon.
Invoke-RestMethod http://localhost:8080/health

Svaret skal ha version lik v2. Det nye imaget inneholder filen slik den var da du bygget v2.

Rull nå tilbake til det opprinnelige v1-imaget. La app.py stå med v2, og kjør disse kommandoene uten å bygge på nytt:

# Stopp den lokale API-containeren før den erstattes eller fjernes.
docker stop ai200-api
# Fjern den stoppede API-containeren; imagene beholdes.
docker rm ai200-api
# Start valgt image i bakgrunnen og koble lokal port 8080 til containerport 8080.
docker run --detach --name ai200-api --publish 127.0.0.1:8080:8080 ai200-api:v1
# Kall den lokale containerens helsesjekk for å se versjon og konfigurasjon.
Invoke-RestMethod http://localhost:8080/health

Svaret skal igjen ha version lik v1. Containeren bruker kopien av app.py som ble bygget inn i v1-imaget, selv om arbeidsfilen nå inneholder v2. Dette viser at filendringer ikke endrer et eksisterende image, og at du kan rulle tilbake ved å starte det tidligere imaget. Taggene v1 og v2 brukes her til å velge mellom de to versjonene.

Rydding og overgang til neste del

# Stopp den lokale API-containeren før den erstattes eller fjernes.
docker stop ai200-api
# Fjern den stoppede API-containeren; imagene beholdes.
docker rm ai200-api

Behold de lokale v1- og v2-imagene til neste økt. Forklar forskjellen mellom en filendring, et nytt image og en ny container.

Før workshop 2: tilbakestill kildefilen labs/containers/app.py med Git. Kjør fra labs/containers; kommandoen forkaster endringene i app.py:

# Forkast lokale endringer i app.py og hent den committede versjonen.
git restore --source=HEAD -- app.py

Sluttstatus: standardverdien for APP_VERSION i kildefilen skal være v1. De bygde imagene ai200-api:v1 og ai200-api:v2 beholdes; tilbakestillingen av filen endrer ikke innholdet i dem.

Ressursgruppen opprettes her ved behov

Dette er første Azure-øvelse i domene 1. Blokken oppretter gruppen bare hvis den mangler. Har du allerede en labgruppe med et annet navn, bruker du det navnet i $rg.

# Sett navnet på ressursgruppen som kommandoene skal bruke.
$rg = "ai200-d1"
# Velg Norway East som region for nye ressurser.
$location = "norwayeast"
# Kjør opprettelsen bare hvis ressursgruppen ikke finnes i abonnementet.
if ((az group exists --name $rg -o tsv) -eq "false") {
    # Opprett den manglende ressursgruppen i valgt region.
    az group create --name $rg --location $location -o none
}
Opprett ett Basic-registry

Hvis du ikke har et labregistry fra før, oppretter du det med blokken nedenfor én gang. ACR-navnet får et tilfeldig suffiks fordi det må være globalt unikt.

# Lag et globalt unikt registrynavn med et tilfeldig suffiks.
$acr = "ai200" + (New-Guid).ToString("N").Substring(0, 12)
# Opprett ett Basic-registry med administratorbrukeren deaktivert og RBAC som tilgangsmodell.
az acr create --resource-group $rg --name $acr --location $location --sku Basic --admin-enabled false --role-assignment-mode rbac
# Tillat Azure Resource Manager-tokens ved autentisering mot registryet.
az acr config authentication-as-arm update -r $acr --status enabled
# Hent registryets innloggingsadresse, som brukes i image-navn.
$login = az acr show --resource-group $rg --name $acr --query loginServer -o tsv
# Hent Azure-ressurs-ID-en til registryet for rolletildelinger.
$acrId = az acr show --resource-group $rg --name $acr --query id -o tsv
# Vis registryets navn, imageadresse, opprettelsesstatus og tilgangsinnstillinger.
az acr show --resource-group $rg --name $acr --query "{Name:name, LoginServer:loginServer, State:provisioningState, AdminEnabled:adminUserEnabled, RoleMode:roleAssignmentMode}" -o table

Kontrollpunkt: registryet er Succeeded, AdminEnabled er False og tilgangsmodellen er LegacyRegistryPermissions (portalens RBAC Registry Permissions). Behold terminalen og variablene til del 3–6, og noter registry-navnet. Ved ny terminal bruker du tilkoblingsblokken nedenfor.

Labben bruker bevisst RBAC Registry Permissions, der AcrPull gir lesetilgang. Bruker du et eksisterende registry med RBAC Registry + ABAC Repository Permissions, må repository-roller brukes i stedet; ikke endre tilgangsmodellen på et delt registry for å følge labben.

Bruk navnene du noterte. Denne blokken henter verdier til del 3–6:

# Sett navnet på ressursgruppen som kommandoene skal bruke.
$rg = "ai200-d1"
# Sett navnet på registryet som allerede finnes.
$acr = "DITT-REGISTRY-NAVN"

Gi labbrukeren tilgang ved behov

Hvis du har Owner eller Contributor på gruppen i denne RBAC-modellen, har du allerede tilgangen labben bruker til image-operasjoner og Tasks. Ved AuthorizationFailed kontrollerer eieren ACR → Access control (IAM) og kan gi deg AcrPush, Container Registry Tasks Contributor og Container Registry Configuration Reader and Data Access Configuration Reader på labregistryet. # Gå til mappen med Dockerfile-en og containerkoden.

Forventet: alle tre stegene fullføres, og Python-versjonen står i loggen. Finn task-kjøringen og den unike taggen. Forklar forskjellen mellom denne manuelle kjøringen og triggere fra kildekode, base-image eller tidsplan.

acr-task.yaml — vis fil og forklaring

Kildefil: labs/containers/acr-task.yaml

# Velg syntaksversjonen for ACR Tasks-filen.
version: v1.1.0
# Kjør stegene i den angitte rekkefølgen.
steps:
  # Bygg Dockerfile fra denne byggkonteksten.
  # Registry settes av ACR, og Run.ID gir hver kjøring en egen tagg.
  - build: -t {{.Run.Registry}}/ai200-api:{{.Run.ID}} -f Dockerfile .
  # Last opp det ferdige imaget til registryet.
  - push:
      # Bruk nøyaktig samme image-navn og tagg som i byggesteget.
      - '{{.Run.Registry}}/ai200-api:{{.Run.ID}}'
  # Kjør imaget og skriv Python-versjonen i task-loggen.
  - cmd: '{{.Run.Registry}}/ai200-api:{{.Run.ID}} python --version'

1. Deploy et manifest

Rediger labs/containers/deployment.yaml og bytt image til ditt ACR-image. Behold ressursgrenser og readiness-proben.

# Opprett eller oppdater labressursene fra manifestfilen.
kubectl apply -n $ns -f labs/containers/deployment.yaml
# Vent opptil 120 sekunder på at utrullingen av workshop-api fullføres.
kubectl rollout status -n $ns deployment/workshop-api --timeout=120s
# Vis podene og tilstanden deres i labnamespace-et.
kubectl get pods -n $ns
# Videresend lokal port 8082 til containerens port 8080 så lenge kommandoen kjører.
kubectl port-forward -n $ns deployment/workshop-api 8082:8080

La videresendingen kjøre. Åpne en annen terminal og kjør Invoke-RestMethod http://localhost:8082/health. Forventet: JSON fra appen.

deployment.yaml — vis fil og forklaring

Kildefil: labs/containers/deployment.yaml

# Bruk Kubernetes-API-et for Deployment-ressurser.
apiVersion: apps/v1
# En Deployment vedlikeholder ønsket antall pod-replikaer.
kind: Deployment
# Metadata identifiserer selve Deployment-ressursen.
metadata:
  # Bruk dette navnet i kubectl rollout, logs og scale.
  name: workshop-api
# Beskriv ønsket tilstand for Deployment-en.
spec:
  # Start med én pod; senere skalerer du til to.
  replicas: 1
  # Velg hvilke pods Deployment-en skal styre.
  selector:
    # Match podenes labels nøyaktig.
    matchLabels:
      # Selectoren må passe med labelen i pod-malen under.
      app: workshop-api
  # Denne malen brukes til å opprette hver pod.
  template:
    # Dette er metadata for podene, ikke for Deployment-en.
    metadata:
      # Sett labels som Deployment og Service kan velge etter.
      labels:
        # Bruk samme app-label som selectoren over.
        app: workshop-api
    # Beskriv innholdet i hver pod.
    spec:
      # Denne poden inneholder én applikasjonscontainer.
      containers:
        # Gi containeren et navn i podens logger og status.
        - name: api
          # Bytt til hele ACR-adressen og taggen du skal teste.
          image: ai200-api:v2
          # Hent imaget hvis noden ikke allerede har denne taggen lokalt.
          imagePullPolicy: IfNotPresent
          # Dokumenter portene containeren lytter på.
          ports:
            # Appen lytter på port 8080 inne i containeren.
            - containerPort: 8080
          # Angi ressursbehov og øvre grenser for containeren.
          resources:
            # Scheduler bruker disse behovene ved plassering på en node.
            requests:
              # Be om 0,1 CPU-kjerne.
              cpu: 100m
              # Be om 64 MiB minne.
              memory: 64Mi
            # Sett øvre grenser for containerens ressursbruk.
            limits:
              # Begrens CPU-bruken til 0,25 kjerne.
              cpu: 250m
              # Minnegrensen er 128 MiB; overskridelse kan avslutte containeren.
              memory: 128Mi
          # Avgjør om poden er klar til å motta tjenestens trafikk.
          readinessProbe:
            # Bruk en HTTP-forespørsel som readiness-kontroll.
            httpGet:
              # Denne stien skal gi et vellykket HTTP-svar.
              path: /health
              # Send kontrollen til appens containerport.
              port: 8080
            # Vent to sekunder før første readiness-kontroll.
            initialDelaySeconds: 2
            # Gjenta kontrollen hvert femte sekund.
            periodSeconds: 5

2. Fremprovoser og finn en feil

Avslutt port-forward. Før du lager feil, lagre en kopi av manifestet som nettopp fungerte. Kjør fra prosjektroten; kopien beholder din ACR-adresse:

# Lagre en kopi av det fungerende manifestet før du lager testfeil.
Copy-Item -LiteralPath labs/containers/deployment.yaml -Destination artifacts/deployment.before-faults.yaml -Force

Endre imagetaggen i arbeidsmanifestet til finnes-ikke, og undersøk utrullingen:

# Opprett eller oppdater labressursene fra manifestfilen.
kubectl apply -n $ns -f labs/containers/deployment.yaml
# Vis podene og tilstanden deres i labnamespace-et.
kubectl get pods -n $ns
# Vis detaljer om podene, inkludert hendelser som forklarer oppstartsfeil.
kubectl describe pods -n $ns
# Vis hendelsene i labnamespace-et, sortert etter siste tidsstempel.
kubectl get events -n $ns --sort-by=.lastTimestamp

Forventet: ImagePullBackOff og en forklarende hendelse. Rull tilbake i klyngen og hent samtidig tilbake den fungerende arbeidsfilen:

# Rull workshop-api tilbake til forrige Deployment-revisjon.
kubectl rollout undo -n $ns deployment/workshop-api
# Vent opptil 120 sekunder på at utrullingen av workshop-api fullføres.
kubectl rollout status -n $ns deployment/workshop-api --timeout=120s
# Gjenopprett arbeidsmanifestet fra kopien med riktig ACR-adresse.
Copy-Item -LiteralPath artifacts/deployment.before-faults.yaml -Destination labs/containers/deployment.yaml -Force

rollout undo endrer klyngen; kopieringen gjenoppretter filen du bruker ved neste apply. Endre nå readiness-stien i arbeidsfilen til /missing, og kjør apply og undersøkelseskommandoene over igjen. Sammenlign en levende prosess med en ready pod.

Etter testen: gjenopprett manifestet med riktig image og /health, og rull det ut:

# Gjenopprett arbeidsmanifestet fra kopien med riktig ACR-adresse.
Copy-Item -LiteralPath artifacts/deployment.before-faults.yaml -Destination labs/containers/deployment.yaml -Force
# Opprett eller oppdater labressursene fra manifestfilen.
kubectl apply -n $ns -f labs/containers/deployment.yaml
# Vent opptil 120 sekunder på at utrullingen av workshop-api fullføres.
kubectl rollout status -n $ns deployment/workshop-api --timeout=120s

Forventet: utrullingen fullføres og podene blir Ready.

3. Undersøk tilgang og logger

# Opprett en intern ClusterIP-tjeneste som ruter port 80 til containerport 8080.
kubectl expose -n $ns deployment workshop-api --port=80 --target-port=8080 --type=ClusterIP
# Vis den interne tjenesten og portene den bruker.
kubectl get service -n $ns workshop-api
# Les applikasjonsloggen fra podene i workshop-api.
kubectl logs -n $ns deployment/workshop-api
# Endre ønsket antall replikaer i workshop-api til to.
kubectl scale -n $ns deployment/workshop-api --replicas=2

Undersøk service-selector, pod-labels og target port. En ClusterIP er intern; port-forward gir din lokale testvei. Forklar hva du kontrollerer hvis en pod er ready, men klienten ikke når tjenesten.

Rydding og overgang til neste del

Slett bare ditt namespace etter å ha kontrollert navn og innhold. Bruker du arrangørens klynge, følger du arrangørens beskjed om hvem som sletter namespace; arrangøren sletter selve klyngen. For egen klynge:

# Kontroller ressursene i labnamespace-et før du sletter det.
kubectl get all -n $ns
# Slett labnamespace-et og ressursene inni det.
kubectl delete namespace $ns

Åpne deretter din egen AKS-ressurs i portalen → Delete og kontroller navnet før du bekrefter. Vent til slettingen er ferdig, og kontroller at den tilhørende nodegruppen er fjernet. Slett labregistryet når siste del som bruker det er ferdig. Hvis hele domene 1-gruppen bare inneholder ferdigbrukte labressurser, kan du følge oppryddingen av ressursgruppen for øvelsen. AKS-nodene blir ikke slettet ved å lukke terminalen.

Når du er ferdig, tilbakestill manifestet til Git-versjonen. Ved en ny gjennomføring setter du ACR-adressen på nytt i deploy-steget.

# Fra prosjektroten. Forkaster lokale endringer i denne kildefilen.
git restore --source=HEAD -- labs/containers/deployment.yaml
# Slett den lokale filen artifacts/deployment.before-faults.yaml hvis den finnes.
Remove-Item -LiteralPath artifacts/deployment.before-faults.yaml -ErrorAction SilentlyContinue

Avslutt og studer videre

Kontroller at ressursene som er ferdig brukt er ryddet. Forklar de viktigste valgene uten å lese oppskriften, og bruk pensumsiden for domenet til å se kompetansemål og videre studier. Studiedekning og begrensninger er den samme for begge formater.
