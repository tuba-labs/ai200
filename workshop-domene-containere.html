Én økt eller to samlinger

Én samlet økt omfatter hele domenet. Delingen i to samlinger er tematisk. Gjennomføringstiden er ikke målt; den avhenger av forkunnskaper, egne forsøk, diskusjon og klargjøring.

Vis øvelser for

Fremdrift deles mellom formatene på samme nettsted i denne nettleseren. Ved lokal bruk åpner du nettstedet via en lokal HTTP-server. Bytte av format gir samme oppgavedekning. Velg korte økter i stedet →

Klargjør før økten

Samling 1: Docker, Azure CLI, ACR og App Service. AKS og Container Apps trengs først i samling 2.

Samling 2: Ha ACR-imaget fra samling 1 tilgjengelig, og klargjør Container Apps, en Storage-kø og AKS. App Service trengs ikke her.

Oversikt for hele domenet

Ha Docker, Azure CLI, ACR-tilgang og et klargjort AKS-labmiljø tilgjengelig. Klargjør App Service og Container Apps etter forberedelsene i de aktuelle delene. Beregn ventetid ved ressursoppretting.

Start fra prosjektroten, der index.html og labs ligger, og lagre rotstien i hovedterminalen. Alle Python-deler bruker samme .venv. Nye terminaler åpnes i prosjektroten og aktiveres ved behov.

$projectRoot = (Get-Location).Path

Følg i tillegg forberedelsene i hver del. Installer pakkene som den aktuelle delen trenger. Ikke del nøkler eller innlogging når dere arbeider sammen.

Behold ressursene til de er ferdig brukt

Ressursplanen under gjelder denne samlede gjennomføringen. Ryddingen i delene er tilpasset overgangen til neste del. Slett bare dedikerte labressurser; en gruppe som også inneholder ressurser til senere deler må beholdes eller ryddes ressurs for ressurs.

Del 1

Bygg og feilsøk et container-image

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Docker med Linux-containere må kjøre. Start i prosjektroten og gå til labs/containers. app.py er ferdig testkode; Dockerfile er filen du skal forstå.

Set-Location labs/containers
docker version

1. Bygg et image

docker build -t ai200-api:v1 .
docker image ls ai200-api

Finn base-image, arbeidsmappe, COPY, bruker og CMD i Dockerfile. Forklar hvilke filer som bygges inn. Forventet: en lokal tag ai200-api:v1.

2. Kjør og feilsøk

docker run --detach --name ai200-api --publish 127.0.0.1:8080:8080 ai200-api:v1
Invoke-RestMethod http://localhost:8080/health
curl.exe -i http://localhost:8080/missing
docker logs --tail 20 ai200-api

Forventet: 200 fra /health og 404 fra /missing. Prosessen fortsetter å kjøre. Forklar hvorfor EXPOSE og portbindingen har ulike oppgaver.

3. Versjoner og tilbakerulling

Endre standardverdien for APP_VERSION fra v1 til v2 i app.py. Den gamle containeren beholder sin kopi til den erstattes.

docker build -t ai200-api:v2 .
docker stop ai200-api
docker rm ai200-api
docker run --detach --name ai200-api --publish 127.0.0.1:8080:8080 ai200-api:v2
Invoke-RestMethod http://localhost:8080/health

Forventet: v2. Gjenta med taggen v1 og bekreft v1. Et image bør kunne identifiseres entydig.

Rydding og overgang til neste del

Stopp og fjern den lokale testcontaineren. Behold imagene og kildefilene, og sett standardverdien APP_VERSION tilbake til v1 før neste del.

docker stop ai200-api
docker rm ai200-api
Del 2

Lagre images og bygg med ACR Tasks

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Ha Azure CLI innlogget, labfilene fra workshop 1 og et eget Basic-registry klart. Opprett det i portalen med administratorkonto deaktivert. Bruk registerets tilgangsmodell til å gi din bruker rett til image-operasjoner og Tasks. Registrer navnene i terminalen.

$acr = "DITT-REGISTRY-NAVN"
$rg = "DIN-LAB-GRUPPE"
$login = az acr show --name $acr --query loginServer -o tsv

1. Bygg i ACR

az acr build --registry $acr --image ai200-api:v1 labs/containers
az acr repository show-tags --name $acr --repository ai200-api --detail -o table

Bygget og lagringen skjer i Azure. Finn tagg og digest. En gjenbrukt tagg kan peke på nytt innhold; digest identifiserer innholdet. Kjør bygget med en ny tagg og sammenlign.

2. Bygg, push og kjør med Tasks

acr-task.yaml bygger med run-ID som tagg, lagrer imaget og kjører python --version i det.

Set-Location labs/containers
az acr run --registry $acr --file acr-task.yaml .
Set-Location ../..
az acr task list-runs --registry $acr -o table

Forventet: alle tre stegene fullføres, og Python-versjonen står i loggen. Finn task-kjøringen og den unike taggen. Forklar forskjellen mellom denne manuelle kjøringen og triggere fra kildekode, base-image eller tidsplan.

3. Hent og kjør

az acr login --name $acr
docker pull "$login/ai200-api:v1"
docker run --rm "$login/ai200-api:v1" python --version

Samme image kan brukes av App Service, Container Apps og AKS i de neste øktene.

Rydding og overgang til neste del

Behold ACR og imagene til App Service, Container Apps og AKS er gjennomført. Slett bare unødvendige testtagger nå.

Del 3

Kjør en container i App Service

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Ha ACR-imaget og et Linux App Service-plan/app klart i en egen labgruppe. Opprett webappen som Container og velg ACR-imaget ai200-api:v1. Bruk managed identity for image-pull.

1. Få containeren i gang

  1. Aktiver appens system-assigned managed identity og gi den lesetilgang til repositoryet i ACR. Velg riktig datarolle for registerets tilgangsmodell.
  2. Kontroller containerport 8080. For klassisk custom-container-konfigurasjon brukes app setting WEBSITES_PORT=8080; med sidecar-modellen settes porten på hovedcontaineren.
  3. Åpne https://DIN-APP.azurewebsites.net/health og Log stream. Ved image-pull-feil kontrollerer du identitet, rolle og image-tagg.

Forventet: JSON fra testappen og oppstartslogger.

2. Send konfigurasjon til containeren

Legg til WORKSHOP_MODE=review under Environment variables. Lagre, vent på restart og kall /health igjen. Forventet: mode blir review, uten nytt image. Finn appens konfigurasjonsendring og skill den fra en image-oppdatering.

3. Lever en testhemmelighet

Opprett app setting DEMO_SECRET=workshop-only og lagre. Dette er en offentlig øvingsverdi. Kall /health: secret_configured skal være true, mens selve verdien aldri returneres. Undersøk hvordan App Service lagrer og leverer innstillinger til containeren. Oppdater verdien og bekreft at samme image fortsatt brukes.

I workshop 19 lærer du å erstatte en lagret hemmelighet med en Key Vault-referanse og managed identity.

Rydding og overgang til neste del

Slett den dedikerte App Service-appen og planen når testen er ferdig. Behold ACR; det brukes i neste del.

Del 4

Miljøer og revisjoner i Container Apps

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Opprett en Container App med Consumption-miljø, ditt ACR-image og ekstern HTTP-ingress mot port 8080. Bruk managed identity med riktig ACR-leserolle. Alternativt klargjør arrangøren denne appen før økten. Ha appens navn, ressursgruppe, miljø og FQDN klart.

1. Undersøk miljø og ingress

Åpne appens Overview, Environment og Log stream. Kall /health. Noter miljøets nettverksvalg og forskjellen mellom appens inngangsadresse og containerens target port. Behold min 0 / maks 2 replikaer.

2. Opprett en ny revisjon

Aktiver Multiple revisions. Velg Edit and deploy og lag en revisjon med miljøvariabelen APP_VERSION=v2. Behold samme image slik at bare revisjonskonfigurasjonen endres. Finn begge revisjonsnavnene og vent til den nye er healthy.

3. Fordel trafikk og rull tilbake

Sett trafikk til 50 % på hver revisjon. Kall /health gjentatte ganger med curl.exe uten å gjenbruke cookies. Observer begge versjonene; få kall garanterer ikke en nøyaktig halvdeling. Sett deretter 100 % tilbake til v1. Bekreft at v2 ikke lenger får appens trafikk. Undersøk logger per revisjon.

Rydding og overgang til neste del

Deaktiver den ubrukte revisjonen, men behold Container App og miljø til KEDA-øvelsen i neste del.

Del 5

Hendelsesstyrt skalering med KEDA

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Bruk appen fra workshop 4 i Single revision-modus. Opprett en Storage-kø scale-demo i en separat labkonto. Legg Storage-connection-string inn som apphemmelighet queue-connection via portalen. Testappen demonstrerer skalering; den leser ikke meldinger fra køen.

1. Lag en KEDA-regel

I Scale: min 0, maks 2, Custom rule med typen azure-queue. Metadata: queueName=scale-demo, accountName lik Storage-kontoen og queueLength=5. Knytt autentiseringsparameteren connection til hemmeligheten queue-connection. Lagre og finn revisjonen som ble opprettet.

2. Gi køen arbeid

Legg minst 15 små meldinger i køen med Storage browser. Observer antall aktive replikaer og appens skaleringshendelser. Med terskel 5 tilsier 15 meldinger tre replikaer, men maksgrensen er 2. Vent gjennom polling og oppstart. Ved null aktivitet: sjekk kønavn, forbindelse og systemlogger.

3. Fjern arbeid og observer

Slett testmeldingene fra køen i Storage browser. Observer at nedskalering tar tid. Sammenlign pollingintervallet med cooldown; disse er ulike mekanismer. Diskuter hva som ville skjedd om en ekte worker fullførte meldingene underveis.

Rydding og overgang til neste del

Fjern kømeldingene, skaleringsregelen og labhemmeligheten. Container App og miljø kan nå slettes. Behold ACR til AKS-delen.

Del 6

Utrulling og feilsøking i AKS

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Klargjør før økten

En liten AKS-labklynge med kubectl-tilgang må være klar før økten. Arrangøren kan dele en klynge med ett namespace per deltaker. Klyngen trenger rett til å hente fra ACR; administrator kobler kubelet-identiteten til riktig ACR-rolle. Bruk kun labkonteksten, og opprett namespace ai200-dittnavn.

kubectl config current-context
kubectl create namespace ai200-dittnavn
$ns = "ai200-dittnavn"

1. Deploy et manifest

Kopier deployment.yaml og bytt image til ditt ACR-image. Behold ressursgrenser og readiness-proben.

kubectl apply -n $ns -f labs/containers/deployment.yaml
kubectl rollout status -n $ns deployment/workshop-api --timeout=120s
kubectl get pods -n $ns
kubectl port-forward -n $ns deployment/workshop-api 8082:8080

La videresendingen kjøre og kall /health på localhost:8082 i en annen terminal.

2. Fremprovoser og finn en feil

Avslutt port-forward. Endre imagetaggen i manifestet til finnes-ikke, apply og undersøk:

kubectl get pods -n $ns
kubectl describe pods -n $ns
kubectl get events -n $ns --sort-by=.lastTimestamp
kubectl rollout undo -n $ns deployment/workshop-api

Forventet: ImagePullBackOff og en forklarende hendelse. Rull ut en ny endring med readiness-sti /missing; sammenlign en levende prosess med en ready pod. Rett tilbake til /health.

3. Undersøk tilgang og logger

kubectl expose -n $ns deployment workshop-api --port=80 --target-port=8080 --type=ClusterIP
kubectl get service -n $ns workshop-api
kubectl logs -n $ns deployment/workshop-api
kubectl scale -n $ns deployment/workshop-api --replicas=2

Undersøk service-selector, pod-labels og target port. En ClusterIP er intern; port-forward gir din lokale testvei. Forklar hva du kontrollerer hvis en pod er ready, men klienten ikke når tjenesten.

Rydding og overgang til neste del

Slett ditt labnamespace etter kontroll av innholdet. Slett en egen labklynge og ACR etter siste bruk; eieren rydder en delt klynge.

kubectl get all -n $ns
kubectl delete namespace $ns

Kontroller at ressursene som er ferdig brukt er ryddet. Forklar de viktigste valgene uten å lese oppskriften, og bruk pensumsiden for domenet til å se kompetansemål og videre studier. Studiedekning og begrensninger er den samme for begge formater.
