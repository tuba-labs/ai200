Self-paced / Chapter 09 of 10

Make the queue drive scaling

Observe zero workers, a bounded backlog, multiple workers, completed answers and a return to zero.

~30 minutes · estimateBash · repository rootCore path

You will learn: KEDA's scaler identity, queue metrics, activation, HPA scaling and scale-to-zero.

Starting requirements: at least one manual is ready and a single chat worker successfully answered a question. There should be no unrelated requests waiting.

Shell and directory: two Bash terminals, both at the repository root. The producer terminal has workshop/.tools/venv activated; the observer uses the supplied script's isolated kubeconfig.

Give scaling to KEDA

Bash · repository root
bash workshop/scripts/09-keda.sh
bash workshop/scripts/demo-scaling.sh start

Canonical commands: commands.sh

k8s/keda.yaml defines a TriggerAuthentication with the KEDA identity's client ID and a ScaledObject targeting only products-chat. The scaler polls every 10 seconds, activates on any active request, targets two active messages per worker, allows zero to three replicas, and uses a 60-second cooldown. HPA scale-down stabilization can add another observation delay.

KEDA reads event-source metrics and changes desired replica counts. It does not receive questions or run RAG processing. The worker still consumes and acknowledges messages. The KEDA operator needs its own federated credential, service-account annotation, Pod label and Service Bus Data Receiver role; the worker identity does not automatically supply these.

The demo switch enables an explicit 20-second per-request delay so the small, bounded backlog remains visible long enough for scaling. It is off in the normal worker manifest. No extra artificial LLM requests are hidden in the delay. Turn it off after the exercise.

Terminal A: watch a complete cycle

Bash · repository root
bash workshop/scripts/watch-scaling.sh

Canonical commands: commands.sh

First wait until the chat deployment reaches zero. Products should stay at one. The observer runs for at most eight minutes; Ctrl+C stops only the observer. It shows deployment replica counts and the request queue's active/dead-letter counts. Azure management counts are sampled and may lag; compare several observations.

Terminal B: submit bounded work

Bash · repository root
# shellcheck source=/dev/null
source workshop/.tools/venv/bin/activate
python workshop/tools/load.py --count 8

Canonical commands: commands.sh

The tool submits eight persisted questions through Products, using a ready manual, then waits boundedly for all replies. It refuses more than twelve. Each uncached request normally makes one question embedding call and one chat call, so tokens are billed. This is a scaling exercise, not a throughput benchmark.

  1. Idle: chat replicas are 0, request backlog is 0, Products remains 1.
  2. Arrival: active messages appear after Products dispatches the committed outbox.
  3. Activation: KEDA starts a worker after its next successful poll.
  4. Scale-out: enough backlog remains for HPA to request more than one worker, capped at 3.
  5. Completion: the producer prints completed request IDs; active backlog drains.
  6. Cooldown: after idle metrics, cooldown and stabilization, workers return to 0.

These are the required observations to make on your deployment, not fabricated captured output. Note the actual maximum replica count and the rough time back to zero in your walkthrough notes. Use the maintainer checklist if a phase is not visible.

Change the threshold and compare

Bash · repository root
bash workshop/scripts/demo-scaling.sh threshold 4
python workshop/tools/load.py --count 8
bash workshop/scripts/demo-scaling.sh stop

Canonical commands: commands.sh

After the first cycle is idle, target four messages per worker rather than two and send the same bounded load. Expect less aggressive scale-out under comparable backlog; exact timing depends on model latency and metric polling. The last command disables the delay and reapplies the normal scaler settings. Do not leave the demonstration delay enabled for ordinary use.

Why this fits one node

One D4ds_v5 node has four vCPUs and 16 GiB before system reservations. Products requests 500m CPU / 768 MiB, each worker 250m / 384 MiB; three workers plus Products leave room for system components and a rollout. Node autoscaling is disabled. A pending Pod means inspect allocatable capacity and existing workloads rather than assuming KEDA must also create nodes.

Queue depth determines the desired scale. Concurrency is one request per worker here. Prefetch is zero so a worker does not lock a large invisible backlog in its local buffer. Model quota can throttle additional workers: scaling above quota may increase retries, not throughput. Cooldown is intentionally short for this exercise; cold starts still take time.

Verification: observe all six phases, all eight completed answers, no new dead letters, and Products still serving at one replica. Disable the delay. If you only observed one worker, investigate and repeat the bounded exercise before marking this chapter complete.

Common failures

  • ScaledObject Ready=False or 401/403: describe it and inspect kube-system/keda-operator logs. Check the operator's identity/federated subject, not just the chat service account. Rerun stage 04 after correcting assignments.
  • Workers never reach zero: check queue backlog, active requests, cooldown/stabilization and whether another manual scaling command or controller is competing. Do not manually keep replicas at one after handing control to KEDA.
  • Only one worker appears: verify the 20-second delay applied to new pods, threshold=2 and prefetch=0. Check HPA metrics and watch long enough. Do not turn the load generator into an infinite loop.
  • Pods Pending: describe the Pod and inspect node allocatable resources. Keep the supplied resource requests and maximum three workers; quota expansion is not needed for this bounded example.
  • Model 429: lower the scaler maximum/producer count or obtain model quota. More replicas cannot overcome a service token limit.

Continue when: you have seen a full scaling cycle and restored normal settings. Next run the final smoke test and clean up.
