Chapter 09 of 10

Make the queue drive scaling

Scale the worker from zero with a bounded queue backlog.

~30 minBash · repository root

Requires: chat works, demo tools are installed and all manuals are ready.

Enable queue-driven scaling

Bash · repository root
bash workshop/scripts/09-keda.sh
bash workshop/scripts/demo-scaling.sh start

Canonical commands: commands.sh

KEDA scales ProductsChat from zero to three workers. Products stays at one.

The demo temporarily adds a 20-second delay per request to make backlog visible. Normal operation has no delay.

Terminal A: observe

Bash · repository root
bash workshop/scripts/watch-scaling.sh

Canonical commands: commands.sh

Wait for chat to reach zero; Products stays at one. The observer shows replicas and active/dead-letter counts for up to eight minutes.

Terminal B: send eight questions

Bash · repository root
# shellcheck source=/dev/null
source workshop/.tools/venv/bin/activate
python workshop/tools/load.py --count 8

Canonical commands: commands.sh

This submits eight persistent questions and waits for their answers (hard maximum twelve). Each normally incurs one embedding + one chat call.

Observe: idle 0 → queued messages → worker starts → more than one worker → completed answers → cooldown back to 0. Management metrics can lag; record actual replicas/timing.

Compare threshold 4, then reset

After the first cycle returns to idle:

Bash · repository root
bash workshop/scripts/demo-scaling.sh threshold 4
python workshop/tools/load.py --count 8
bash workshop/scripts/demo-scaling.sh stop

Canonical commands: commands.sh

Targeting four messages per worker should scale less aggressively under similar backlog. The final command restores normal settings and disables the delay.

Verification: both cycles complete, the first exceeds one worker, no new dead letters, and chat returns to zero. Products stays at one; demo delay is off.
What affects scaling?

keda.yaml scales only ProductsChat: 0–3 replicas, two active messages per worker, 10-second polling, 60-second cooldown. KEDA reads metrics; workers process messages. Its scaler uses a separate identity.

Queue depth drives desired replicas; worker concurrency is one and prefetch zero. Model quota can throttle extra workers. Polling, cold starts, cooldown and HPA stabilization affect timing.

The single D4ds_v5 node has four vCPUs/16 GiB before reservations. Products requests 500m/768 MiB; each worker 250m/384 MiB. Maximum three workers fits without node autoscaling.

Troubleshooting
  • ScaledObject not Ready / 403: inspect its conditions and kube-system/keda-operator logs; check the scaler's federation/Receiver role, not only the worker's.
  • Only one worker: confirm delay=20, threshold=2 and prefetch=0; inspect HPA metrics. Repeat bounded load only after diagnosis.
  • Never zero: check backlog, cooldown/stabilization and competing manual scaling.
  • Pending / model 429: inspect Pod capacity or reduce max replicas/load; more replicas cannot overcome model quota.
