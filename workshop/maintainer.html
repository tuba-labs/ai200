Before the first Azure run

This is a participant-path checklist, not an instructor timetable. Record actual outcomes, elapsed time, region, selected versions and fixes. The proposed core duration is an estimate until a person follows it successfully.

  1. Build the static site with python scripts/build.py. Serve the repository at the documented base path and follow the workshop link from the main page. Check navigation, copy, search, source viewer, theme and persisted completion/reset.
  2. Use a clean, suitable subscription scope or a fresh workshop prefix. Run prerequisite checks without bypassing missing permissions or quota. Confirm the actual selected subscription with the owner.
  3. Review the cost estimate, create only the model stage, and require the actual identity-based embedding/chat probe to pass before AKS/database provisioning starts.
  4. Start stage 02, then perform the Docker chapter while provisioning runs. Record whether this overlap is enough to keep the main path near four hours.
  5. Wait through stage 03. Verify the VM is Ready, Functions is on Flex/Python 3.12, PostgreSQL has private networking and VECTOR is allowlisted. No internet-wide database firewall rule should exist.
  6. Complete roles/settings/federation. Inspect the KEDA operator's identity separately, and confirm the kubelet can pull both image tags.

Reproduce local software checks

verify-local.sh runs local verification with a disposable loopback-only PostgreSQL/pgvector container and removes that container on exit. It requires Java 21, Docker and Python 3.12+. Its model fixtures are deterministic: passing them does not demonstrate Azure identity or live model behavior.

Run bash workshop/scripts/verify-local.sh. Use python -m playwright install chromium inside the verification environment before the browser suite, or set BROWSER_EXECUTABLE to a compatible installed Chromium/Edge executable. The browser tests run at /ai200/workshop/, not only at the host root.

For infrastructure, compile all four Bicep files with for file in workshop/infra/*.bicep; do az bicep build --file "$file" --stdout > /dev/null; done and perform ARM/server-side validation in the intended subscription before a clean deployment. Run bash -n and ShellCheck on the scripts. Validate rendered standard manifests against Kubernetes schemas and KEDA resources against the official add-on CRDs; then validate against the actual cluster with kubectl apply --dry-run=server before applying.

The supplied python workshop/tools/validate_manifests.py creates non-secret fixture renderings and validates the custom resources against official KEDA 2.18.2 CRDs. Standard resources can be checked with the pinned kubeconform container, as reproduced in the repository's workshop-checks workflow. These offline structures do not prove live cluster admission, current Azure capacity or identity propagation.

Record what actually happened

Update VALIDATION.md with command summaries and dates. Separate local fixture results, container results, ARM/schema checks, live model probes and the actual deployment smoke result. Do not turn “expected output” from a chapter into an observed result. Record any Azure blocker explicitly and leave its acceptance row unverified.

If the path takes substantially longer than four hours after prerequisites, record the slow chapters. Keep advanced indexing, identity hardening and production operations optional; do not remove the requested core learning goals just to claim a shorter duration.
