Deploy Products to AKS

Read a Deployment, Pod and Service; then open a restricted HTTPS endpoint and inspect its rollout.

~20 minutes · estimateBash · repository rootCore path

You will learn: the relationship between a Deployment, Pod, Service, probes and a rollout.

Starting requirements: stages 03–05 pass; images exist in ACR and the kubelet can pull them.

Shell and directory: Bash, repository root. For manual commands use export KUBECONFIG="$PWD/workshop/.state/kubeconfig" in each new terminal.

Read the Kubernetes resources

k8s/products.yaml declares a namespace, an annotated service account, a bootstrap ConfigMap and a Deployment with one replica. The Deployment controller keeps the desired Pod running. A Pod is the smallest Kubernetes scheduling unit; here it contains one Java container. Its labels connect the Deployment selector, the Service and the identity webhook.

The Pod requests 500 millicores and 768 MiB so the scheduler can reserve capacity; its larger limits bound usage. Startup allows time for configuration, PostgreSQL connection and Flyway migration. Readiness includes database health; liveness checks whether the process is alive. A temporary database outage should remove the Pod from ready traffic rather than cause a liveness restart loop.

k8s/service.yaml is a LoadBalancer Service: a stable entry point whose selector finds Products Pods. Port 443 forwards to the container's HTTPS port 8443. It restricts callers to the configured public IPv4 /32. A Service forwards traffic; it does not run application code.

Create the endpoint and deploy

Bash · repository root
bash workshop/scripts/06-products.sh

Canonical commands: commands.sh

The script applies the namespace and Service first, waits boundedly for the public IP, and generates a short-lived self-signed certificate for that IP. It installs the certificate/private key as a Kubernetes TLS Secret, renders only known non-secret manifest values, applies the Deployment, waits for rollout and checks HTTPS readiness using the saved certificate.

Endpoint assumptions: this is a real public HTTPS endpoint, restricted by source IP and requiring sign-in. Its certificate is self-signed and valid for two days. Compare the script's SHA-256 fingerprint with the browser's certificate before accepting the warning. Do not disable TLS verification globally. The supplied tools trust only workshop/.state/tls.crt. Production needs a trusted certificate, DNS, SSO and an access design.

The script prints the actual URL and saves it in .state/endpoint.txt. Open it in your browser. Use username participant. Deliberately retrieve the random password with bash workshop/scripts/credentials.sh in your own interactive terminal; the helper refuses redirected output. Do not paste the password into this documentation site's search, progress storage or a URL.

Inspect a working rollout

After setting this terminal's kubeconfig as above, run kubectl get deployment,pods,service -n products. Expect one ready Products replica, a Pod whose name was generated by the Deployment, and a load balancer IP. Run kubectl logs deployment/products -n products --tail=50 and find the Flyway schema creation/validation and Java startup lines. The exact Pod name and output will differ.

Use kubectl describe pod -n products -l app=products to inspect events, identity-injected variables, mounted volumes and probe configuration. Pod events explain image-pull, scheduling and readiness failures more directly than repeatedly refreshing the browser.

Try kubectl rollout restart deployment/products -n products followed by kubectl rollout status deployment/products -n products --timeout=300s. It starts a new Pod from the same image and persisted database; Flyway should not create the schema again. The core has one node, so a rolling update depends on the spare capacity left by the small resource requests.

Open Upload product, but do not index yet

The empty product list and upload form should render. It is possible to upload now, but Event Grid is not subscribed until the next chapter. To avoid a stranded demonstration upload, wait until the Function and subscription are ready before creating your first product. Event Grid does not automatically replay a BlobCreated event that happened before the subscription existed.

Verification: open the real URL, sign in, and see both “Upload product” and “Chat about products”. The readiness request must report UP. Restart Products once and confirm it returns ready with its existing schema.

Common failures and exact next checks

  • ImagePullBackOff: use kubectl describe pod; compare the rendered ACR image/tag with the push and verify the kubelet principal's AcrPull assignment. The workload's blob identity does not pull the image.
  • CrashLoopBackOff: run kubectl logs -n products deployment/products --previous if a container restarted. Check App Configuration, Key Vault and private PostgreSQL reachability in that order.
  • Browser cannot reach the IP: confirm the current network still has the configured public IPv4. A changed VPN/egress IP will be blocked. Update allowedCidr to the new exact /32 and rerun the stage; never replace it with the entire internet.
  • Certificate expires: rerun stage 06; it regenerates a near-expiry certificate. Restart Products to load a changed mounted certificate, then compare its new fingerprint.
  • 403 on a write API: CSRF protection remains enabled. The UI uses it automatically; smoke/load clients first request a session token from /api/csrf.

Continue when: Products is ready and accessible. Next, connect the upload event to actual embedding work.
