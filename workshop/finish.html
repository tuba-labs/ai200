Verify, diagnose and clean up

Run the real-deployment smoke test, diagnose failures and deliberately remove only workshop resources.

~15 minutes · estimateBash · repository rootCore path

You will learn: how to verify an asynchronous system without guessing model wording, locate its separate failure queues and remove resources deliberately.

Starting requirements: all core components are deployed, KEDA is Ready, the demo delay is disabled and the sample manuals are indexed.

Shell and directory: Bash, repository root; activate the verification virtual environment in this terminal.

Run the real-deployment acceptance check

Bash · repository root
# shellcheck source=/dev/null
source workshop/.tools/venv/bin/activate
python workshop/tools/smoke.py

Canonical commands: commands.sh

tools/smoke.py first checks ARM deployment states, the Ready Products rollout, Function discovery, event subscription and queue configuration. It verifies database readiness through Products, uploads a new Aurora manual, waits up to seven minutes for indexing, submits a temperature question with a product filter, and waits up to eight minutes for its persisted reply.

It checks the request/correlation IDs, a non-empty answer and a returned passage containing the known temperature specification with the correct product/manual IDs. It does not assert exact LLM wording. Its non-secret result report is saved under .state/smoke-result.json. Passwords stay in process memory, TLS verification uses the exact local certificate, and no credential is placed in a URL.

Verification: expect the tool to report a real upload → Function indexing → queue/worker → correlated answer with relevant references. That line counts as a successful deployment check only if the tool actually ran successfully in your subscription. Consult the validation report for the maintainer's observed results.

Diagnose the failing boundary

Bash · repository root
bash workshop/scripts/diagnostics.sh

Canonical commands: commands.sh

SymptomInspectConcrete action
Upload failedProducts logs and its waiting/failed rowCheck its Blob Data Contributor role and storage endpoint. Retry as a new product after the cause is fixed.
Waiting manualEvent subscription filter/delivery and Function discoveryVerify the private manuals container/path, Blob-extension webhook key and code publication. A pre-subscription upload needs a new product or a deliberate replay.
Failed indexingFunction telemetry, host poison queue, PostgreSQL connectivityUse the manual ID in logs; fix model quota/identity/dimensions, then replay the immutable blob. Never change a ready manual in place.
Queued questionOutbox warnings, request queue, ScaledObject conditionsCheck sender/scaler/receiver roles separately. Inspect workload federation and queue namespace.
Processing questionWorker logs, model throttling, message renewal and request deadlineUse the request/correlation IDs. Inspect failed/dead-lettered messages; repair the cause before resubmitting a new question.
Bad answer/sourceSelected product, actual chunks and promptRead evidence, try a focused product filter and inspect retrieval count. An LLM's plausible sentence is not proof of grounding.

Function runtime traces are in the workshop's Application Insights resource. The supplied infra/function-logs.kql selects recent manual-ID logs and warnings. It is a small log-inspection example, not a claim that end-to-end OpenTelemetry tracing has been implemented across Java, the Function and the worker.

There are three distinct dead-letter/poison locations: Event Grid's private event-deadletters blob container, the Blob extension's webjobs-blobtrigger-poison host-storage queue, and each Service Bus queue's $DeadLetterQueue subqueue. A message arriving in one does not imply that the next component ever ran. Avoid dumping event-subscription destination URLs: the Blob webhook URL contains its system key.

Deliberately clean up

Bash · repository root
bash workshop/scripts/cleanup.sh

Canonical commands: commands.sh

The cleanup tool checks the exact subscription and workshop group tag, lists the resources it will delete, names AKS's managed node resource group, and requires you to type DELETE plus the complete group name. It only requests deletion of the tagged workshop group; AKS removes its managed node group as part of its lifecycle. It never deletes arbitrary similarly named groups.

Deletion is asynchronous. Run the exact az group exists command printed by the tool until it returns false, and verify the managed node group is gone. Azure locks or policy can prevent cleanup; inspect the failed operation instead of assuming costs have stopped.

Key Vault secrets/vault remain soft-deleted for seven days; App Configuration uses a one-day soft-delete period. No automatic purge is performed. Names may not be immediately reusable. This workshop does not create resources in an existing shared group. Resource-provider registration remains at subscription level and is intentionally not unregistered.

After Azure confirms deletion, remove the local workshop/.state directory if you no longer need its non-secret notes, kubeconfig and short-lived TLS private key. Review the exact directory before any recursive deletion. Keep the repository source and documentation; the website itself can still run with no Azure access.

What you have exercised

  • Built, tagged, run and pushed a Java container, then inspected its AKS Deployment, Pod, Service, probes and rollout.
  • Used Flyway and PostgreSQL/pgvector for products, chunks, persistent work and explicit vector retrieval.
  • Separated Blob notifications/Event Grid/Functions from queued application communication through Service Bus.
  • Configured workload/managed identity, real Key Vault secrets and ordinary App Configuration settings with explicit restart behavior.
  • Observed KEDA scale only the worker from zero and back, with a finite producer and finite token spend.
Optional extensions after the first successful walkthrough

Add trusted TLS and Entra sign-in, separate migration/runtime database roles, private endpoints for public Azure services, retries with backoff/jitter and richer operational dashboards, manual-version lifecycle, tested token-aware chunking, or measured ANN indexing. Keep each extension separate from the working core baseline.

Before you finish

If smoke failed, retain the printed IDs and use the first-run checklist to record the failing boundary. If cleanup is still running or blocked, keep monitoring costs. Marking a documentation chapter complete does not perform cleanup or validate Azure.

A reading checklist, not proof of a successful Azure deployment.
