Self-paced / Chapter 01 of 10

A small system, end to end

Deploy an event-driven product-manual assistant. Follow uploads, indexing, questions and answers through the whole system.

~15 minutes · estimateBash · repository rootCore path

The outcome: upload a fictional product manual, wait for indexing, and ask a question whose answer includes the actual supporting passages. You receive all application code. Your work is to understand, configure, deploy and inspect it.

You will learn: how a small RAG system fits together, which component owns each state transition, and how to follow this self-paced path.

Starting requirements: experience writing software. Azure, Python, Docker, Kubernetes and RAG can be new to you. The next chapter checks your environment before anything paid is created.

Working context: read here; all later commands run in Bash from the repository root, the folder containing the site's index.html.

Before you start

Prepare an Azure account with an active subscription, permission to create resources and assign roles, and quota/access for the chosen VM and models. Locally you need Azure CLI, Bicep, Docker, kubectl, Java 21, Python 3.12+, Git and the supporting Bash tools. Windows participants use Ubuntu 24.04 in WSL2 with Docker Desktop integration. You create your own AKS cluster during the workshop.

Use the full pre-workshop checklist and downloadable Windows/Ubuntu setup scripts before beginning the four-hour core path. Installation, restarts and account/quota approvals are preparation time. Terms throughout the workshop use the site's dotted-underlined tooltips; the shared jargon page contains all definitions and sources.

What you will deploy

Products is a Java 21 / Spring Boot application on AKS. It has two views: upload a product and chat about products. Thymeleaf renders the pages; a little browser JavaScript polls for status. JDBC and explicit SQL persist products, questions and answers. There is no ORM or separate SPA.

ProductsEmbedder is a small Python Azure Function. A Blob Storage notification starts it. It turns UTF-8 manual text into chunks and embeddings and stores them in PostgreSQL with pgvector.

ProductsChat is a Python container on AKS. It receives questions from Service Bus, retrieves relevant chunks, calls an Azure-hosted chat model and publishes a reply. KEDA changes its replica count. Products keeps at least one replica running.

The upload and embedding flow

Blob Storage organizes objects as containers containing blobs. A storage container is not a Docker container. Event Grid carries a notification that something happened; the notification does not contain the manual itself. The Blob trigger's extension fetches it using the Function's managed identity.

The question and answer flow

Embeddings support retrieval: related text should be nearby in vector space. They do not write the answer. The LLM generates an answer from the question and the retrieved reference text. The reference text is untrusted data, never an instruction to override the application prompt.

The four-hour boundary

The ten core chapters total an estimated 240 minutes, once tools and Azure access are ready. Start long provisioning early and read/build while it runs. Model-access approvals, quota increases, large downloads and unusual provisioning delays are outside that estimate. This duration has not been established by a timed participant walkthrough.

This is selected AI-200 practice, not complete exam preparation. You exercise ACR, AKS manifests, PostgreSQL/vector retrieval, Service Bus, Event Grid, Functions, Key Vault and App Configuration. The exam specifically places one KEDA objective under Container Apps; our AKS KEDA exercise teaches the mechanism without claiming to cover Container Apps revisions. See the concise objective mapping.

Optional depth: deliberately outside the core path

Production SSO, public CA certificates, a custom domain, private endpoints for every Azure service, independent database roles, manual replacement/deletion, ANN index tuning and distributed tracing are extensions. The core uses one small database owner, one AKS node and an IP-restricted, self-signed HTTPS endpoint. These choices are documented rather than presented as production defaults.

Check your understanding

Verification: locate the three application directories in the source explorer. Explain why upload success is different from a manual being ready, and why Event Grid and Service Bus both appear. Then continue to the prerequisite checker.

Common starting mistakes

  • Expecting the documentation to provision Azure: this website is static and needs no Azure credentials. Only explicitly executed scripts create cloud resources.
  • Starting with an existing cluster: none is required. The supplied stages create a separate workshop AKS cluster and isolate its kubeconfig.
  • Using real product documents: use the three fictional manuals provided. The application calls a paid Azure model and is not a production data-handling platform.

A reading checklist, not proof of a successful Azure deployment.
