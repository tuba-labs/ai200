Self-paced / Chapter 05 of 10

Connect data, settings and identity

Configure private PostgreSQL, Flyway, private blobs, Key Vault secrets and App Configuration settings.

~30 minutes · estimateBash · repository rootCore path

You will learn: schema migration versus data, vector shape, private networking, and the distinction between settings, secrets and identity.

Starting requirements: stages 01–02 were submitted successfully; images have been built. Slow provisioning may still be running.

Shell and directory: Bash, repository root. The scripts isolate kubectl in workshop/.state/kubeconfig; set that path explicitly for manual kubectl commands.

Wait, then configure access

Bash · repository root
bash workshop/scripts/03-ready.sh
bash workshop/scripts/04-configure.sh

Canonical commands: commands.sh

03-ready.sh waits for actual ARM completion, reports failed operations, gets this cluster's credentials into its own kubeconfig, waits for a Ready node and checks the PostgreSQL extension allowlist. It does not open a public PostgreSQL firewall rule. Your laptop normally cannot connect directly to the private database.

04-configure.sh assigns data-plane roles, creates federated credentials, grants the kubelet identity AcrPull, configures KEDA's own identity, and writes ordinary settings. It retries boundedly for directory/RBAC propagation. Resource creation permissions do not automatically grant a workload permission to read a blob, secret, setting or queue.

Follow identity to settings and secrets

AKS workload identity requires all three: the service account's azure.workload.identity/client-id annotation, the Pod's azure.workload.identity/use: "true" label, and an Azure federated credential with the exact issuer, subject and audience. The webhook injects token-file/environment bootstrap. See k8s/products.yaml and scripts/04-configure.sh.

The only application-specific bootstrap environment settings are APP_CONFIG_ENDPOINT and its workshop label. The SDK credential uses the workload/managed identity. App Configuration supplies the Key Vault URI and ordinary service settings. Then the application reads the PostgreSQL password from Key Vault. The Java application also reads its browser sign-in password there. These values are not Kubernetes environment variables or image layers.

Read the Flyway migration

Products runs the supplied Flyway migration during startup, before serving application requests. Flyway records its version/checksum in flyway_schema_history. A second startup validates/reuses the existing migration; do not edit an applied migration to change a live schema.

apps/products/src/main/resources/db/migration/V1__products_and_messages.sql creates vector and the product, chunk, chat, outbox and result-cache tables. PostgreSQL must first allowlist VECTOR; Bicep does that at server level. Flyway then runs as workshopadmin, the database owner created by this workshop. That account can create the allowlisted extension and all tables.

The core deliberately uses the same database owner's credentials in all three applications to keep the first deployment small. They are stored only in Key Vault and retrieved at startup. This grants broader database access than a production application should have. Independent migration/runtime SQL roles or Entra PostgreSQL authentication are optional extensions, not secretly assumed setup.

InvariantImplementation
Document/question vector agreementBoth call the embedding deployment and request 1536 dimensions; the table is vector(1536). Code rejects non-finite or incorrectly sized vectors.
Retry-safe chunksPrimary key (manual_id, chunk_index); all chunk writes and the ready state commit atomically.

Persistent asynchronous chatQuestions + outbox commit together; worker results are cached by request ID; terminal replies cannot overwrite a displayed answer.

Notice upload ordering

The product row commits before Blob upload starts. If upload fails, Products marks the record failed. If a process dies between those operations, the record may remain waiting; the timeout sweep marks old work failed. A participant retries by creating a new product/manual, not by mutating the old blob. The embedder checks the stored checksum and IDs before indexing.

Optional: inspect the full SQL or think about production changes
apps/products/src/main/resources/db/migration/V1__products_and_messages.sql
-- Azure must allowlist VECTOR before Flyway runs. Run as the database owner.
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE products (
    id uuid PRIMARY KEY,
    name varchar(120) NOT NULL,
    manual_id uuid NOT NULL UNIQUE,
    blob_name text NOT NULL UNIQUE,
    manual_sha256 char(64) NOT NULL,
    status text NOT NULL DEFAULT 'waiting'
        CHECK (status IN ('waiting', 'processing', 'ready', 'failed')),
    error text,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

-- No ANN index: an exact cosine scan is easier to inspect for three manuals.
CREATE TABLE manual_chunks (
    manual_id uuid NOT NULL REFERENCES products(manual_id),
    product_id uuid NOT NULL REFERENCES products(id),
    chunk_index integer NOT NULL CHECK (chunk_index >= 0),
    content text NOT NULL,
    embedding vector(1536) NOT NULL,
    embedding_deployment text NOT NULL,
    PRIMARY KEY (manual_id, chunk_index)
);
CREATE INDEX manual_chunks_product ON manual_chunks(product_id);

CREATE TABLE chat_requests (
    id uuid PRIMARY KEY,
    correlation_id uuid NOT NULL UNIQUE,
    product_id uuid REFERENCES products(id),
    question varchar(1000) NOT NULL,
    status text NOT NULL DEFAULT 'queued'
        CHECK (status IN ('queued', 'processing', 'completed', 'failed')),
    answer text,
    sources jsonb NOT NULL DEFAULT '[]',
    error text,
    created_at timestamptz NOT NULL DEFAULT now(),
    deadline timestamptz NOT NULL DEFAULT now() + interval '8 minutes',
    updated_at timestamptz NOT NULL DEFAULT now()
);

-- Commit the request and its outgoing message together. A crash after sending
-- may resend it; the worker's persistent result cache handles that duplicate.
CREATE TABLE chat_outbox (
    request_id uuid PRIMARY KEY REFERENCES chat_requests(id),
    payload jsonb NOT NULL,
    sent_at timestamptz,
    attempts integer NOT NULL DEFAULT 0
);
CREATE TABLE chat_results (
    request_id uuid PRIMARY KEY REFERENCES chat_requests(id),
    correlation_id uuid NOT NULL,
    payload jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

Source: apps/products/src/main/resources/db/migration/V1__products_and_messages.sql

The small dataset does not justify an approximate-nearest-neighbor index. For a large corpus, compare an exact scan with HNSW/IVFFlat, recall, memory and query plans. An index is a measured optimization, not a required RAG decoration.

Verification and common failures

Verification: stage 03 should report a Ready node and VECTOR; stage 04 should finish configuration without printing secret values. Flyway runs in the next chapter when Products starts. No fabricated SQL output is presented here.
  • PostgreSQL hostname resolves publicly or not at all inside a Pod: inspect the private DNS zone's VNet link and the database's delegated subnet. Do not solve it with a public 0.0.0.0/0 firewall rule.
  • Key Vault / App Configuration returns 403: check the workload's principal ID and the exact resource scope; wait for the bounded propagation retries. A CLI login as yourself does not configure the Pod identity.
  • Flyway cannot create vector: check azure.extensions and confirm you are using the configured database owner. Do not use pgvector as the SQL extension name; the extension is vector.
  • KEDA later shows authentication errors: the scaler has a separate identity/federated credential, not the worker's service account. Its configuration is completed here for the later exercise.

Continue when: the cluster, database, identities and ordinary settings are ready. Next, deploy Products and observe Flyway startup.
