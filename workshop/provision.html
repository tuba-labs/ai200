Start the Azure resources

Prove model access, create the shared network, then start AKS and PostgreSQL while you work on Docker.

~20 minutes · estimateBash · repository rootCore path

You will learn: how to provision dependent Azure resources in understandable stages and prove model access before starting a cluster.

Starting requirements: the prerequisite checker passes; the selected subscription, region and source IP are correct.

Shell and directory: Bash, repository root. Keep the virtual environment available for later verification tools.

Read the cost boundary first

This is a paid workshop. A planning estimate checked on 11 November 2026 is roughly US$5–15 for one four-hour walkthrough with the small sample and prompt cleanup, before tax, discounts and subscription-specific rates. This is an allowance, not a measured bill or a guaranteed price. Resources left running for a day can cost materially more.

Main drivers are the AKS VM and disk, PostgreSQL compute/storage, NAT gateway and public IPs, Standard Service Bus/App Configuration, model tokens, and any diagnostic ingestion. AKS's Free management tier does not make its VM free. GlobalStandard model processing may occur outside the account's region. Check the Azure calculator and your subscription's actual offers; the reference page lists cost drivers. You will deliberately confirm the group name before the first creation.

Start the first two stages

Bash · repository root
bash workshop/scripts/01-models.sh
bash workshop/scripts/02-provision.sh

Canonical commands: commands.sh

Stage 01: models before machines

scripts/01-models.sh checks prerequisites again, creates a tagged workshop-only resource group, and deploys infra/models.bicep. It creates an Azure OpenAI resource with key authentication disabled, a chat deployment named chat, and an embedding deployment named embedding. Versions, SKUs and requested capacities come from the bootstrap configuration.

The default chat model is gpt-5-mini, version 2025-08-07; the embedding model is text-embedding-3-small, version 1. tools/model_probe.py obtains an Entra token, requests one 1536-dimensional embedding, and checks for a non-empty chat response. RBAC propagation retries are bounded. Model tokens are billed even during this small test.

If that stage fails, no AKS or database provisioning has begun. Fix model access, regional deployment support or quota first. The tool does not silently substitute a different model or change vector dimensions.

Stage 02: foundation, then independent long operations

infra/foundation.bicep creates a virtual network with separate AKS, Functions and PostgreSQL subnets; a NAT gateway with a static egress IP; private PostgreSQL DNS; ACR; a storage account and private containers; request/reply queues; Key Vault; App Configuration; five managed identities; and Function telemetry. It explicitly provides outbound connectivity instead of relying on implicit default outbound access.

After the foundation is ready, the script creates random PostgreSQL and browser passwords directly in Key Vault. Values are not printed. The PostgreSQL secure ARM parameter is written to a permission-restricted temporary file only while submitting that deployment, then deleted. Never enable shell tracing with set -x around these scripts.

infra/database.bicep creates PostgreSQL 17 Flexible Server on the delegated private subnet, a database called products, and the VECTOR extension allowlist setting. infra/compute.bicep independently starts one-node AKS with workload identity, OIDC and the KEDA add-on, and a Python 3.12 Flex Consumption Function app integrated into its delegated subnet.

Use the provisioning time

The command returns after ARM accepts the two long deployments; it does not claim they are ready. Now continue directly to the Docker chapter. Do not run later dependent stages until 03-ready.sh confirms both operations. Resume state and non-secret outputs live under workshop/.state/. A different terminal still uses the same subscription and group through common.sh.

Verification: expect the final line to say that AKS/Functions and PostgreSQL are provisioning. This is example/expected behavior. Stage 03 will poll actual deployment states, report failed ARM operations and enforce a 40-minute deadline for each operation.

Common failures

  • A name is already soft-deleted: inspect the matching Key Vault/App Configuration name. Recover your own workshop resource deliberately, or use a new prefix in a new state folder. Do not purge or adopt someone else's resource.
  • Resource policy or region denies an SKU: read the failed ARM operation. Choose a compatible region/SKU in the bootstrap configuration before a new deployment, or have the owner adjust policy. A successful model probe does not grant compute quota.
  • A rerun finds an existing resource group: the script verifies its workshop-id tag. It refuses to modify a group with a different tag; never work around that by changing another group's tags.
  • Interrupted stage: rerun the same stage. Names, role-assignment IDs and secret reuse are deliberate. Check the deployment state before replacing configuration.
