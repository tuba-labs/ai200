Observed software checks

The canonical dated report is VALIDATION.md. Local tests use deterministic model fixtures, never pretend to be Azure inference, and exercise real PostgreSQL with pgvector for the integration risks.

Java compilation, Flyway migration/rerun, product commit ordering, persistent outbox, correlation, duplicate replies and timeout persistence have been checked against real PostgreSQL. Python core tests cover chunking, duplicate indexing, vector dimensions, failure/retry persistence, filtered retrieval, result caching and binding metadata. Direct Python dependency resolution and Bicep compilation have also been performed.

Observed: four Java integration tests, 26 workshop pytest cases, all 58 existing Python tests and 91 existing JavaScript tests pass. Both Linux container images build; the Products inspect container's actual HTTP health is UP. Real browser checks, shell lint, strict standard Kubernetes schemas and official KEDA CRD structures pass. The canonical report describes the fixture boundaries and commands.

What still needs Azure

Interface/setup follow-up: 14 relevant checks pass after adopting the default header and shared jargon tooltips: five browser, six documentation/export and three local-preflight boundary cases. The 58 existing Python and 91 JavaScript checks were rerun successfully. Windows setup parsing and a real -WhatIf preview, Ubuntu Bash syntax and ShellCheck pass. A clean OS installation using the new installers has not been run; no local software was installed or changed for this verification.

Azure testing is deliberately left for the user's walkthrough. No providers were registered or paid resources created. Read-only checks found Compute, AKS and model providers unregistered and regional quota queries empty; empty results do not prove a lack of quota. Use the supplied registration/check stage in the intended subscription first.

Actual cloud model probes, ARM/server-side validation, a clean deployment, Function host/Event Grid delivery, private-network access, workload/KEDA identity propagation, public HTTPS access, the real smoke test, observed scaling and cloud cleanup require the maintainer acceptance path in a suitable authorized subscription.

How to interpret the tutorial

Chapter outputs are expected behavior unless explicitly recorded as observed in the dated report. The core path is estimated at about four hours after tools/access are ready. It has not been timed with a participant. Fix and record first-run failures rather than converting expectations into a claim of success.
