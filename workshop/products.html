Self-paced / Chapter 04 of 10

Read, build and run Products

Understand the supplied Spring Boot application and turn its source into a versioned container image.

~35 minutes · estimateBash · repository rootCore path

You will learn: image versus container, a Dockerfile's build stages, version tags, and the important Java application boundaries.

Starting requirements: stage 02 has created ACR and begun the slow deployments. Docker can run Linux containers. You receive complete working source; do not rewrite the applications.

Shell and directory: Bash, repository root. The script selects each correct Docker build context.

Read the supplied application first

Open apps/products/src/main/java/org/tubalabs/products/ProductsController.java. The upload endpoint validates the name and UTF-8 .txt file, creates a product with a random product ID and manual ID, then uploads to manuals/products/<productId>/<manualId>.txt. It includes both IDs and a checksum in blob metadata. The IDs are stable for that upload; a different product receives new ones.

Open apps/products/src/main/java/org/tubalabs/products/Store.java. Notice the explicit SQL, JdbcClient, and the small transaction that writes a question and its outbox message together. The scheduled apps/products/src/main/java/org/tubalabs/products/MessagePump.java sends committed outbox entries and consumes replies. These are separate operations because PostgreSQL and Service Bus do not share one atomic transaction.

Thymeleaf templates live under src/main/resources/templates. They render the upload and chat forms on the server. The browser's apps/products/src/main/resources/static/app.js sends requests, polls persistent states and renders text safely using textContent. It does not call Azure models or hold Azure credentials.

Understand the two-stage Dockerfile

apps/products/Dockerfile
FROM maven:3.9.11-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src src
RUN mvn -B package -DskipTests

FROM eclipse-temurin:21.0.9_10-jre-jammy
RUN groupadd --gid 10001 app && useradd --uid 10001 --gid app --no-create-home app
WORKDIR /app
COPY --from=build /src/target/products.jar app.jar
USER 10001:10001
EXPOSE 8080 8443
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=65", "-jar", "/app/app.jar"]

Source: apps/products/Dockerfile

The first FROM supplies Maven and Java 21. WORKDIR selects the container's build directory. Copying pom.xml before the source lets Docker cache dependency downloads. Maven creates target/products.jar. The second stage copies only the JAR into a JRE image and runs as an unprivileged user.

An image is the packaged, versioned filesystem and startup configuration. A container is a running instance of an image. EXPOSE documents ports; it does not publish them. -p on docker run publishes a port. AKS later runs the same image as a container inside a Pod.

Build, tag and push both images

Bash · repository root
bash workshop/scripts/05-images.sh

Canonical commands: commands.sh

The stage performs docker build for Products and ProductsChat, authenticates Docker to ACR with your Azure sign-in, then performs docker push. The tag looks like w1-… and is derived from the build inputs, not latest. The registry name comes from the shared configuration. You do not replace hostnames throughout the tutorial.

Read scripts/05-images.sh: -t registry/name:tag assigns the full image reference during the build. Giving an existing image another name uses docker tag; it does not rebuild or copy its layers. A tag can move; a digest identifies content. Do not overwrite workshop tags after publishing them.

Products' context is its own directory. The worker context is the repository root so it can include the small shared Python package; the root .dockerignore excludes everything except its required inputs. No .state, secret files, local virtual environments or build credentials enter either image.

Run a container without Azure connections

Bash · repository root
tag=$(python3 -c 'import json; print(json.load(open("workshop/.state/images.json"))["tag"])')
registry=$(python3 -c 'import json; print(json.load(open("workshop/.state/config.json"))["stem"]+"acr.azurecr.io")')
docker run --rm --name products-inspect -p 127.0.0.1:8080:8080 \
  "$registry/products:$tag" --spring.profiles.active=inspect

Canonical commands: commands.sh

In another Bash terminal, run curl --fail http://127.0.0.1:8080/ and curl --fail http://127.0.0.1:8080/actuator/health/liveness. The first response explicitly says Inspect profile. This profile exposes startup information and health only; upload/chat and Azure connections are disabled. It is a Docker exercise, not a simulated Azure deployment.

Use docker ps to see the running container and docker logs products-inspect to inspect Java startup. Stop it with Ctrl+C; --rm removes this disposable container. The cloud deployment uses the azure profile and requires real dependencies.

Optional: practice a separate docker tag command or compile with Wrapper

Use the same tag and registry variables from the run block, then run docker tag "$registry/products:$tag" products-local:$tag. Inspect it with docker image inspect "products-local:$tag". The image ID matches. For a local Java build, change to workshop/apps/products and run bash mvnw test with Java 21. Database integration tests require the disposable PostgreSQL fixture described on the maintainer page.

Expected behavior and common fixes

Verification: both pushes finish with a registry digest, the inspect container responds on localhost, and its health response is {"status":"UP"}. These are expected outputs; see the validation report for checks actually run by the maintainer.
  • ACR push returns denied: rerun az acr login through the stage and confirm your subscription has registry push rights. Registry administrator credentials are intentionally disabled.
  • Port 8080 is occupied: use 127.0.0.1:8081:8080 for this local run and curl port 8081. The AKS manifest still uses its own port 8443.
  • Build download fails: check Docker's internet/proxy access and rerun. Layers cache completed work; do not change library versions just to mask a transient repository failure.
  • Exec format error: rebuild with the supplied --platform linux/amd64 flag and confirm Docker supports that platform.

Continue when: the images are in ACR and the local inspect run works. Now wait for Azure readiness and connect the real services.

A reading checklist, not proof of a successful Azure deployment.
