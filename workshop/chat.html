Self-paced / Chapter 08 of 10

Ask a grounded question

Follow a persistent question through Service Bus, vector retrieval, the model and a correlated reply.

~35 minutes · estimateBash · repository rootCore path

You will learn: persistent asynchronous request/reply, correlation, vector retrieval, grounding and safe retries.

Starting requirements: Products works; the supplied manuals are ready; request/reply queues and all identity assignments exist.

Shell and directory: Bash, repository root. Use workshop/.state/kubeconfig for manual Kubernetes commands.

Start one worker first

Bash · repository root
bash workshop/scripts/08-chat.sh

Canonical commands: commands.sh

The stage applies k8s/chat.yaml, temporarily starts one worker and waits for readiness. It verifies App Configuration, Key Vault and database startup before KEDA takes over in the next chapter. Products still runs separately with one replica.

Read apps/products-chat/worker.py. A context manager opens a Service Bus receiver and sender. Each pod handles one request at a time with prefetch zero. It validates the JSON body against its expected fields and checks message ID/correlation headers against the persistent identifiers. No model key is present; model and Azure service calls use identity tokens.

Follow the persistent protocol

StepPersisted behavior
SubmitProducts stores question, optional product, request ID, correlation ID, an eight-minute deadline and an outbox entry in one PostgreSQL transaction. The browser receives HTTP 202.
DispatchThe sender publishes the outbox body to chat-requests, with message ID=request ID and matching correlation ID. It marks the outbox sent only after sending.
ProcessThe worker changes queued → processing, embeds the question, retrieves evidence and generates an answer. It caches the reply in PostgreSQL before publishing.
ReplyThe worker sends to chat-replies. Products checks the correlation and commits the terminal answer/sources before acknowledging the reply.
PollThe browser polls Products by request ID. Refreshing the chat URL resumes polling that database record; no open HTTP request has to survive.

The exact message contracts are contracts/chat-request.schema.json and contracts/chat-reply.schema.json. Request and correlation IDs are both persisted UUIDs. The worker compares the message with the stored question/product so a body/header mismatch is rejected, not silently associated with another request.

Read the small RAG implementation

apps/shared/rag_core/chat.py contains the direct SQL query: join ready products to chunks, optionally filter the product ID, compute cosine similarity using 1 - (embedding <=> question_vector), filter by minimum similarity, order by distance and take the configured count. There is no orchestration framework and no approximate vector index.

The model helper sends a short application instruction and inspectable JSON containing the question and retrieved reference data. It asks for numbered citations and an explicit insufficient-information response when the sources cannot support an answer. The application exposes the actual retrieved passages. If retrieval has no useful evidence, it returns the insufficient-information answer without a chat call. If the generated answer has no valid cited reference, the application also falls back to that answer.

Untrusted manuals: text in a manual or question is not allowed to override application instructions, reveal secrets or call tools. The worker does not offer tools or access to additional documents to the model. Prompt separation and evidence checks reduce risks; they are not a guarantee that a model can never make an incorrect claim.

Ask questions you can check

  1. In Products → Chat, select Aurora Trail Lamp and ask: “What is the operating temperature of the Aurora Trail Lamp?” The supporting passage should include “−10 to 40 degrees Celsius” (the supplied plain text uses -10).
  2. Select Cedar Desk Fan and ask how to enable its timer. Check for the two-second hold and 45-minute duration in the returned source, not just in the generated sentence.
  3. Select Harbor Travel Kettle and ask whether it works on a 110 V supply. The manual explicitly says 220–240 V only and not dual voltage.
  4. Ask: “What is the CEO's private telephone number?” The manuals provide no evidence. Expect an explicit insufficient-information answer, not an invented number.

samples/questions.json records the questions and expected supporting passages. LLM wording is nondeterministic; verification checks evidence and source IDs rather than a fixed answer string. If you uploaded Aurora revision B, select each revision separately and ask about lumens: the product filter should prevent cross-product mixing.

Change an ordinary setting

Bash · repository root
bash workshop/scripts/change-retrieval.sh 1

Canonical commands: commands.sh

This changes rag:retrieval-count from 3 to 1 in App Configuration and restarts the worker deployment. Refresh is not implemented. Settings and secrets are read once at process startup in both Python applications and Products. For the Function, a changed chunk setting requires a Function app restart; for Products, a changed bootstrap/secret requires its rollout restart. A stored result remains cached and is not regenerated.

Ask a new question after restart and verify that the worker startup log says retrieval_count=1 and at most one cited passage appears. Restore 3 by running bash workshop/scripts/change-retrieval.sh 3. At zero replicas later, the changed pod template takes effect when KEDA starts a new worker.

Know what acknowledgement means

A receive operation locks a Service Bus message temporarily; it does not remove it. Complete acknowledges successful processing. Abandon makes it available for retry. A lost lock or expired receiver can also cause redelivery. The queue starts with a one-minute lock, while automatic lock renewal in the worker allows up to ten minutes for slow model calls. Requests still have their own eight-minute application deadline.

Repeated processing failures produce a safe failed reply and a dead-lettered request. The broker also dead-letters messages after its configured maximum deliveries or TTL. Products persists timeouts independently, so a lost reply does not leave an endless spinner. Inspect the request ID in logs and the dead-letter subqueue; increasing delivery count alone does not fix bad credentials or model quota.

There is an intentional at-least-once window between sending and marking an outbox entry, and between replying and acknowledging a request. A per-request advisory lock and persistent result cache avoid repeated displayed answers and normally avoid repeat LLM calls after a cached result. A crash before caching can repeat a model call. Terminal reply updates are guarded by request/correlation/deadline. This is not exactly-once delivery.

Verification: see queued/processing/completed states, a non-empty answer and relevant passages. Refresh the request URL: it should show the same persisted answer. Confirm the unsupported question is refused.

Common failures

  • Queued forever: inspect Products' outbox warnings, request queue counts and worker readiness. Check queue-scoped Sender/Receiver roles and the correct namespace.
  • Processing then failed: inspect worker logs by request ID; check model 429 throttling, model deployment names, database access and lock renewal. The browser shows a persisted error or timeout.
  • Wrong product's passage: check the selected product ID and source IDs. An unfiltered question can legitimately retrieve multiple manuals; a filtered one must not.
  • Manual instructions appear to influence behavior: inspect the prompt and references. Do not add unsafe content or broaden tool access to make an unsupported answer work.

Continue when: grounded questions, unsupported questions and the retrieval-count change are observable. Next, let queue metrics control worker replicas.

A reading checklist, not proof of a successful Azure deployment.
