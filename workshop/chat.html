Chapter 08 of 10

Ask a grounded question

Retrieve evidence, generate a cited answer and inspect asynchronous replies.

~35 minBash · repository root

Requires: Products ready and the three manuals indexed.

Deploy one worker

Bash · repository root
bash workshop/scripts/08-chat.sh

Canonical commands: commands.sh

Starts one worker from chat.yaml. worker.py receives Service Bus requests serially, with prefetch zero. KEDA takes over next.

Ask and inspect the evidence

In Products → Chat, select the matching product. Compare returned passages, not exact LLM wording.

Product / questionExpected evidence
Aurora: operating temperature?-10 to 40 degrees Celsius
Cedar: how to enable the timer?Hold two seconds; runs for 45 minutes
Harbor: does it work on 110 V?220–240 V only; not dual voltage
Any: what is the CEO's private telephone number?Insufficient information

For Aurora revision B, compare lumens using each product filter. Questions and supporting passages: questions.json.

How retrieval and prompting work

chat.py embeds the question, filters ready chunks by optional product ID, ranks cosine distance with <=>, and supplies the best passages to the chat model. No useful evidence means an insufficient-information answer.

Manuals are untrusted reference data, separated from application instructions. The model receives context, not secrets or tools; citations let you inspect support.

Change retrieval count

Bash · repository root
bash workshop/scripts/change-retrieval.sh 1

Canonical commands: commands.sh

Changes App Configuration from 3 passages to 1 and restarts the worker. No live refresh. Ask a new question: startup logs should show retrieval_count=1, with at most one source. Existing answers remain cached. Restore with bash workshop/scripts/change-retrieval.sh 3.

Verification: observe queued/processing/completed states, cited answers and an unsupported-question refusal. Refreshing the request URL returns the same persisted answer.
Request/reply and retry guarantees

Products commits question + outbox, returns HTTP 202, and sends to chat-requests. The worker validates stored request/correlation IDs, caches the result before sending to chat-replies, then acknowledges. Products persists the correlated reply before acknowledging it; the browser polls by request ID.

A receive locks work; Complete acknowledges, Abandon retries. Initial lock: one minute; automatic renewal: up to ten minutes; application deadline: eight minutes. Persistent failure/timeouts end browser polling. Repeated failures reach the dead-letter queue.

Advisory locks, cached results and guarded updates prevent duplicate displayed answers. A crash before caching can repeat a paid model call; delivery is not exactly-once. Contracts: chat-request.schema.json, chat-reply.schema.json.

Troubleshooting
  • Queued: check Products' outbox logs, queue counts, worker readiness and Sender/Receiver roles.
  • Failed/timeout: inspect worker logs by request ID; check model quota/429s, deployments, DB access and lock renewal.
  • Wrong product: compare selected product and returned source IDs. Only unfiltered questions may mix manuals.
