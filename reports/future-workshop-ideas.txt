TWO FUTURE AI-200 WORKSHOP PROJECTS — PROPOSAL, 29 OCTOBER 2026

RECOMMENDATION
Build one understandable system in two connected workshop projects: a repair desk and its searchable solution library. Residents report a broken streetlight or leaking pipe; staff track the job and find a useful previous fix. Each new component must improve that user flow.
These are two substantial workshop tracks with several checkpoints, not two short sessions. The main path uses Container Apps. App Service and AKS reuse the same images as optional hosting branches. Covering AKS practically requires doing that branch; a comparison paragraph does not teach manifest deployment and troubleshooting.
Use Python and supplied/precomputed embeddings. The learners do not need a model account, prompt-engineering framework, model training or a separate generative-AI service to practice the measured data skills.

WHAT THIS FILE CLAIMS
All 559 current cards are assigned once: 171 implementation candidates, 84 controlled experiments, 137 design/reference checks and 167 vocabulary introductions.
Implementation plus experiments: 255 cards (45.6% of the whole deck; 65.1% of subject cards). Of these, 207 fit the main path and 48 need an explicitly optional branch.
These numbers count proposed learning opportunities, not completed coverage. Vocabulary and a discussion are not substitutes for demonstrating a skill. The card-by-card appendix identifies the distinction.
The mapping is a dated planning snapshot. It does not alter the current site’s workshop tags or claim that any new workshop exists.

THE APP AND ITS DATA
Cosmos DB owns repair jobs and their changing status. PostgreSQL owns curated repair articles and embeddings. Redis caches derived results and can be cleared without deleting authoritative data. Blob Storage owns uploaded photos. This gives each store a distinct job rather than keeping three synchronized authoritative copies.
Service Bus holds work that must be completed. Event Grid reports things that happened, such as a photo upload. The API returns quickly; a worker does slow work. Functions provide a small event adapter and the change-feed consumer.
Managed identities, Key Vault, App Configuration and tracing are shared foundations across both projects, not four unrelated security demos.

WORKSHOP 1: REPORT A PROBLEM AND TRACK THE REPAIR

Resident -> API -> Cosmos repair record
              -> Service Bus -> worker -> updated job status
Photo -> Blob Storage -> Event Grid -> Function -> existing work flow
All components -> OpenTelemetry/Application Insights -> KQL investigation

Observable end state: a resident submits a report with a photo, receives an ID, and sees processing status. A worker restart does not duplicate the business action. A broken permission or a bad image release can be located and recovered.

1.1 Build and publish the repair API
Outcome: The same versioned image can run locally and be pulled from a private registry.
Start with a tiny Python API and one worker from the same repository. Build an image locally or with an ACR quick task, inspect its tag and digest, then push/pull it. Add one source-triggered build after the manual path works. Use one simple build path first; multi-step tasks, timers, signatures, ABAC and private networking are short extensions or design checks.
Card candidates: 11 implement, 4 experiment, 12 design/reference, 25 vocabulary.

1.2 Release the API without breaking the report form
Outcome: A user submits a repair report through a working HTTPS endpoint; a bad release can be rolled back.
Use Container Apps as the main host. Compare single and multiple revision behavior, route a small traffic share to a test revision and move a stable label URL. Set the listening port and environment values explicitly. An App Service slot deployment is an alternative-host exercise using the same image, not another required production component. Deployment-labels mode is a preview reference or optional demo.
Card candidates: 12 implement, 4 experiment, 9 design/reference, 10 vocabulary.

1.3 Save a report and show its current status
Outcome: The form returns a report ID and the status page reads the right repair record.
Store repair jobs in Cosmos DB. Use Python SDK clients, a deliberate partition key and point reads. Compare one partition-targeted query with a cross-partition query, inspect RU charges and change an unnecessary index. A short consistency exercise explains what a user may read after an update. Discuss multi-region guarantees from a supplied scenario rather than deploying several regions solely for the exercise.
Card candidates: 6 implement, 9 experiment, 10 design/reference, 6 vocabulary.

1.4 Process repair work reliably in the background
Outcome: The API acknowledges quickly; workers complete jobs without applying the same repair twice.
Send work to Service Bus and return HTTP 202 plus a status location. Let worker replicas compete on one queue. Crash a worker before completion, observe redelivery and make the operation idempotent. Add a dead-letter recovery path, one topic with independent subscribers and one property filter. Scale the worker from the queue backlog with KEDA. Sessions, scheduled work, deferral, broker transactions, request/reply and an outbox are focused variants of this flow, not all mandatory features of the repair app.
Card candidates: 19 implement, 4 experiment, 18 design/reference, 13 vocabulary.

1.5 React when a resident uploads a photo
Outcome: A photo upload is associated with its report and produces a visible processing status.
A BlobCreated event reaches a Python Function through Event Grid. The handler accepts the event quickly and hands slow work to the existing worker. Add event-type/subject filtering, retry-safe processing and dead-letter storage. Inspect a failed delivery. Use a small Timer or Storage Queue function as a binding comparison only; do not introduce extra queues into the main flow just to demonstrate every trigger.
Card candidates: 23 implement, 8 experiment, 22 design/reference, 17 vocabulary.

1.6 Give each component only the settings and access it needs
Outcome: The API and worker read configuration securely; a deliberate permission error is diagnosable.
Use managed identities, narrow data-plane roles, Key Vault for a real demonstration credential and App Configuration for ordinary settings. Compare a fresh SDK read with a cached or version-pinned value. Rotate the demonstration credential in both the target and vault, then refresh its consumers. Load a key/label pair and refresh a watched setting. Use a feature flag to expose the new search page. Private endpoints and federation are optional infrastructure extensions, not prerequisites for the first successful request.
Card candidates: 26 implement, 14 experiment, 14 design/reference, 25 vocabulary.

1.7 Follow a slow or failed report through the system
Outcome: A learner can explain where a request failed using traces and a small set of log queries.
Instrument API and worker with OpenTelemetry, give them distinct service names and propagate trace context. Observe request and dependency spans, a log and a metric. Write KQL that filters failures, groups requests, calculates durations, joins related telemetry and plots time buckets. Break one permission or dependency and find it again. Sampling and ingestion-cap exercises use controlled test traffic and configuration comparisons rather than silently dropping evidence during the main debugging exercise.
Card candidates: 26 implement, 9 experiment, 11 design/reference, 16 vocabulary.

1.8 Optional hosting branch: run the same API and worker on AKS
Outcome: The existing images run behind Kubernetes Services and can be investigated with kubectl.
Reuse the API/worker; write Deployment and Service manifests, probes and requests/limits. Roll out and undo an image change, test a selector or target-port error, inspect previous logs and compare pod scaling with node capacity. Add workload identity and a mounted secret in a later step. Namespace permissions, quota/LimitRange, NetworkPolicy and shared volumes are optional variants. DaemonSets, GPU placement, CNI choices and every Service type are discussion or isolated examples unless a real requirement emerges. This branch is needed for practical AKS coverage; it is not needed to finish the main repair app.
Card candidates: 14 implement, 9 experiment, 8 design/reference, 26 vocabulary.

WORKSHOP 2: FIND A PREVIOUS FIX QUICKLY AND KEEP IT CURRENT

Staff search -> existing API -> Redis cache
                            -> PostgreSQL article/vector search on a miss
Solved repair -> Cosmos change feed -> derived suggestion/cache invalidation

Optional comparisons: Cosmos vector retrieval for solved cases; Redis semantic caching of prior suggestions. Use one small shared fixture with known relevant matches. Do not force all three vector engines into the essential request path.
Observable end state: a paraphrased problem finds a relevant article, a repeat request is faster, an update invalidates stale derived data, and the learner can explain a measured latency or recall change.

2.1 Create a searchable library of previous fixes
Outcome: Staff can retrieve a known repair article, filtered by a useful category such as electrical or plumbing.
Reuse the running API and authentication from workshop 1. Store curated knowledge articles and supplied embeddings in PostgreSQL. Load rows in bulk, parameterize reads and use an ordinary index for metadata. Use a bounded Python connection pool and secure database access. The source of truth is the article library; Cosmos DB remains the source of truth for live repair jobs.
Card candidates: 5 implement, 5 vocabulary.

2.2 Find similar problems and compare search quality
Outcome: “The street lamp is dark” can find an article titled “Outdoor light does not turn on.”
Use supplied embeddings so no model API is needed. Establish exact nearest-neighbor results, then compare HNSW and IVFFlat on the same question set. Explain cosine, L2 and dot product with tiny numeric examples. Apply metadata filters and compare recall/latency. An optional Cosmos vector branch searches solved repair records or the same copied test fixture to compare indexing policies; it is an alternative retrieval experiment, not a second compulsory copy of the article database.
Card candidates: 14 implement, 5 experiment, 7 design/reference, 13 vocabulary.

2.3 Serve repeated searches quickly without showing stale answers
Outcome: A repeated search becomes a cache hit, and an edited article does not remain wrong indefinitely.
Add Redis cache-aside for article/search results, explicit TTLs and invalidation after updates. Measure hit rate, misses and evictions; simulate a popular key expiring. Start with ordinary caching. An optional semantic-cache branch uses compatible Redis vector search and a clear similarity threshold to reuse stored suggestions for paraphrases. FLAT/HNSW and hash encodings belong to that branch; they are not required merely to cache an article by ID.
Card candidates: 8 implement, 10 experiment, 5 design/reference, 8 vocabulary.

2.4 Keep suggestions synchronized when repair records change
Outcome: A solved repair becomes searchable and its cached status is invalidated without the API publishing a second event for every write.
Consume Cosmos change feed with a Python Function or Python pull client. Maintain progress, tolerate repeated batches and update a derived search entry or invalidate a cached repair status. Run independent consumers for indexing and cache invalidation; use a separate named consumer/checkpoint group for each job. Do not model these as one shared worker group if each needs every change. Explain latest-version omissions and explicit deletion/tombstone handling. Native Change Feed Processor names/APIs are conceptual comparisons because the native processor libraries in the linked material are .NET/Java, not a Python client to implement in this lab.
Card candidates: 4 implement, 1 experiment, 7 design/reference, 1 vocabulary.

2.5 Measure and fix a slow search under realistic concurrency
Outcome: A learner can separate slow connection setup from slow SQL and demonstrate whether a chosen change helped.
Run repeatable searches with fixed data and concurrency. Record P95 latency, recall, pool waits, memory pressure and disk reads. Use EXPLAIN ANALYZE, tune one index search parameter and compare before/after. Test client pooling against repeated new connections; optionally compare built-in PgBouncer. Resource-tier changes are estimates or a controlled extension after finding a bottleneck. Exact SKU ratios, ports, dimension ceilings and defaults remain short reference checks rather than separate app features. Reuse workshop 1 tracing/KQL to explain the measurements.
Card candidates: 3 implement, 7 experiment, 14 design/reference, 2 vocabulary.

KEEP THE BUILD SMALL
Start from two container entry points (API and worker), one small Function project and seed data. Add search routes to the API rather than creating a microservice for each database. Keep jobs and articles as the two understandable business objects.
The first checkpoint in each project must work before adding reliability or performance variants. Provide independent starting snapshots at the main checkpoints so one earlier Azure configuration problem does not block the entire course.
The core flow should use one straightforward build path, one primary host, one queue and one primary vector store. Add the topic/subscription, alternative hosts and alternative vector engines as focused extensions after that path works.
Keep authorization and tracing in the code from the first deployed checkpoint, then deliberately break and diagnose them later. This makes the security and KQL work part of the app rather than a final slide deck.

AWKWARD FITS AND HONEST LIMITS
AKS and App Service are alternative deployment experiences. They cannot both be taught practically merely by mentioning them while running Container Apps.
Multi-region Cosmos consistency, geo-replicated/private ACR, private networking, GPU placement and dedicated workload sizing need design scenarios or optional environments. They are not required by a repair desk’s basic user flow.
The native Cosmos Change Feed Processor API is documented for .NET/Java. Use Python pull/Functions for implementation and teach processor/group versus instance names as the language-neutral coordination model.
Exact retry schedules, status-code sets, ports, minimum staleness values, retention windows, index limits and distro defaults are small reference checks when they affect a decision. Do not add infrastructure solely to make learners memorize a number.
Preview capabilities and uncommon trigger/binding combinations should be labeled optional. A working Timer demo does not prove understanding of every Functions plan, timeout and scaling variant.
OpenTelemetry sampler APIs and environment settings can be compared with a tiny instrumented test. A learner still needs to explain the difference between instrumentation, sampling, propagation, export and query scope.
Some cards are implementation prerequisites rather than explicitly named exam tasks. Introducing their vocabulary in context supports the workshop but does not establish exam completeness.
If the requirement is two brief workshops, reduce the practical claim. Two coherent projects can organize the whole deck, but all 559 cards cannot honestly become distinct core hands-on tasks in that time.

HOW TO JUDGE A FUTURE WORKSHOP
For implementation candidates, require an observable result: the API reads data, a message is settled, a secret resolves or the query returns the expected rows.
For experiments, require before/after evidence: a failed delivery recovers, an old cache value disappears, a new index changes the plan or a resource change improves a repeatable measurement.
For design/reference checks, require a short explanation of the relevant trade-off or failure mode. Record this separately from practical completion.
For vocabulary, show the concrete object first, then ask the learner to identify and explain it. Knowing an acronym is useful but does not prove the operational skill.
