Én økt eller to samlinger

Én samlet økt omfatter hele domenet. Delingen i to samlinger er tematisk. Gjennomføringstiden er ikke målt; den avhenger av forkunnskaper, egne forsøk, diskusjon og klargjøring.

Vis øvelser for

Fremdrift deles mellom formatene på samme nettsted i denne nettleseren. Ved lokal bruk åpner du nettstedet via en lokal HTTP-server. Bytte av format gir samme oppgavedekning. Velg korte økter i stedet →

Samling 1: Functions Core Tools, en publiserbar HTTP Function App og et Standard Service Bus-namespace med kø, topic og subscriptions.

Oversikt for hele domenet

Ha Functions Core Tools, en Python Function App, en lab-Storage-konto og et Standard Service Bus-namespace klart. Standard trengs til topics. Event Grid bruker event-hook i Function App-en fra del 14.

Start fra prosjektroten, der index.html og labs ligger, og lagre rotstien i hovedterminalen. Alle Python-deler bruker samme .venv. Nye terminaler åpnes i prosjektroten og aktiveres ved behov.

$projectRoot = (Get-Location).Path
.\.venv\Scripts\Activate.ps1

Følg i tillegg forberedelsene i hver del. Installer pakkene som den aktuelle delen trenger. Ikke del nøkler eller innlogging når dere arbeider sammen.

Behold ressursene til de er ferdig brukt

Del 14

Bygg og publiser en HTTP Function

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Python 3.12, prosjektets .venv og Functions Core Tools v4 må være klare. Ha en Python 3.12 Function App på Linux med tilhørende Storage-konto klargjort i en egen labgruppe. Bruk en støttet hostingplan. Vi arbeider i labs/integrations.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/integrations/requirements.txt
Copy-Item labs/integrations/local.settings.example.json labs/integrations/local.settings.json
Set-Location labs/integrations
func start

1. Test en HTTP-trigger

La host-en kjøre. Send fra en ny PowerShell-terminal:

$body = @{ id = "doc-001"; text = "Workshop" } | ConvertTo-Json
Invoke-RestMethod http://localhost:7071/api/documents -Method Post -ContentType application/json -Body $body

Forventet: processed=true første gang og false ved samme ID. Finn route, trigger og HTTP-respons i function_app.py.

2. Undersøk feil og restart

Invoke-RestMethod http://localhost:7071/api/documents -Method Post -ContentType application/json -Body '{}'

Forventet HTTP 400. Restart host-en og send doc-001 igjen: minnesettet er tømt. Forklar hvorfor HTTP-triggeren ikke gjentar klientens kall, og hvorfor varig idempotens trenger mer enn prosessminne.

3. Publiser og konfigurer

Stopp host-en. Fra labs/integrations, med miljøet aktivt:

az login
az account show --query "{name:name,id:id}" -o table
func azure functionapp publish "DITT-FUNCTION-APP-NAVN"

Finn Get Function URL for documents i portalen og send samme body til den komplette URL-en med nøkkel. Undersøk Function-logger og appinnstillingen FUNCTIONS_WORKER_RUNTIME. Behold appnavnet til workshop 18–19; de bruker event-hook og configuration-endepunktene fra samme kode.

Rydding og overgang til neste del

Stopp lokal host, men behold den publiserte HTTP Function App-en til Event Grid i del 18. Den kan også brukes i domene 4.

Del 15

Behandle kømeldinger og DLQ i kode

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Opprett et eget Service Bus-namespace og køen documents. Basic holder her; velg Standard dersom samme namespace skal brukes til topics i neste økt. Gi din innloggede bruker Azure Service Bus Data Owner på labnamespace-et. Aktiver .venv, installer labs/integrations/requirements.txt og kjør az login.

$env:SERVICEBUS_NAMESPACE = "DITT-NAMESPACE.servicebus.windows.net"

1. Send fra Python

python labs/integrations/message_bus.py send

Åpne Service Bus Explorer og bruk Peek for å se meldingen uten å fjerne den. Finn body, subject, message ID og application properties. Les senderen i message_bus.py.

2. Lås, frigjør og lever igjen

I Explorer: Receive med PeekLock, velg Abandon, og motta på nytt. Sammenlign DeliveryCount. Forklar forskjellen mellom Peek, ReceiveAndDelete, Complete og Abandon. Ikke bruk andre køer enn labkøen.

3. Håndter DLQ i kode

python labs/integrations/message_bus.py receive
python labs/integrations/message_bus.py dlq

Receive-steget flytter mottatte meldinger til DLQ med en kontrollert feilårsak. DLQ-steget leser, skriver dem ut og fullfører dem. Inspiser reason i portalen mellom kjøringene. Diskuter hvilke feil som kan prøves på nytt og hvilke som trenger rettet innhold.

Rydding og overgang til neste del

Kontroller at labmeldingene er håndtert. Behold Service Bus-namespace og documents-kø til del 16–17.

Del 16

Service Bus: topics og subscriptions

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Bruk et Standard-namespace med samme SDK-oppsett og SERVICEBUS_NAMESPACE som i workshop 15. Opprett topic document-events og subscriptions indexer og audit. Begge starter med standardregelen som tar imot alt.

1. Test uavhengige kopier

python labs/integrations/message_bus.py topic
python labs/integrations/message_bus.py subscription --subscription indexer
python labs/integrations/message_bus.py subscription --subscription audit

Forventet: begge mottar én kopi. Fullføring i indexer fjerner ikke audit sin kopi. Finn skillelinjen mellom topic og subscription; det er subscription som fungerer som mottakerens kø.

2. Legg på et filter

På indexer i portalen: erstatt standardregelen med en SQL-filterregel kind = 'note'. Fjern standardregelen som matcher alt, ellers gjelder reglene som OR. Audit beholder standardregelen. Send en ny melding og motta fra begge.

3. Vis at filteret virker

I en lokal kopi av message_bus.py: endre application property kind fra note til other, og send på nytt. Forventet: audit mottar meldingen, indexer gjør det ikke. Sett koden tilbake. Forklar hvorfor filteret ser på metadata og ikke parser JSON-body.

Rydding og overgang til neste del

Fullfør labmeldingene og slett topic/subscriptions når testen er ferdig. Behold documents-kø og namespace til bindingene i neste del.

Del 17

Functions: triggere og output-binding

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Bruk en dedikert documents-kø med Max delivery count=3. I innstillingseksemplet trenger du en lab-Storage-connection-string og en Service Bus-policy med Send og Listen. Dette er lokale innstillinger; de skal ikke committes.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/bindings/requirements.txt
Copy-Item labs/bindings/local.settings.example.json labs/bindings/local.settings.json

Erstatt plassholderne, gå til labs/bindings og kjør func start --port 7073.

1. Følg en melding gjennom bindingene

Invoke-RestMethod http://localhost:7073/api/enqueue -Method Post -ContentType application/json -Body '{"id":"doc-001"}'

Forventet: HTTP 202 og deretter en Consumed-logglinje. Finn service_bus_queue_output og service_bus_queue_trigger. Output-bindingen sender meldingen; triggeren starter mottakeren og fullfører vellykket behandling.

2. La behandlingen feile

Invoke-RestMethod http://localhost:7073/api/enqueue -Method Post -ContentType application/json -Body '{"id":"fail-demo"}'

Koden fremprovoserer en feil når body inneholder fail. Observer gjentatte forsøk og økende delivery count. Etter køens maksimale leveringer ligger meldingen i DLQ. Inspiser feil og innhold i Explorer.

3. Skill ansvarsområdene

Forklar forskjellen mellom klientens HTTP-retry, bindingens sendeoperasjon og brokerens nye levering. Beskriv hvor en varig idempotensnøkkel må registreres dersom behandlingen oppdaterer en database. Sammenlign denne løsningen med den direkte SDK-mottakeren fra workshop 15.

Rydding og overgang til neste del

Stopp bindingenes Functions-host, håndter DLQ-meldingen og slett local.settings.json. Service Bus kan slettes nå. Behold HTTP Function App-en til Event Grid.

Del 18

Event Grid: filtre, egne hendelser og retries

Åpne som kort workshop →

Start denne delen i prosjektroten i terminalen du klargjorde over:

Set-Location $projectRoot

Før du starter

Bruk den publiserte Function App-en fra workshop 14. Opprett et Event Grid custom topic i labgruppen. Finn topic endpoint og en labnøkkel. Koden har et anonymt event-hook-endepunkt som bare logger testhendelser og kan returnere en kontrollert feil.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/integrations/requirements.txt
$env:EVENTGRID_ENDPOINT = "DITT-TOPIC-ENDPOINT"
$env:EVENTGRID_KEY = "DIN-LAB-NOKKEL"

1. Lag et filtrert abonnement

På topic-et: opprett Event Subscription med Event Grid Schema og Web Hook https://DIN-APP.azurewebsites.net/api/event-hook. Koden svarer på valideringshendelsen. Filtrer event type AI200.DocumentCreated, subject begins with documents/ og ends with .txt. Sett retry-policy til for eksempel 10 forsøk og 30 minutter TTL.

2. Publiser egne hendelser

python labs/integrations/publish_event.py

Forventet: bare note.txt kommer til webhooken. Finn event-id og subject i Function-loggene. Skriptet sender både en .txt- og en .csv-hendelse; kontroller at avvisningen skyldes filteret. Sammenlign en egen hendelse med BlobCreated fra en Azure-kilde.

3. Test levering etter feil

Sett app setting FAIL_EVENTS=true på Function App-en og vent på restart. Publiser igjen. Finn HTTP 503 og leveringsfeil i Event Grid-metrikkene. Sett FAIL_EVENTS=false, og vent på retry. Noter event-id ved vellykket levering. Retry har backoff og skjer ikke øyeblikkelig; behold abonnementet gjennom den konfigurerte perioden. Forklar hvorfor mottakeren må tåle duplikater og hva som skjer ved utløpt TTL.

Rydding og overgang til neste del

Slett Event Grid-abonnement og topic, fjern FAIL_EVENTS og EVENTGRID_KEY. Behold Function App-en bare hvis Key Vault-øvelsen i domene 4 skal bruke den.
