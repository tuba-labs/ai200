Én økt eller to samlinger

Én samlet økt omfatter hele domenet. Delingen i to samlinger er tematisk. Gjennomføringstiden er ikke målt; den avhenger av forkunnskaper, egne forsøk, diskusjon og klargjøring.

Del 7

PostgreSQL: vektorsøk og indekser

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Før du starter

Docker må kjøre. Bruk setup.sql som ferdig datasett. Vektorene er små undervisningstall; øvelsen undersøker lagring, avstand og gjenfinning.

1. Start database og schema

docker run --detach --name ai200-pg --env POSTGRES_PASSWORD=local-workshop-only --env POSTGRES_DB=workshop pgvector/pgvector:pg17
docker exec ai200-pg pg_isready -U postgres -d workshop
Get-Content labs/data/setup.sql -Raw | docker exec -i ai200-pg psql -U postgres -d workshop
docker exec -it ai200-pg psql -U postgres -d workshop

Vent på accepting connections før setup. Tabellen har id, topic, textinnhold og vector(3). Forklar valg av primærnøkkel og dimensjoner.

2. Søk og filtrer

SELECT id, topic, content, embedding <=> '[0,1,0]'::vector AS distance
FROM workshop_notes
WHERE topic = 'containers'
ORDER BY embedding <=> '[0,1,0]'::vector
LIMIT 2;

Forventet: dokument 2 før 1. Uten filter er dokument 3 nærmest. Forklar hvordan et metadatafilter avgrenser RAG-konteksten før en språkmodell eventuelt bruker treffene.

3. Les planen og bygg indeks

CREATE INDEX IF NOT EXISTS notes_embedding_hnsw
ON workshop_notes USING hnsw (embedding vector_cosine_ops);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM workshop_notes
ORDER BY embedding <=> '[0,1,0]'::vector LIMIT 2;

Fire rader er ofte for lite til at indeksen lønner seg; Seq Scan er normalt. Sammenlign operator og operator class. Beskriv avveiningen mellom recall, minne og svartid for en større vektorindeks.

Rydding og overgang til neste del

Avslutt psql og slett den lokale ai200-pg-containeren med volumene når du har tatt vare på egne SQL-notater. Neste del bruker Azure PostgreSQL.

docker stop ai200-pg
docker rm --volumes ai200-pg
Del 8

PostgreSQL i Azure: SDK og forbindelser

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Klargjør før økten

Ha en liten Azure Database for PostgreSQL Flexible Server klar i en labgruppe, med TLS og nettverkstilgang fra din maskin. Opprett databasen workshop. Tillat utvidelsen vector i serverparameteren azure.extensions. Bruk en databasebruker med rett til å opprette labtabellen.

1. Koble til med Python

Start i prosjektroten. Hent tilkoblingsinformasjonen fra Connect i portalen. PGCONNINFO er en lokal miljøvariabel; behold sslmode=require og legg ikke passordet i filene.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/data/requirements.txt
$env:PGCONNINFO = "host=DIN-SERVER.postgres.database.azure.com port=5432 dbname=workshop user=DIN-BRUKER password=DITT-PASSORD sslmode=require"
python labs/data/postgres_client.py setup
python labs/data/postgres_client.py query

Forventet: dokument 2 og 1. Finn de parameteriserte verdiene i postgres_client.py og forklar hvorfor SQL og data sendes separat.

2. Mål og gjenbruk forbindelser

python labs/data/postgres_client.py compare

Skriptet sammenligner ti nye forbindelser med ti spørringer via en liten klientpool. Gjenta og noter variasjonen. Tilkoblingslatens, nettverk og oppvarming påvirker resultatene. Undersøk min_size/max_size og hvorfor hver prosess trenger sin egen pool.

3. Undersøk Azure-flaskehalser

  1. Åpne Metrics for CPU, minne, aktive forbindelser og lagrings-I/O. Kjør compare igjen og noter hva en så liten last faktisk kan vise.
  2. Undersøk Compute + storage og PgBouncer. Velg et foreslått alternativ for mange samtidige oppslag og begrunn CPU/minne/lagring. Gjennomfør en endring bare på din labserver hvis øvelsen trenger den.
  3. På en tier med innebygd PgBouncer: aktiver den, bruk port 6432 i PGCONNINFO og kjør query/compare på nytt. Hvis tier-en ikke støtter det, bruker du klientpoolen og forklarer skillet.

Kombiner målingene med EXPLAIN-planen fra workshop 7. En liten datasamling er ikke en representativ kapasitetsmåling.

Rydding og overgang til neste del

Fjern PGCONNINFO fra terminalen. Slett den dedikerte PostgreSQL-serveren; de øvrige delene bruker andre tjenester.

Remove-Item Env:PGCONNINFO -ErrorAction SilentlyContinue
Del 9

Cosmos DB: SDK, indekser og RU

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Før du starter

Opprett en Cosmos DB for NoSQL-labkonto og databasen workshop uten delt throughput. Skriptet oppretter hver labcontainer med 400 RU/s. Vektorsøket i neste økt støtter ikke shared throughput. Bruk en egen labkonto. Ha endpoint og en lokal labnøkkel klar. Kontoen brukes også i workshop 10–11.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/cosmos/requirements.txt
$env:COSMOS_ENDPOINT = "https://DIN-KONTO.documents.azure.com:443/"
$env:COSMOS_KEY = "DIN-LAB-NOKKEL"
$env:COSMOS_DATABASE = "workshop"

1. Opprett og hent dokumenter

python labs/cosmos/demo.py setup
python labs/cosmos/demo.py query
python labs/cosmos/demo.py point

demo.py bruker /topic som partisjonsnøkkel og skriver request charge. Sammenlign spørringen med point read. Forventet: note-1 og note-2 fra query, note-1 fra point. Noter RU; tallene varierer.

2. Endre en indekseringspolicy

Undersøk policyen for notes: embedding-feltet er utelatt fra vanlig indeksering. Kjør SQL i Data Explorer med query metrics på. På den lille labcontaineren: ekskluder /text/? fra policyen og vent på fullført transformasjon. Kjør en spørring på topic og sammenlign med søk på text. Rett policyen tilbake etterpå.

Målet er å se hvilke felter som støttes effektivt av en indeks. Tre dokumenter gir ikke grunnlag for store ytelseskonklusjoner.

3. Velg consistency bevisst

Undersøk kontoens consistency og klientens session-håndtering. Sammenlign Session, Eventual og Strong i portalen og den offisielle beskrivelsen. Noter hvilke konsistenskrav en chat-historikk og en statistikkvisning kan ha. Hvis du endrer labkontoens standard, kjør oppslagene igjen og noter RU. Et vellykket enkeltoppslag demonstrerer ikke alle garantiene.

Rydding og overgang til neste del

Behold Cosmos-kontoen, databasen og notes til del 10–11. Ved to samlinger må disse være tilgjengelige ved starten av samling 2, eller opprettes på nytt med setup-steget.

Del 10

Vektorsøk i Cosmos DB

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Før du starter

Bruk kontoen og Python-miljøet fra workshop 9. Sett COSMOS_ENDPOINT, COSMOS_KEY og COSMOS_DATABASE igjen i denne terminalen. Aktiver vector search under kontoens Features og vent på at funksjonen er klar. Vi oppretter en ny container fordi vektorpolicyen fastsettes ved opprettelsen.

Databasen skal ha separat throughput per container, og vektorfunksjonen kan bruke omtrent 15 minutter på å aktiveres. Klargjør dette før økten.

1. Opprett policy og indeks

python labs/cosmos/demo.py vector-setup

Les vector-setup i demo.py: vectorEmbeddingPolicy angir sti, tre dimensjoner, float32 og cosinus. vectorIndexes velger flat-indeks. Den vanlige array-indeksen er ekskludert. Finn policyene i portalen og forklar hvorfor en dedikert vektorindeks trengs.

2. Utfør filtrert vektorsøk

python labs/cosmos/demo.py vector

Forventet: note-2 før note-1 innen topic=containers. Fjern metadatafilteret i en lokal kopi av spørringen og kjør igjen med cross-partition query aktivert; note-3 blir nærmest. Pass både SQL-filter og partition_key til det nye søkeområdet. Endre søkevektoren og forklar rangeringen.

3. Velg indeks for arbeidsmengden

Sammenlign flat, quantizedFlat og diskANN i dokumentasjonen. Knytt valget til dimensjoner, mengde, recall og latency. Vi bruker små undervisningsvektorer for å verifisere spørringen; en virkelig løsning bruker dokument- og spørsmålsvektorer fra samme embedding-modell. Selve modellkallet er ikke del av økten.

Rydding og overgang til neste del

Vectors-containeren kan slettes etter testen. Behold notes, databasen og kontoen til change feed-øvelsen i neste del.

Del 11

Behandle endringer fra Cosmos DB

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Før du starter

Bruk notes-containeren fra workshop 9, Azure Functions Core Tools v4 og en lab-Storage-konto. Kjør Python-aktivering fra prosjektroten. Kopier innstillingseksemplet til local.settings.json og erstatt begge connection strings med labverdier.

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/cosmos/requirements.txt
Copy-Item labs/cosmos/local.settings.example.json labs/cosmos/local.settings.json
Set-Location labs/cosmos
func start

1. Observer nye endringer

Ha COSMOS_ENDPOINT, COSMOS_KEY og COSMOS_DATABASE satt i en annen, aktivert terminal i prosjektroten. Kjør:

python labs/cosmos/demo.py update

Forventet: Function-loggen viser changed id=note-1 med ny revision. Finn cosmos_db_trigger. Dette er en change feed-prosessor med checkpoint i lease-containeren; den erstatter polling du ellers måtte håndtert selv.

2. Restart og undersøk leases

Finn leases i databasen. Stopp Functions-host, oppdater note-1 to ganger, og start host-en igjen. Observer at behandlingen fortsetter fra checkpoint. Sammenlign siste endringsversjon med applikasjonens behov: standard latest-version feed er ikke en komplett historikk over alle mellomliggende tilstander eller slettinger.

3. Gjør behandlingen robust

Forklar hvorfor sideeffekter må tåle gjentatt levering. Utvid logglinjen med dokumentets _etag og diskuter en varig nøkkel for en indeksoppdatering. I denne laben er sideeffekten bare logging; en applikasjon må registrere ferdig behandling før den kan stole på deduplisering.

Rydding og overgang til neste del

Stopp Functions-host og slett local.settings.json med labnøkler. Cosmos-konto og dedikert Storage kan slettes når change feed-testen er ferdig.

Del 12

Caching og invalidering med Managed Redis

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Klargjør før økten

Ha en Azure Managed Redis-labinstans klar med Enterprise clustering, TLS og en labnøkkel. Hvis du skal ta workshop 13, må RediSearch velges ved opprettelsen, med en tier som støtter modulen og NoEviction. Modulen kan ikke legges til senere. En arrangør kan klargjøre en delt labinstans.

1. Koble til sikkert

.\.venv\Scripts\Activate.ps1
python -m pip install -r labs/redis/requirements.txt
$env:REDIS_HOST = "DITT-REDIS-ENDPOINT"
$env:REDIS_PORT = "10000"
$env:REDIS_KEY = "DIN-LAB-NOKKEL"

Les tilkoblingen i demo.py. Den bruker TLS og en gjenbrukt klient. Enterprise clustering gir ett logisk endepunkt til den vanlige Redis-klienten; OSS clustering krever en cluster-klient.

2. Hit, miss og utløp

python labs/redis/demo.py cache

Forventet: først en miss, så en hit med positiv TTL, deretter miss etter invalidation og miss etter utløp. Skriptet sletter bare sin egen nøkkel. Kjør på nytt og sammenlign. Finn GET, SET med EX, DELETE og TTL i koden.

3. Knytt operasjonene til applikasjonen

Tegn rekkefølgen for cache-aside: GET, databaseoppslag ved miss, SET med TTL. Beskriv deretter hva en dokumentoppdatering skal invalidere. La nøkkelen inneholde søkeområde og dataversjon. Sammenlign kort TTL med eksplisitt invalidation; de løser ulike deler av problemet.

Rydding og overgang til neste del

Behold Managed Redis og RediSearch-oppsettet til vektorøvelsen i neste del. Sett miljøvariablene på nytt hvis du bytter terminal.

Del 13

Vektorindeks i Managed Redis

Åpne som kort workshop →

Gå tilbake til prosjektmappen i terminalen fra klargjøringen over:

Set-Location $projectRoot

Før du starter

Bruk RediSearch-instansen fra workshop 12 med Enterprise clustering og NoEviction. Sett REDIS_HOST, REDIS_PORT og REDIS_KEY på nytt. Aktiver prosjektets .venv. En standard Redis-instans uten søkemodulen kan ikke kjøre FT.CREATE.

1. Opprett en vektorindeks

python labs/redis/demo.py index

Finn VectorField, HNSW, FLOAT32 og DIM=3 i demo.py. De lagrede byteverdiene og spørsmålsvektoren må bruke samme dtype og dimensjon. Undersøk også TAG-feltet topic og prefikset som avgrenser labens dokumenter.

2. Søk og avgrens

python labs/redis/demo.py search

Vent på indeksering hvis første søk er tomt. Forventet: dokument 2 før 1, mens dokument 3 utelates av topic-filteret. Prøv en annen søkevektor i en lokal kopi og forklar både metadatafilter og KNN-rangering.

3. Undersøk endringer

Endre vektoren for dokument 2 i index-steget, kjør index og search igjen, og observer rangeringen etter at indeksen er oppdatert. Forklar forskjellen mellom en cache som inneholder ferdige søkeresultater og Redis som lagrer en søkbar vektorindeks.

Rydding og overgang til neste del

Kjør cleanup i Redis-skriptet for å fjerne labindeksen og dens dokumenter. Fjern REDIS_KEY og slett den dedikerte instansen.

python labs/redis/demo.py cleanup
Remove-Item Env:REDIS_KEY -ErrorAction SilentlyContinue
