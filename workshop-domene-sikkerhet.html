Én økt eller to samlinger

Én samlet økt omfatter hele domenet. Delingen i to samlinger er tematisk. Gjennomføringstiden er ikke målt; den avhenger av forkunnskaper, egne forsøk, diskusjon og klargjøring.

Vis øvelser for

Fremdrift deles mellom formatene på samme nettsted i denne nettleseren. Ved lokal bruk åpner du nettstedet via en lokal HTTP-server. Bytte av format gir samme oppgavedekning. Velg korte økter i stedet →

Del 19

Key Vault: oppslag, identitet og rotasjon

Åpne som kort workshop →

Før du starter

Bruk en egen Key Vault med Azure RBAC og nettverkstilgang fra maskinen, og Function App-en fra workshop 14. Gi din bruker Secrets Officer for å opprette testhemmeligheten; appen får en egen leserolle. Ha Azure CLI innlogget.

.\.venv\Scripts\Activate.ps1
python -m pip install -r artifacts/labs/security/requirements.txt
az login
$env:KEY_VAULT_URL = "https://DITT-HVELV.vault.azure.net/"

1. Opprett og les en testhemmelighet

I hvelvet: opprett demo-secret med verdien workshop-only-v1. Kjør:

python artifacts/labs/security/read_settings.py secret

Forventet: Secret read successfully: True og en versjons-ID. Skriptet bruker DefaultAzureCredential og skriver aldri verdien. Forklar hvorfor data-plane-tilgang trengs i tillegg til rett til å administrere ressursen.

2. Roter ved å opprette ny versjon

Legg til ny versjon av demo-secret med verdien workshop-only-v2. Kjør oppslaget igjen og sammenlign versjons-ID. Undersøk forskjellen på en versjonsbundet og en versjonsløs URI. Beskriv hvordan en app som cacher verdien må få den oppdatert.

3. Gi appen egen tilgang

  1. Aktiver system-assigned identity på Function App-en.
  2. Gi appidentiteten Key Vault Secrets User på labhvelvet.
  3. Legg app setting DEMO_SECRET til Function App-en med referansen under. Lagre og kontroller referansestatus.
  4. Kall configuration-funksjonen med Get Function URL. Forventet: secret_configured=true.
@Microsoft.KeyVault(SecretUri=https://DITT-HVELV.vault.azure.net/secrets/demo-secret/)

Plattformen løser referansen. Koden leser miljøvariabelen. Oppdateringer kan være forsinket av referansens cache; følg dokumentert refresh eller endre appkonfigurasjonen hvis du skal teste ny henting.

Rydding og overgang til neste del

Fjern appens DEMO_SECRET-setting og rydd labhvelv/Function App når de er ferdig brukt. App Configuration-øvelsen i neste del trenger ikke Key Vault-oppslaget.

Del 20

Les appkonfigurasjon med etiketter

Åpne som kort workshop →

Før du starter

Opprett en App Configuration-labressurs, for eksempel Free hvis tilgjengelig. Gi deg selv App Configuration Data Owner for å legge inn verdier. Bruk prosjektets .venv og artifacts/labs/security/requirements.txt. Innstillingene skal være vanlig konfigurasjon; hemmeligheter hører til i Key Vault.

1. Lag to verdier med etiketter

I Configuration explorer: opprett nøkkel Workshop:Mode, label lab, verdi practice. Legg samme nøkkel med label test og verdi review. Finn endpoint på Overview.

2. Les med SDK

$env:APP_CONFIG_ENDPOINT = "https://DITT-NAVN.azconfig.io"
python artifacts/labs/security/read_settings.py config

Forventet: Workshop mode: practice. Finn label=lab i koden. Endre label til test i arbeidskopien og kontroller review. For en driftet app som bare leser, holder Data Reader.

3. Endre uten nytt image

Endre lab-verdien i portalen og kjør skriptet igjen. Forklar hvorfor dette korte programmet leser på nytt hver gang. En langlivet prosess trenger en bevisst strategi for refresh og cache; nytt portalinnhold alene endrer ikke gamle verdier i minnet.

Rydding og overgang til neste del

Fjern APP_CONFIG_ENDPOINT og slett den dedikerte App Configuration-ressursen. Neste del bruker de lokale sporingsprogrammene.

Remove-Item Env:APP_CONFIG_ENDPOINT -ErrorAction SilentlyContinue
Del 21

Spor et kall mellom to tjenester

Åpne som kort workshop →

Før du starter

.\.venv\Scripts\Activate.ps1
python -m pip install -r artifacts/labs/observability/requirements.txt

services.py kjører enten frontend på 8091 eller backend på 8092. Start dem i to terminaler, begge fra prosjektroten. Uten connection string eksporteres spans til konsollen.

1. Start to tjenester

python artifacts/labs/observability/services.py backend

I den andre aktiverte terminalen:

python artifacts/labs/observability/services.py frontend

I en tredje terminal:

Invoke-RestMethod http://localhost:8091/process

Forventet: status 200 og en trace-ID. Finn samme ID i begge konsollene.

2. Følg foreldre og kontekst

Finn SERVER-spannet i frontend, CLIENT-spannet call-backend og SERVER-spannet i backend. Trace-ID er felles; span-ID-ene er ulike og ParentId kobler dem. Finn inject på senderen og extract på mottakeren. Fjern inject i arbeidskopien, restart frontend og sammenlign. Sett den tilbake etter testen.

3. Finn treghet og feil

Invoke-RestMethod "http://localhost:8091/process?delay=0.4"
curl.exe -i "http://localhost:8091/process?fail=1"

Forventet: tregere span og deretter HTTP 500 med error-status på berørte spans. Finn hvor feilen oppstår, og skill den fra symptomene i frontend.

4. Send til Azure og rydd opp

Forbered en Application Insights-ressurs med tilknyttet workspace før neste økt. Stopp begge tjenester og sett denne variabelen i begge aktiverte terminaler:

$env:APPLICATIONINSIGHTS_CONNECTION_STRING = "LIM-INN-DIN-CONNECTION-STRING"

Start backend og frontend igjen og gjenta kallene. Koden eksporterer både spans og egendefinerte request-/duration-målinger. Avslutt med Ctrl+C slik at eksportørene får flush.

Del 22

Finn feil og målinger med KQL

Åpne som kort workshop →

Før du starter

Bruk Application Insights og workspace fra workshop 21. Begge prosesser må bruke samme connection string. Start dem igjen ved behov og send noen vanlige, trege og feilende kall. Vent på innlesing av telemetri. Åpne Logs i den tilknyttede Log Analytics-workspace-en. Lagre egne spørringer i artifacts/queries.kql og eventuelle dataeksporter i artifacts/kql-results.csv.

1. Finn feil og svartid

AppRequests
| where TimeGenerated > ago(30m)
| where AppRoleName startswith "ai200-"
| summarize Requests=count(), Failures=countif(Success == false),
            P95=percentile(DurationMs, 95) by AppRoleName
| order by Failures desc

Forklar hva summarize gjør med radene, og hvorfor få kall gir en ustabil prosentil. Lag en spørring som viser bare mislykkede kall med OperationId.

2. Følg én trace på tvers av tjenester

union AppRequests, AppDependencies
| where TimeGenerated > ago(30m)
| where OperationId == "LIM-INN-TRACE-ID"
| project TimeGenerated, AppRoleName, Name, Id, ParentId, Success, DurationMs
| order by TimeGenerated asc

Forventet: frontend, call-backend og backend i samme operasjon. Undersøk ParentId/Id. En manglende backend-rad kan bety propagasjons- eller eksportfeil, ikke bare at backend ikke ble kalt.

3. Spør på egne målinger

AppMetrics
| where TimeGenerated > ago(30m)
| where AppRoleName startswith "ai200-"
| where Name == "workshop.requests"
| summarize Requests=sum(Sum) by bin(TimeGenerated, 1m), AppRoleName
| render timechart

Finn også workshop.duration. Undersøk Sum og Count, og beregn gjennomsnittlig varighet som sum(Sum)/sum(Count). Skill en forhåndsaggregert metrikk fra de enkelte span-radene. Dersom navnene avviker, start med å liste distinct Name fra AppMetrics.

Rydding og overgang til neste del

Stopp begge tjenester, fjern APPLICATIONINSIGHTS_CONNECTION_STRING og slett dedikerte overvåkingsressurser etter at du har undersøkt telemetrien.

Avslutt og studer videre

Kontroller at ressursene som er ferdig brukt er ryddet. Forklar de viktigste valgene uten å lese oppskriften, og bruk pensumsiden for domenet til å se kompetansemål og videre studier. Studiedekning og begrensninger er den samme for begge formater.
