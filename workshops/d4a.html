Why is ManagedIdentityCredential normally unavailable on a developer laptop?

ManagedIdentityCredential requests a token from the supported Azure host’s managed-identity endpoint. An ordinary developer laptop does not have that endpoint. For local work, use a developer credential, for example AzureCliCredential after az login, and grant that developer identity the necessary service permissions.

What is the Azure RBAC scope hierarchy from broadest to narrowest?

Management group → subscription → resource group → resource. Permissions assigned at a parent scope normally apply to its children. For example, a role on a resource group applies to resources in that group, so granting it on one resource is narrower than granting it on the entire subscription.

What is a service principal in an Entra tenant?

A service principal is an application’s local identity in a Microsoft Entra tenant. Permissions in that tenant are assigned to this identity. The application registration describes the application; a multitenant application can have a separate service principal in each tenant that uses it.

What does an Azure Network Security Group filter?

A Network Security Group (NSG) allows or denies network flows using rules for addresses, ports and protocols. It can apply to supported subnets or network interfaces. An allowed connection still needs application or service authorization. An NSG rule does not grant permission to read a secret or database record.

prep-rbac-028 · Åpne dette flashcardet

How do system-assigned and user-assigned identities differ in lifecycle?

A system-assigned managed identity belongs to one Azure resource and is deleted with it. A user-assigned managed identity is a separate resource that can outlive an app and be attached to several supported resources. Use a user-assigned identity when you need to authorize it before deploying the app or share its lifecycle across deployments.

In what order does Python DefaultAzureCredential try credential types?

The documented Python sequence is: 1. Environment-configured application credentials. 2. Workload Identity using a federated token. 3. Managed Identity on an Azure host. 4. Shared Token Cache on Windows. 5. Visual Studio Code sign-in. 6. Azure CLI sign-in. 7. Azure PowerShell sign-in. 8. Azure Developer CLI sign-in. 9. Interactive browser, disabled by default. 10. Broker authentication where supported. Unavailable/excluded mechanisms are skipped. Developer tools require a signed-in account; VS Code/broker support also depends on the broker package/platform. SDK version and options can change the effective chain.

How can the same DefaultAzureCredential code run locally and on Azure?

Locally, DefaultAzureCredential can use a signed-in developer tool, such as Azure CLI. On Azure, it can use the application’s managed identity. The service client accepts the same credential interface in either environment. Give both identities the required permissions. A failing configured deployment credential can stop the chain; fallback is not guaranteed for every authentication error.

What does AZURE_TOKEN_CREDENTIALS control in Python DefaultAzureCredential?

AZURE_TOKEN_CREDENTIALS limits which mechanisms Python DefaultAzureCredential tries. prod includes deployed-service credentials; dev includes developer-tool credentials. Supported versions also accept a single credential name, such as AzureCliCredential. The prod/dev options require azure-identity 1.23.0 or later; individual names require 1.24.0 or later. This selects authentication methods, not the permissions granted to the identity.

How do Azure Owner and Contributor differ in access management?

Both Owner and Contributor can manage resources within their assigned scope. Owner also grants the ability to create and remove Azure role assignments. Contributor does not grant that access-management permission.

prep-rbac-001 · Åpne dette flashcardet

How do Azure RBAC allow assignments combine across scopes?

Permissions from applicable role assignments add together, including assignments inherited from parent scopes. A narrower role does not cancel permissions already granted by a broader one. Applicable role conditions and deny assignments can restrict the result. Evaluate the complete set of assignments when investigating access.

Which Azure data-plane role permits an app identity to read Blob content?

Use Storage Blob Data Reader. It allows an identity to read blob content through Microsoft Entra authentication at the assigned container, account or parent scope. The general Reader role only reads management information; it does not itself authorize access to blob contents.

prep-p-rbac-007 · Åpne dette flashcardet

How can a CI pipeline authenticate to Azure without storing a long-lived client secret?

Use workload identity federation. Microsoft Entra trusts a token issued by the pipeline provider for a configured repository, branch or environment and exchanges it for an Azure access token. Grant the federated identity the deployment roles it needs. The pipeline does not need to store a long-lived client secret.

prep-p-rbac-023 · Åpne dette flashcardet

What can an Azure ABAC condition add to a supported role assignment?

Attribute-based access control (ABAC) conditions narrow the permission granted by a supported role assignment. For example, a Blob data role can be restricted to objects with particular tags. Conditions can use supported resource, request, identity or environment attributes; they do not grant access on their own.

What does an Entra sign-in log reveal about an authentication attempt?

It records the identity/application involved, time, source IP, success/failure and available authentication or Conditional Access details. Use it to investigate why a sign-in succeeded or failed. It describes authentication-related activity; use the target service’s logs as well to investigate later data-access authorization or application failures.

"""Show secret version metadata; never print a secret value."""
# Velg versjonsløs eller versjonsfestet lesing.
import argparse
# Les endpoint og første versjons-ID fra terminalen.
import os


# Kjør ett eksplisitt oppslag.
def main():
    # Beskriv tillatte operasjoner.
    parser = argparse.ArgumentParser()
    # current velger siste versjon; pinned bruker lagret ID.
    parser.add_argument("mode", choices=["current", "pinned"])
    # Les valget før nettverk brukes.
    args = parser.parse_args()
    # Autentiser med samme identitetskjede som resten av løpet.
    from azure.identity import DefaultAzureCredential
    # Bruk Key Vaults secret-klient.
    from azure.keyvault.secrets import SecretClient
    # Velg en eksplisitt versjon bare i pinned-modus.
    version = os.environ["FIRST_SECRET_VERSION"] if args.mode == "pinned" else None
    # Lukk både credential og nettverksklient etter oppslaget.
    with DefaultAzureCredential() as credential, SecretClient(vault_url=os.environ["KEY_VAULT_URL"], credential=credential) as client:
        # Les selve verdien, men bruk bare status og metadata i utskriften.
        secret = client.get_secret("demo-secret", version=version)
        # Vis at lesingen faktisk returnerte en verdi uten å eksponere den.
        print("Read:", bool(secret.value), "Version:", secret.properties.version)


# Ingen oppslag skjer ved import.
if __name__ == "__main__":
    # Utfør det valgte oppslaget.
    main()
Forventet resultat og forklaring

Current viser ny versjon; pinned viser den opprinnelige. En versjons-ID, en tillatelse og en refresh-mekanisme er hver sin del av rotasjonsforløpet.

Which Key Vault object type should hold an API credential?

Use a secret. An API credential is a value that an application presents to another service, like a password. A Key Vault key is a cryptographic object used for operations such as encryption and signing. The word “key” in “API key” does not make the credential that kind of object.

Which Key Vault RBAC role reads secret values?

Use Key Vault Secrets User. It allows an identity to read secret values without creating, changing or deleting them. The vault must use the Azure RBAC permission model. Network access is also required; the role does not make an unreachable private vault reachable.

Which Key Vault RBAC role manages secret versions and deletion?

Key Vault Secrets Officer can manage secrets, including creating versions, reading, deleting and recovering them, subject to vault protections. It does not grant role-assignment management. An application that only retrieves a credential normally needs the narrower Key Vault Secrets User role.

m-52-3-1 · Åpne dette flashcardet

Which vault permission model makes Key Vault data-plane role assignments effective?

The vault must use the Azure role-based access control (RBAC) permission model. If it uses legacy access policies, those policies govern object access instead. Assigning Key Vault Secrets User has no secret-read effect on a vault that still uses access policies.

How does a versionless Key Vault SDK read behave after rotation?

A new get_secret("name") call requests the latest version without specifying its version ID. After rotation, a fresh call can therefore retrieve the replacement. A value already stored in memory does not change itself. The application must read again and update any client or connection that uses the old credential.

m-53-1-1 · Åpne dette flashcardet

How does a version-pinned Key Vault SDK read behave after rotation?

A call such as get_secret("name", version="version-id") continues requesting that specific version, even after a newer one is created. Update the configured version to adopt the replacement, or use a versionless read to follow the latest version. The requested version must remain enabled and available.

What is the setup order for reading Key Vault with an app identity?

Enable the application’s managed identity, grant it Key Vault Secrets User on the appropriate RBAC-enabled vault and provide network access. Then create a SecretClient with the vault URL and token credential, and call get_secret. When running locally, your developer identity needs its own access. The deployed app’s role assignment does not grant your signed-in account permission.

What scope should be preferred for an application's Key Vault permissions?

Microsoft recommends a separate vault per application per environment, with suitable roles at the vault scope. This gives the app access to its own secrets without broad subscription-wide authority. Individual-secret scopes are supported for special cases, but are not the usual default design. Give a read-only app Secrets User rather than Administrator.

Why does copying a secret into app settings at deployment not implement rotation?

The app setting holds a copy of the value at deployment time. Creating a new Key Vault version does not rewrite that copy or update an already connected client. Use a supported reference with its documented refresh behavior, or reread the secret in code and update the clients that use it.

Where should non-secret configuration and credentials be stored?

Store ordinary settings, such as service URLs and feature choices, in app settings or Azure App Configuration. Store passwords and API credentials in Key Vault. The app can retrieve a secret through an authorized SDK call or a supported Key Vault reference. The reference identifies the secret without copying its value into source code.

Can Key Vault Reader read secret values?

No. Key Vault Reader can inspect object metadata, such as names and properties, but cannot read secret values or private key material. For an application that needs secret values, assign Key Vault Secrets User at the appropriate scope on an RBAC-enabled vault.

What data-plane permissions does Key Vault Administrator grant?

Key Vault Administrator grants all data-plane operations on keys, secrets and certificates within its scope. The data plane is where callers work with those stored objects. It does not grant management of the vault resource or role assignments, and it cannot bypass protections such as purge protection.

m-52-4-1 · Åpne dette flashcardet

Does Key Vault Contributor grant access to secret contents?

No direct secret-read permission. Key Vault Contributor manages the vault resource on the control plane; it is not Key Vault Secrets User. With the legacy access-policy model, a sufficiently privileged contributor may change policies to grant data access, which is a reason to tightly control that management permission.

m-52-6-1 · Åpne dette flashcardet

How can Event Grid and Functions automate rotation of a Key Vault secret?

Set the secret’s expiration and route Key Vault’s SecretNearExpiry event through Event Grid to a rotation function. The documented notification occurs 30 days before expiry. The function must update the credential in the target service and save the matching new secret version with a new expiry. Clients must then adopt that replacement; changing only the Key Vault value is insufficient.

m-53-3-1 · Åpne dette flashcardet

Do Key Vault secrets have the same built-in rotation policies as cryptographic keys?

No. Cryptographic keys support Key Vault rotation policies. A password or API secret also belongs to an external service, so a workflow must update that service’s credential and store its matching value in Key Vault. An expiry notification can start that workflow, but does not itself generate and apply a working replacement credential.

What happens to access policies when a vault switches to Azure RBAC?

The existing access policies stop authorizing operations on keys, secrets and certificates. They are not automatically converted into equivalent role assignments. Prepare the required Azure role assignments before changing the permission model, then verify that each application can still access its objects.

Which secret lifecycle features does Key Vault provide?

Key Vault provides secret versions, expiration metadata, access auditing and recovery through soft delete. Purge protection can prevent permanent deletion before the retention period ends. These features manage the stored secret. A separate rotation workflow must replace the credential in the external service that accepts it.

Who resolves a Key Vault reference stored in App Configuration?

The application’s App Configuration provider or resolver reads the reference and retrieves the secret from Key Vault. It needs an authorized credential for that vault as well as access to the configuration store. App Configuration stores the reference; it does not retrieve the secret on the application’s behalf.

How can AKS mount Key Vault secrets as files without creating Kubernetes Secret objects?

Use the Azure Key Vault provider for the Secrets Store CSI Driver. A SecretProviderClass identifies the objects to retrieve, and an authorized identity lets the driver mount their contents as files in the pod. Synchronizing them into Kubernetes Secret objects is optional. If rotation changes the mounted files, the application still needs to reread them.

Which Key Vault capability retains deleted objects for possible recovery?

Soft delete. Deleted vaults and objects remain recoverable for the configured retention period, from 7 to 90 days with a default of 90. Recovery requires permission. After permanent purge or the recovery period ends, soft delete cannot restore the object.

What does Key Vault purge protection prevent?

It prevents permanently purging a protected soft-deleted vault or object until its retention period has elapsed, including attempts by administrators. Soft delete makes recovery possible; purge protection prevents an early permanent deletion from removing that recovery option. Enabling purge protection cannot later be undone to bypass the waiting period.

Which Key Vault diagnostic category records data-plane access such as secret reads?

The AuditEvent diagnostic category records Key Vault data-plane operations, including secret-read attempts and their outcomes. It does not contain the secret values. Configure a diagnostic setting to send those logs to a destination such as Log Analytics. Creating a vault alone does not route its audit records to your workspace.

How should a private package-feed token be supplied during a container build?

Use a build-time secret mount, such as Docker BuildKit secrets. If FEED_TOKEN is securely set in the environment: docker build --secret id=feed_token,env=FEED_TOKEN -t myapp:v1 . A Dockerfile RUN step using --mount=type=secret,id=feed_token can read /run/secrets/feed_token for that step. Configure the package client to consume it without printing or copying it into the image. ARG, ENV and ordinary COPY can expose credentials in image/configuration history or layers.

How can a credential rotation avoid immediately breaking clients that still hold the old value?

Where the service supports two valid credentials, introduce or regenerate the unused one, store it in Key Vault and refresh clients to use it. Keep the old credential valid during that transition, then retire it after confirming adoption. Refresh cached values and connection pools as needed. A new Key Vault version alone does not update every running client.

"""Optional Azure exercise: read a demo secret and ordinary configuration via Entra ID."""

# Velg Key Vault-hemmelighet eller vanlig appkonfigurasjon.
import argparse
# Les tjenestenes endpoint fra miljøet.
import os

# Les nøkkel-/etikettverdier fra App Configuration.
from azure.appconfiguration import AzureAppConfigurationClient
# Bruk Entra-identitet, for eksempel Azure CLI-innlogging på egen maskin.
from azure.identity import DefaultAzureCredential
# Les hemmeligheter gjennom Key Vaults data-API.
from azure.keyvault.secrets import SecretClient

# Kjør ett oppslag mot den valgte tjenesten.
def main():
    # Opprett kommandolinjeparseren.
    parser = argparse.ArgumentParser()
    # Tillat bare de to oppslagstypene.
    parser.add_argument("mode", choices=["secret", "config"])
    # Les valgt oppslagstype.
    args = parser.parse_args()
    # Gjenbruk samme identitetsoppsett for begge tjenester.
    with DefaultAzureCredential() as credential:
        # Key Vault-operasjonen krever tilgang til hemmelighetens verdi.
        if args.mode == "secret":
            # Åpne klienten for ditt labhvelv.
            with SecretClient(vault_url=os.environ["KEY_VAULT_URL"], credential=credential) as vault:
                # Les gjeldende versjon av demo-secret.
                secret = vault.get_secret("demo-secret")
                # Vis bare at verdien ble lest, aldri selve hemmeligheten.
                print("Secret read successfully:", bool(secret.value))
                # Bruk versjons-ID til å observere rotasjon.
                print("Secret version:", secret.properties.version)
            # Avslutt etter Key Vault-oppslaget.
            return
        # Åpne klienten for vanlig konfigurasjon.
        with AzureAppConfigurationClient(
            # Bruk App Configuration-endpoint og den samme Entra-identiteten.
            base_url=os.environ["APP_CONFIG_ENDPOINT"], credential=credential
        # Lukk konfigurasjonsklienten etter bruk.
        ) as config:
            # Les akkurat nøkkelen og miljøetiketten som ble opprettet i portalen.
            setting = config.get_configuration_setting(key="Workshop:Mode", label="lab")
            # Vis den vanlige konfigurasjonsverdien i terminalen.
            print("Workshop mode:", setting.value)


# Start bare når filen kjøres direkte.
if __name__ == "__main__":
    # Kjør valgt konfigurasjonsoppslag.
    main()

"""Refresh ordinary configuration in one long-lived Python process."""
# Les butikkens endpoint fra terminalen.
import os
# Vent mellom eksplisitte refresh-forsøk.
import time


# Kjør en kort, avgrenset observasjonsøkt.
def main():
    # Bruk den offisielle provideren med sentinel og intervallet i øvelsen.
    from azure.appconfiguration.provider import load, SettingSelector, WatchKey
    # Del samme identitet mellom provider og underliggende klienter.
    from azure.identity import DefaultAzureCredential
    # Lukk credential og provider når observasjonen er ferdig.
    with DefaultAzureCredential() as credential, load(
        # Velg ressursen deltakeren har opprettet.
        endpoint=os.environ["APP_CONFIG_ENDPOINT"], credential=credential,
        # Last bare verdiene som den kjørende appen trenger.
        selects=[SettingSelector(key_filter="Workshop:*", label_filter="lab"), SettingSelector(key_filter="sentinel")],
        # Sentinel uten label utløser ny lasting av de valgte verdiene.
        refresh_on=[WatchKey("sentinel")], refresh_interval=5
    ) as config:
        # Kjør i omtrent ett minutt, nok til en manuell endring.
        for _ in range(30):
            # Kall refresh eksplisitt; provider respekterer intervallet.
            config.refresh()
            # Vis bare vanlig konfigurasjon, ikke secrets.
            print("Workshop:Mode =", config["Workshop:Mode"], flush=True)
            # La deltakeren endre labverdien og sentinel underveis.
            time.sleep(2)


# Unngå nettverkskall ved import.
if __name__ == "__main__":
    # Start observasjonsløkken.
    main()

What is an App Configuration sentinel key used for?

A sentinel is a setting you change after completing a related set of configuration edits. Configure the application’s provider to watch it and reload the selected settings when it changes. This signals when the update is ready to load. It does not turn the separate store writes into one atomic transaction.

What uniquely identifies an App Configuration key-value?

The key and label together identify an entry. For example, Api:Timeout with label Production can contain 30, while Api:Timeout with label Development contains 10. The same key with no label is another entry. The application chooses which key/label combinations to load.

How do App Configuration Data Reader and Data Owner differ?

App Configuration Data Reader can read stored key-values. App Configuration Data Owner can also create, update and delete them. Use Reader for an application that only consumes configuration. These are data-access roles, separate from permission to manage the Azure resource itself.

How does Python App Configuration refresh use a watch key and interval?

Use a watched sentinel with the Python provider: from azure.appconfiguration.provider import load, WatchKey from azure.identity import DefaultAzureCredential config = load(endpoint=endpoint, credential=DefaultAzureCredential(), refresh_on=[WatchKey("sentinel")], refresh_interval=10) config.refresh() Here endpoint is the store URL. What should an app do when a configuration refresh fails?

After a successful initial load, keep serving the cached configuration and record the refresh failure. A later eligible refresh can retry. Startup needs a separate policy: with no previously loaded values, either fail startup or use explicitly chosen safe defaults. There is no last successful configuration to fall back to yet.

Why are environment variables unsuitable for in-process dynamic refresh?

An external setting change does not rewrite a running process’s environment. App Service applies changed app settings through a restart; Container Apps environment-variable changes create a new revision. For updates inside an existing process, use a refresh-capable provider and ensure the application reads its refreshed values.
