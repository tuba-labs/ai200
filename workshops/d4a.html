Why is ManagedIdentityCredential normally unavailable on a developer laptop?

ManagedIdentityCredential asks the Azure host's managed-identity endpoint for a token. An ordinary developer laptop has no such endpoint. Use a developer credential locally, such as AzureCliCredential after signing in with az login.

What is the Azure RBAC scope hierarchy from broadest to narrowest?

Management group → subscription → resource group → resource. Permissions assigned at a parent scope normally apply to its children. For example, a role on a resource group applies to resources in that group, so granting it on one resource is narrower than granting it on the entire subscription.

How do system-assigned and user-assigned identities differ in lifecycle?

A system-assigned managed identity belongs to one resource and is deleted with it. A user-assigned identity is a separate Azure resource that can outlive an app and be attached to several supported resources. You can therefore create and authorize a user-assigned identity before the app exists.

How do Azure Owner and Contributor differ in access management?

Both can manage resources at their assigned scope. Owner can also create and remove role assignments, controlling who gets access. Contributor does not include that role-assignment permission.

How do Azure RBAC allow assignments combine across scopes?

Allowed permissions add together across the roles and inherited scopes that apply to the identity. A narrowly scoped role does not remove permission granted by a broader role. Applicable role conditions and deny assignments can still restrict access, so evaluate the full set rather than looking only at one assignment.

What can an Azure deny assignment block despite an allow role assignment?

It blocks the actions specified by that deny assignment for the affected principals and scope, even when an allow role would grant them. Adding another allow role does not override it. Deny assignments have their own applicability and exclusion rules; they are different from a custom role’s NotActions list.

What does the actions field of a custom Azure RBAC role define?

Actions lists permitted management operations, such as creating or updating an Azure resource. DataActions covers supported operations on the service's data. NotActions removes operations from this role's Actions list; another role can still grant them, so it is not a global denial.

What does assignableScopes constrain in a custom Azure RBAC role?

AssignableScopes defines where the custom role is available to be assigned, such as particular subscriptions or resource groups. It does not grant anyone access by itself. An actual role assignment must still connect a principal, that role definition and an allowed scope.

It blocks deletion through Azure Resource Manager for the protected resource/scope, while allowing permitted reads and updates. What does the Azure User Access Administrator role allow?

It manages user access at the assigned scope, including creating and removing Azure role assignments. It does not give the general resource-management permissions of Contributor. Because it can grant powerful roles, keep its scope and assignment tightly controlled.

"""Show secret version metadata; never print a secret value."""
# Velg versjonsløs eller versjonsfestet lesing.
import argparse
# Les endpoint og første versjons-ID fra terminalen.
import os


# Kjør ett eksplisitt oppslag.
def main():
    # Beskriv tillatte operasjoner.
    parser = argparse.ArgumentParser()
    # current velger siste versjon; pinned bruker lagret ID.
    parser.add_argument("mode", choices=["current", "pinned"])
    # Les valget før nettverk brukes.
    args = parser.parse_args()
    # Autentiser med samme identitetskjede som resten av løpet.
    from azure.identity import DefaultAzureCredential
    # Bruk Key Vaults secret-klient.
    from azure.keyvault.secrets import SecretClient
    # Velg en eksplisitt versjon bare i pinned-modus.
    version = os.environ["FIRST_SECRET_VERSION"] if args.mode == "pinned" else None
    # Lukk både credential og nettverksklient etter oppslaget.
    with DefaultAzureCredential() as credential, SecretClient(vault_url=os.environ["KEY_VAULT_URL"], credential=credential) as client:
        # Les selve verdien, men bruk bare status og metadata i utskriften.
        secret = client.get_secret("demo-secret", version=version)
        # Vis at lesingen faktisk returnerte en verdi uten å eksponere den.
        print("Read:", bool(secret.value), "Version:", secret.properties.version)


# Ingen oppslag skjer ved import.
if __name__ == "__main__":
    # Utfør det valgte oppslaget.
    main()
Forventet resultat og forklaring

Current viser ny versjon; pinned viser den opprinnelige. En versjons-ID, en tillatelse og en refresh-mekanisme er hver sin del av rotasjonsforløpet.

Which Key Vault object type should hold an API credential?

A secret. In Key Vault terminology, an API key is an opaque credential value, like a password. A Key Vault key is a cryptographic key used for operations such as signing or encryption. The word “key” in an API credential’s name does not make it a cryptographic-key object.

Which Key Vault RBAC role reads secret values?

Key Vault Secrets User. It lets an identity read secret values without managing or deleting the secrets. The vault must use the Azure role-based access control (RBAC) permission model, and the app must also be able to reach the vault.

Which Key Vault RBAC role manages secret versions and deletion?

Key Vault Secrets Officer. It can perform secret operations such as setting new versions, reading, deleting and recovering secrets, subject to vault protections. It does not grant permission to manage role assignments. Use Secrets User instead when an application only needs to read a credential.

Which vault permission model makes Key Vault data-plane role assignments effective?

The Azure role-based access control (RBAC) permission model. On a vault using legacy access policies, those policies control data access instead. Assigning Key Vault Secrets User will not grant a secret read until the vault is using the RBAC model.

How does a versionless Key Vault SDK read behave after rotation?

A fresh get_secret("name") call requests the latest version, so it can retrieve the rotated value without changing the name. A value already held in memory does not update itself; the app must read again and update anything using the old credential.

How does a version-pinned Key Vault SDK read behave after rotation?

It keeps requesting the specified version. For example, get_secret("name", version="version-id") continues reading that version after rotation. Change the configured version, or use a versionless read to follow the latest version. The pinned version must still be enabled and available.

What is the setup order for reading Key Vault with an app identity?

Enable a managed identity for the app, grant it Key Vault Secrets User on the appropriate RBAC-enabled vault, and ensure network access. Then create a SecretClient with the vault URL and a token credential, and call get_secret. For local development, the signed-in developer identity needs its own access; enabling the deployed app’s identity does not grant the developer permission.

What scope should be preferred for an application's Key Vault permissions?

Microsoft recommends a separate vault per application per environment, with suitable roles at the vault scope. This gives the app access to its own secrets without broad subscription-wide authority. Individual-secret scopes are supported for special cases, but are not the usual default design. Give a read-only app Secrets User rather than Administrator.

Why does copying a secret into app settings at deployment not implement rotation?

The app setting contains a copy of the old value. A new Key Vault version does not rewrite that copy or update a running client. Use a supported Key Vault reference with refresh, or code that rereads the secret and updates the clients that use it.

Where should non-secret configuration and credentials be stored?

Use app settings or Azure App Configuration for ordinary values such as feature options and service URLs. Store passwords, API tokens and similar credentials in Key Vault. The app retrieves secrets through an authorized SDK call or a supported Key Vault reference, keeping the actual credential out of source code and ordinary configuration files.

Can Key Vault Reader read secret values?

No. Key Vault Reader can read metadata, such as object names and properties, but not secret values or private key material. Reading an actual secret requires a role such as Key Vault Secrets User on a vault using the Azure RBAC permission model.

What data-plane permissions does Key Vault Administrator grant?

All Key Vault data-plane operations on keys, secrets and certificates in its assigned scope. “Data plane” means working with the stored objects themselves. It does not manage the vault resource or role assignments, and it does not bypass protections such as purge protection.

m-52-4-1 · Åpne dette flashcardet

What does Key Vault Purge Operator permit?

Permanent deletion of soft-deleted vaults, within the assigned scope and subject to purge protection. It is not the general role for reading secret contents or purging any arbitrary secret object. If purge protection still applies, an administrator cannot use this role to bypass the retention period.

What does Key Vault Data Access Administrator manage?

It can add or remove a specified set of Key Vault data-plane role assignments, such as Secrets User and Secrets Officer. Its built-in condition limits which roles it may assign. It is an access-management role, not unrestricted Owner permission or automatic access to every secret value.

Does Key Vault Contributor grant access to secret contents?

No direct secret-read permission. Key Vault Contributor manages the vault resource on the control plane; it is not Key Vault Secrets User. With the legacy access-policy model, a sufficiently privileged contributor may change policies to grant data access, which is a reason to tightly control that management permission.

How can Event Grid and Functions automate rotation of a Key Vault secret?

Set the secret’s expiry. Key Vault emits SecretNearExpiry, normally 30 days before expiration; route that event through Event Grid to a rotation function. The function must change the credential in the actual target service and store the corresponding new secret version with a new expiry. Writing a random new value only to Key Vault would leave the service and clients disagreeing.

Do Key Vault secrets have the same built-in rotation policies as cryptographic keys?

No. Cryptographic keys support Key Vault rotation policies. A password or API secret also belongs to an external service, so a workflow must update that service’s credential and store its matching value in Key Vault. An expiry notification can start that workflow, but does not itself generate and apply a working replacement credential.

What happens to access policies when a vault switches to Azure RBAC?

They no longer authorize operations on keys, secrets and certificates. Equivalent Azure role assignments must be configured separately; existing policies are not converted automatically. Prepare the role assignments before the switch and verify application access afterward.

Does Key Vault's recover permission allow reading a secret value?

No. Recover restores a soft-deleted object; Get/read permission controls access to its secret value. An identity can therefore be allowed to recover a secret without being allowed to retrieve its contents. Keep these permissions separate when designing recovery and application roles.

Which Key Vault capability retains deleted objects for possible recovery?

Soft delete. Deleted vaults and objects remain recoverable for the configured retention period, from 7 to 90 days with a default of 90. Recovery requires permission. After permanent purge or the recovery period ends, soft delete cannot restore the object.

What does Key Vault purge protection prevent?

It prevents permanently purging a protected soft-deleted vault or object until its retention period has elapsed, including attempts by administrators. Soft delete makes recovery possible; purge protection prevents an early permanent deletion from removing that recovery option. Enabling purge protection cannot later be undone to bypass the waiting period.

How do the DEK and KEK work in envelope encryption?

A data encryption key (DEK) encrypts the actual data. A key encryption key (KEK) encrypts, or “wraps,” the DEK. Store the wrapped DEK with the encrypted data and protect the KEK separately, for example in Key Vault. To read the data, an authorized process unwraps the DEK and uses it to decrypt the content.

"""Refresh ordinary configuration in one long-lived Python process."""
# Les butikkens endpoint fra terminalen.
import os
# Vent mellom eksplisitte refresh-forsøk.
import time


# Kjør en kort, avgrenset observasjonsøkt.
def main():
    # Bruk den offisielle provideren med sentinel og intervallet i øvelsen.
    from azure.appconfiguration.provider import load, SettingSelector, WatchKey
    # Del samme identitet mellom provider og underliggende klienter.
    from azure.identity import DefaultAzureCredential
    # Lukk credential og provider når observasjonen er ferdig.
    with DefaultAzureCredential() as credential, load(
        # Velg ressursen deltakeren har opprettet.
        endpoint=os.environ["APP_CONFIG_ENDPOINT"], credential=credential,
        # Last bare verdiene som den kjørende appen trenger.
        selects=[SettingSelector(key_filter="Workshop:*", label_filter="lab"), SettingSelector(key_filter="sentinel")],
        # Sentinel uten label utløser ny lasting av de valgte verdiene.
        refresh_on=[WatchKey("sentinel")], refresh_interval=5
    ) as config:
        # Kjør i omtrent ett minutt, nok til en manuell endring.
        for _ in range(30):
            # Kall refresh eksplisitt; provider respekterer intervallet.
            config.refresh()
            # Vis bare vanlig konfigurasjon, ikke secrets.
            print("Workshop:Mode =", config["Workshop:Mode"], flush=True)
            # La deltakeren endre labverdien og sentinel underveis.
            time.sleep(2)


# Unngå nettverkskall ved import.
if __name__ == "__main__":
    # Start observasjonsløkken.
    main()
