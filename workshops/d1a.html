Bygg to versjoner og påvis hva en tag peker på

  1. Opprett registeret i den nye gruppen. Sett $acr til registernavnet og $login til login server fra Overview. La $rg være ai200-v2-d1a.
  2. Kjør et lokalt image med APP_VERSION=v1 og push det med Docker. Bygg deretter v2 med ACR Tasks og build-argumentet. Samme appkode får ulike image-konfigurasjoner; versjonen kan også overstyres ved oppstart.
  3. Noter tag, manifest-digest og /health-resultat. Importer eller bygg en annen versjon til en gjenbrukt test-tag og sammenlign digestene. Forklar hva som faktisk fryser innholdet.
# Bygg imaget fra den nye labmappen.
docker build -t ai200-v2-api:v1 workshops/labs/containers
# Kjør imaget lokalt med en synlig versjon.
docker run --rm --name ai200-v2-api -d -p 127.0.0.1:8080:8080 -e APP_VERSION=v1 ai200-v2-api:v1
# Les versjon og helsestatus fra API-et.
Invoke-RestMethod http://localhost:8080/health
# Autentiser Docker mot ditt register med innlogget Azure-identitet.
az acr login --name $acr
# Gi det lokale imaget en full registeradresse.
docker tag ai200-v2-api:v1 "$login/ai200-v2-api:v1"
# Push første versjon til registeret.
docker push "$login/ai200-v2-api:v1"
# Bygg og push v2 i ACR uten lokal Docker-bygging.
az acr build --registry $acr --image ai200-v2-api:v2 --build-arg APP_VERSION=v2 workshops/labs/containers
# Vis hvilke tagger registeret inneholder.
az acr repository show-tags --name $acr --repository ai200-v2-api -o table

"""Small, deliberately local workshop API; no external Python dependencies."""
# Gjør Python-data om til JSON i HTTP-svaret.
import json
# Les appkonfigurasjon fra miljøvariabler i containeren.
import os
# Bruk en liten HTTP-server og en handler for hver forespørsel.
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
# Skill URL-stien fra eventuelle spørringsparametere.
from urllib.parse import urlsplit


# Samle behandlingen av HTTP-forespørsler i en handlerklasse.
class Handler(BaseHTTPRequestHandler):
    # HTTP-serveren kaller denne metoden for GET-forespørsler.
    def do_GET(self):
        # Hent bare stien, for eksempel /health.
        path = urlsplit(self.path).path
        # Helsesjekken gir 200; alle andre stier gir 404.
        status = 200 if path == "/health" else 404
        # Vis versjonen fra miljøet, med v1 som standard.
        payload = {"status": "ok", "version": os.getenv("APP_VERSION", "v1"),
                   # Vis konfigurasjonen uten at vi trenger å bygge et nytt image.
                   "mode": os.getenv("WORKSHOP_MODE", "practice"),
                   # Vis bare om en hemmelighet finnes. Selve verdien sendes aldri til klienten.
                   # For andre stier brukes en enkel feilmelding i stedet.
                   "secret_configured": bool(os.getenv("DEMO_SECRET"))} if status == 200 else {"error": "not found"}
        # Serialiser JSON og kod teksten som byte til nettverksforbindelsen.
        body = json.dumps(payload).encode("utf-8")
        # Start HTTP-svaret med statuskoden.
        self.send_response(status)
        # Fortell klienten at innholdet er JSON i UTF-8.
        self.send_header("Content-Type", "application/json; charset=utf-8")
        # Oppgi lengden på svaret i byte.
        self.send_header("Content-Length", str(len(body)))
        # Avslutt headerne før selve innholdet sendes.
        self.end_headers()
        # Skriv JSON-innholdet til HTTP-svaret.
        self.wfile.write(body)


# Start serveren bare når filen kjøres som et program.
if __name__ == "__main__":
    # Skriv en oppstartsmelding direkte til containerloggen.
    print("Workshop API listening on port 8080", flush=True)
    # Lytt på port 8080 på alle containerens nettverksgrensesnitt.
    ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

What does an ACR quick task do?

An ACR quick task builds an image on demand using Azure’s build infrastructure. For example: az acr build --registry myregistry --image orders:v1 . The final dot supplies the current directory as the build context. Azure builds the Dockerfile and, by default, stores the result as orders:v1 in myregistry. Your machine needs the source files and Azure CLI; Azure performs the Docker build.

m-03-1-1 · Åpne dette flashcardet

Why can pulling myapp:latest return a different image after another push?

latest is a tag that can be reassigned to another image. A later pull can therefore download different content under the same name. Use an unchanged release tag or, for an exact content reference, the image digest.

Eksempel · Scenario

On Monday, orders:latest points to build 10. On Tuesday, the pipeline reuses latest for build 11. A new pull can now select build 11 even though the text of the image reference has not changed.

m-04-1-1 · Åpne dette flashcardet

Why use a different image tag for each build?

A unique tag makes each build identifiable. For example, orders:build-1042 distinguishes one release from orders:build-1043, helping you deploy or roll back deliberately. Protect release tags from overwriting when they must remain fixed.

m-04-2-1 · Åpne dette flashcardet

Which image reference pins exact content even if a tag moves?

Reference the image by its manifest digest, such as myregistry.azurecr.io/orders@sha256:<digest>. The digest identifies the manifest’s content, so moving a tag does not change the image selected by this reference.

m-04-3-1 · Åpne dette flashcardet

How do you push a local container image to Azure Container Registry?

Assume myapp:v1 already exists locally and your ACR registry is named myregistry. 1. Sign in to Azure and authenticate Docker to the registry: az login az acr login --name myregistry 2. Give the local image a name that includes the destination registry: docker tag myapp:v1 myregistry.azurecr.io/myapp:v1 3. Upload the image using that full name: docker push myregistry.azurecr.io/myapp:v1 myregistry.azurecr.io is the registry hostname, myapp is the repository and v1 is the version tag. Tagging adds a local name; it does not rebuild or upload the image. Replace the example names with yours and use the actual Login server shown by ACR.

Which image tag is assumed when none is specified?

Docker assumes the tag latest. For example, docker pull myregistry.azurecr.io/orders requests orders:latest. latest is simply a published tag name; Docker does not search the repository for the newest build.

m-04-5-1 · Åpne dette flashcardet

How do you find the login-server hostname to use for an ACR image?

Use the registry’s actual Login server value. You can retrieve it with: az acr show --name myregistry --query loginServer -o tsv Use the returned hostname in image names. It is often myregistry.azurecr.io, but some registry naming configurations add a hash.

Use az acr repository show-tags: az acr repository show-tags --name myregistry --repository orders This lists tags in the orders repository, such as v1 and latest. It queries registry metadata rather than downloading the images.

Which source-code events can trigger an ACR Task?

An ACR Task can start when a commit reaches its configured branch, or when a pull request is created or updated. Commit triggers are enabled by default; pull-request triggers are opt-in. The repository and access token must support the webhook ACR registers.

Eksempel · Scenario

A build-orders task watches the main branch. Pushing a commit to main starts its image build. Opening a pull request starts a build only if the task’s pull-request trigger has also been enabled.

m-01-1-1 · Åpne dette flashcardet

How does an ACR Task know when to rebuild after its base image changes?

The first build records which base images the task uses. With base-image triggering enabled, an update to a tracked base image can start another build. Updates in an Azure container registry can trigger dependent tasks. Public Docker Hub and Microsoft Container Registry images are checked periodically, so rebuilding is not necessarily immediate.

Eksempel · Dockerfile base-image fragment

FROM studyacr.azurecr.io/python-base:v1

An ACR Task’s first build records this dependency. With base-image triggering configured, publishing changed content to this tracked base can trigger a dependent rebuild after detection.

m-01-2-1 · Åpne dette flashcardet

What schedule format does an ACR Tasks timer use?

Use a five-field cron expression for minute, hour, day of month, month and day of week. ACR interprets the schedule in UTC. For example, 0 9 * * 1-5 runs at 09:00 UTC on weekdays. ACR Tasks supports schedules as frequent as once per minute.

m-01-3-1 · Åpne dette flashcardet

Do ACR webhooks or Artifact Cache rules start source builds?

No. A registry webhook sends notifications about registry events, while an Artifact Cache rule retrieves and caches upstream images. To build source code automatically, configure an ACR Task with an appropriate source, base-image or timer trigger.

Eksempel · Scenario

An Artifact Cache rule makes an upstream nginx image available through your registry. It does not compile the orders repository. To compile that source after a commit, configure an ACR Task with a source trigger.

m-01-4-1 · Åpne dette flashcardet

Which pull and push roles apply to an ACR registry using RBAC Registry Permissions?

AcrPull grants image download access. AcrPush grants upload and download access. These roles apply when the registry uses RBAC Registry Permissions; check the permission mode before choosing a role.

Eksempel · Scenario

Give the running orders app only AcrPull so it can download images. Give the build identity AcrPush so it can upload releases as well. This example assumes RBAC Registry Permissions mode and no other grants.

m-02-1-1 · Åpne dette flashcardet

Which ACR roles grant repository pull or push access when ABAC is enabled?

Use Container Registry Repository Reader for pulls, or Container Registry Repository Writer for pushes and pulls. In RBAC Registry + ABAC Repository Permissions mode, a condition on the assignment can restrict it to selected repositories.

Eksempel · Scenario

Assign Repository Writer with a condition selecting the orders repository. If this is the identity’s only repository grant, it can push and pull orders images but cannot use that assignment to access payments images.

m-02-2-1 · Åpne dette flashcardet

Are legacy AcrPull, AcrPush and AcrDelete roles honored on an ABAC-enabled registry?

No. An ABAC-enabled registry does not honor AcrPull, AcrPush or AcrDelete for repository access. Use the applicable Container Registry Repository Reader, Writer or Contributor role, with repository conditions where needed.

Eksempel · Scenario

An app whose only image permission is AcrPull starts failing pulls after its registry switches to ABAC repository permissions. Replace that legacy grant with the appropriate repository-reader assignment; changing the image’s name alone will not fix authorization.

m-02-3-1 · Åpne dette flashcardet

How is a Git repository configured as an ACR Task's build context?

Set the task’s build context to the Git repository and branch. For example, in PowerShell, with an authorized token already stored in GIT_TOKEN: az acr task create --registry myregistry --name build-orders --image "orders:{{.Run.ID}}" --context "https://github.com/example/orders.git#main" --file Dockerfile --git-access-token $env:GIT_TOKEN Replace the example registry and repository. --context selects the source and branch, --file selects the Dockerfile, and the run ID gives each build its own image tag. The token needs the permissions required for the supported repository integration.

What defines an ACR multi-step task?

A task YAML file defines the steps, such as building an image, running tests and pushing it. Dependencies determine when each step may run, so a failed test can prevent a later push. To run an existing task file from the current directory: az acr run --registry myregistry --file task.yaml .

What sequence connects a Git commit to a new ACR image?

A commit reaches the watched branch, its webhook starts the ACR Task, and the task builds and pushes the image. Giving the image a unique build tag, such as orders:{{.Run.ID}}, lets you identify the result of that particular run.

How can a GitHub Actions workflow run an existing ACR Task?

After the workflow has authenticated to Azure, run the existing task with: az acr task run --registry myregistry --name build-orders GitHub Actions requests the run; ACR executes the task’s build steps. The task and workflow identity need the appropriate registry permissions.

How can an ACR tag be protected from later overwrites?

Disable writes to that tag. For example: az acr repository update --name myregistry --image orders:v1 --write-enabled false This protects orders:v1 from being overwritten. Also set delete-enabled to false when deletion must be blocked.

Premium supports geo-replication. It gives one registry replicas in multiple Azure regions, helping deployments pull images from a nearby replica.

Which ACR service tier supports private endpoints?

Premium supports private endpoints. A private endpoint exposes the registry through a private network address; clients also need the appropriate network path, DNS resolution and registry permissions.

Which Azure CLI command imports an existing image into ACR without local Docker?

Use az acr import to copy an existing image into your registry: az acr import --name myregistry --source mcr.microsoft.com/hello-world:latest --image hello-world:v1 Azure transfers the image between registries, so the command does not require a local Docker pull and push.

prep-acr-003 · Åpne dette flashcardet

What does image signature verification add beyond digest pinning?

Signature verification checks that an artifact was signed by an identity your verification policy trusts, and that the signed content is intact. A digest identifies content; the signature also provides evidence about its signer. Vulnerability assessment is a separate check.

Eksempel · Scenario

An image has the digest you downloaded, but your verification policy requires a signature from the company’s release identity. A matching digest alone does not establish that trusted identity as the publisher.

prep-p-acr-m01 · Åpne dette flashcardet

What can an ACR repository-scoped token restrict?

Its scope map can restrict the repositories and operations the token may use, such as reading images from one repository. This is useful for a client that needs limited registry access without broad permissions to every repository.

Eksempel · Scenario

A deployment token’s scope map permits reading the orders repository. That token can pull orders:v1, while a push or access to an unrelated repository is outside the granted scope.

prep-p-acr-008 · Åpne dette flashcardet

What must accompany an ACR private endpoint when public registry access is disabled?

The client needs private network connectivity and DNS that resolves the registry’s endpoints to their private addresses. It also needs permission to pull or push images. A private endpoint changes the network path, while authorization still controls access.

Eksempel · Scenario

The registry’s public access is off. A developer connects through the approved private network, where DNS resolves the registry endpoints to private addresses. A laptop with no route to that network still cannot pull the image.

prep-acr-012 · Åpne dette flashcardet

Which ACR capability can recover accidentally deleted artifacts when enabled beforehand?

An enabled soft delete policy can retain deleted artifacts for recovery during its retention period. It must be enabled before the deletion. The documented feature is in preview and has restrictions, including unsupported combinations with geo-replication and Artifact Cache. Check those restrictions before relying on it.

How can App Service pull from ACR without storing registry credentials?

Give the App Service app a managed identity, grant that identity image-read access to ACR, and configure App Service to use it for pulls. The role depends on ACR’s permission mode: use AcrPull for RBAC Registry Permissions, or the appropriate repository-reader role for an ABAC-enabled registry. App Service can then authenticate without storing a registry password.

m-05-1-1 · Åpne dette flashcardet

Why is the ACR administrator account unsuitable for a production app identity?

The administrator account uses shared credentials with broad registry access. A separate managed identity gives each app its own identity and allows narrower permissions and clearer auditing. Use that identity for production image pulls.

Eksempel · Scenario

If two apps share the registry administrator password, rotating it affects both. Separate app identities let you revoke one app’s image access without changing a shared password used by the other.

m-05-3-1 · Åpne dette flashcardet

Does pushing to the same tag automatically refresh an App Service container?

No. Pushing a new image under the same tag does not replace the already-running container. Restart or update the app to trigger another pull, or configure the App Service continuous-deployment webhook to request that update.

Eksempel · Scenario

The running API reports version 1. A pipeline pushes version 2 under the same orders:latest tag, but requests still reach the existing version-1 process until App Service restarts/updates and pulls the replacement.

m-05-4-1 · Åpne dette flashcardet

How do App Service and Functions expose app settings to application code?

They expose app settings as environment variables. For example, setting WORKSHOP_MODE to production lets Python read it through os.environ["WORKSHOP_MODE"]. This supplies environment-specific configuration without rebuilding the image.

m-06-1-1 · Åpne dette flashcardet

Why should runtime credentials be kept out of a Dockerfile?

Credentials included in a Dockerfile or image can be exposed to anyone able to inspect the image or its history. Supply runtime credentials through an authorized secret mechanism, such as a Key Vault reference, so they can be controlled and rotated separately from the image.

What happens to a slot setting during an App Service slot swap?

A setting marked as a deployment-slot setting stays with its slot during a swap. For example, staging can keep its own database address while the application version moves to production. Use slot settings for values that belong to the environment.

The identity resolving the reference needs permission to read the secret, plus network access to the vault. What does a Container Apps revision represent?

A revision is an immutable snapshot of a Container App’s revision-scoped configuration, such as its image and environment variables. Changing those settings creates another revision. App-scoped settings, including secret definitions, have a separate lifecycle.

How does single-revision mode route Container Apps traffic?

The current revision keeps serving while the replacement starts. Once the new revision is ready, Container Apps moves traffic to it and deactivates the old revision. This makes single-revision mode useful when you want one active application version at a time.

Eksempel · Scenario

Revision v1 serves customers while v2 starts. If v2 is not ready, v1 keeps serving. Once v2 becomes ready, single-revision mode moves traffic to it and deactivates v1.

What does multiple-revision mode allow in Container Apps?

Several revisions can remain active together. You can test a release by sending a small percentage of traffic to it, such as 10%, while the rest goes to the current version. You control traffic assignments and when old revisions are deactivated.

What information does a custom scaling rule need in Azure Container Apps?

A custom rule needs its name, scaler type, source-specific settings and any required authentication. A Service Bus rule, for example, identifies a queue and sets a target backlog per replica. The scaler uses that metric and target to decide the desired replica count.

How can Azure CLI configure queue-based scaling for an existing Container App?

For an existing app whose system-assigned identity can read the Service Bus queue: az containerapp update --name myapp --resource-group mygroup --min-replicas 0 --max-replicas 3 --scale-rule-name jobs --scale-rule-type azure-servicebus --scale-rule-metadata namespace=mybus queueName=jobs messageCount=5 --scale-rule-identity system Replace myapp, mygroup and mybus with your resources. The rule watches the jobs queue, targets five messages per replica and allows zero to three replicas.

What is the trade-off of setting Container Apps minReplicas to zero?

A minimum of zero allows an idle app to stop all replicas, reducing usage-based compute costs where applicable. Starting a new replica can add delay to the next request or event. Other resources can still incur charges.

Eksempel · Scenario

Keeping at least one replica available reduces startup delay for the next request. Set minReplicas to 1 or more when that latency matters, while accounting for the cost of keeping capacity running.
