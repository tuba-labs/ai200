  1. Opprett registeret i den nye gruppen. Sett $acr til registernavnet og $login til login server fra Overview. La $rg være ai200-v2-d1a.
  2. Kjør et lokalt image med APP_VERSION=v1 og push det med Docker. Bygg deretter v2 med ACR Tasks og build-argumentet. Samme appkode får ulike image-konfigurasjoner; versjonen kan også overstyres ved oppstart.
  3. Noter tag, manifest-digest og /health-resultat. Importer eller bygg en annen versjon til en gjenbrukt test-tag og sammenlign digestene. Forklar hva som faktisk fryser innholdet.
# Bygg imaget fra den nye labmappen.
docker build -t ai200-v2-api:v1 workshops/labs/containers
# Kjør imaget lokalt med en synlig versjon.
docker run --rm --name ai200-v2-api -d -p 127.0.0.1:8080:8080 -e APP_VERSION=v1 ai200-v2-api:v1
# Les versjon og helsestatus fra API-et.
Invoke-RestMethod http://localhost:8080/health
# Autentiser Docker mot ditt register med innlogget Azure-identitet.
az acr login --name $acr
# Gi det lokale imaget en full registeradresse.
docker tag ai200-v2-api:v1 "$login/ai200-v2-api:v1"
# Push første versjon til registeret.
docker push "$login/ai200-v2-api:v1"
# Bygg og push v2 i ACR uten lokal Docker-bygging.
az acr build --registry $acr --image ai200-v2-api:v2 --build-arg APP_VERSION=v2 workshops/labs/containers
# Vis hvilke tagger registeret inneholder.
az acr repository show-tags --name $acr --repository ai200-v2-api -o table

"""Small, deliberately local workshop API; no external Python dependencies."""
# Gjør Python-data om til JSON i HTTP-svaret.
import json
# Les appkonfigurasjon fra miljøvariabler i containeren.
import os
# Bruk en liten HTTP-server og en handler for hver forespørsel.
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
# Skill URL-stien fra eventuelle spørringsparametere.
from urllib.parse import urlsplit


# Samle behandlingen av HTTP-forespørsler i en handlerklasse.
class Handler(BaseHTTPRequestHandler):
    # HTTP-serveren kaller denne metoden for GET-forespørsler.
    def do_GET(self):
        # Hent bare stien, for eksempel /health.
        path = urlsplit(self.path).path
        # Helsesjekken gir 200; alle andre stier gir 404.
        status = 200 if path == "/health" else 404
        # Vis versjonen fra miljøet, med v1 som standard.
        payload = {"status": "ok", "version": os.getenv("APP_VERSION", "v1"),
                   # Vis konfigurasjonen uten at vi trenger å bygge et nytt image.
                   "mode": os.getenv("WORKSHOP_MODE", "practice"),
                   # Vis bare om en hemmelighet finnes. Selve verdien sendes aldri til klienten.
                   # For andre stier brukes en enkel feilmelding i stedet.
                   "secret_configured": bool(os.getenv("DEMO_SECRET"))} if status == 200 else {"error": "not found"}
        # Serialiser JSON og kod teksten som byte til nettverksforbindelsen.
        body = json.dumps(payload).encode("utf-8")
        # Start HTTP-svaret med statuskoden.
        self.send_response(status)
        # Fortell klienten at innholdet er JSON i UTF-8.
        self.send_header("Content-Type", "application/json; charset=utf-8")
        # Oppgi lengden på svaret i byte.
        self.send_header("Content-Length", str(len(body)))
        # Avslutt headerne før selve innholdet sendes.
        self.end_headers()
        # Skriv JSON-innholdet til HTTP-svaret.
        self.wfile.write(body)


# Start serveren bare når filen kjøres som et program.
if __name__ == "__main__":
    # Skriv en oppstartsmelding direkte til containerloggen.
    print("Workshop API listening on port 8080", flush=True)
    # Lytt på port 8080 på alle containerens nettverksgrensesnitt.
    ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

# slim-varianten har færre forhåndsinstallerte pakker enn standardimaget.
FROM python:3.12-slim

# Sett /app som arbeidsmappe i imaget. Mappen opprettes hvis den mangler.

What does an ACR quick task do?

A quick task builds a container image on demand in Azure Container Registry (ACR). For example: az acr build --registry myregistry --image myapp:v1 . This builds from the current directory, marked by the final dot, using its Dockerfile and source files. By default it uploads the resulting image to myregistry as repository myapp with tag v1. You need Azure CLI and the source files, but no local Docker Engine, because Azure runs the build.

m-03-1-1 · Åpne dette flashcardet

Why can pulling myapp:latest return a different image after another push?

Because latest is a movable tag. Someone can push a new image under the same name, so a later pull retrieves different content. Use a protected release tag or a digest when you need a fixed version.

m-04-1-1 · Åpne dette flashcardet

Why use a different image tag for each build?

To identify the build you intend to deploy. For example, myapp:build-1042 distinguishes that release from build-1043, so a restart does not accidentally select a newer build under a reused name. Keep each release tag unchanged or protect it from overwrites.

m-04-2-1 · Åpne dette flashcardet

Which image reference pins exact content even if a tag moves?

Use the manifest digest, for example myregistry.azurecr.io/myapp@sha256:<digest>. The digest identifies the manifest content, so moving a tag such as latest does not change what this reference selects.

m-04-3-1 · Åpne dette flashcardet

How do you push a local container image to Azure Container Registry?

Assume myapp:v1 already exists locally and your ACR registry is named myregistry. 1. Sign in to Azure and authenticate Docker to the registry: az login az acr login --name myregistry 2. Give the local image a name that includes the destination registry: docker tag myapp:v1 myregistry.azurecr.io/myapp:v1 3. Upload the image using that full name: docker push myregistry.azurecr.io/myapp:v1 myregistry.azurecr.io is the registry hostname, myapp is the repository and v1 is the version tag. Tagging adds a local name; it does not rebuild or upload the image. Replace the example names with yours and use the actual Login server shown by ACR.

Which image tag is assumed when none is specified?

Docker assumes the tag latest. For example, docker pull myregistry.azurecr.io/myapp requests myapp:latest. The name latest does not guarantee that it is the most recently built image; it is simply a tag someone must publish.

How do you find the login-server hostname to use for an ACR image?

Read the registry’s Login server value in Azure, or run: az acr show --name myregistry --query loginServer -o tsv It is often myregistry.azurecr.io, but some registries include an additional hash in the hostname. Use the returned value for Docker image names.

Which Azure CLI command lists a repository's tags in ACR?

Run az acr repository show-tags --name myregistry --repository myapp. Replace myregistry with the registry name and myapp with the repository name. This lists tag names such as v1 and latest; it does not download the images.

Which source-code events can trigger an ACR Task?

A commit to the configured Git branch, or creation/update of a pull request. Commit triggers are enabled by default; pull-request triggers must be enabled. The task needs access to a supported repository so ACR can register its event webhook.

m-01-1-1 · Åpne dette flashcardet

How does an ACR Task know when to rebuild after its base image changes?

During the first build, the task records the base images it depends on. With base-image triggering enabled, later updates can start a rebuild. ACR-hosted image updates trigger dependent tasks; public Docker Hub and Microsoft Container Registry images are checked at intervals of 10–60 minutes.

m-01-2-1 · Åpne dette flashcardet

What schedule format does an ACR Tasks timer use?

A five-field cron expression: minute, hour, day of month, month and day of week. Times are in UTC. For example, 0 9 * * 1-5 runs at 09:00 UTC on weekdays. The shortest supported interval is one minute.

m-01-3-1 · Åpne dette flashcardet

Do ACR webhooks or Artifact Cache rules start source builds?

No. A registry webhook notifies another service about registry activity. An Artifact Cache rule caches images from an upstream registry. Neither is an ACR Tasks trigger that builds application source code; task triggers are configured separately.

m-01-4-1 · Åpne dette flashcardet

Which pull and push roles apply to an ACR registry using RBAC Registry Permissions?

AcrPull allows downloading images. AcrPush allows uploading and downloading images. Use these roles when the registry’s permission mode is RBAC Registry Permissions.

m-02-1-1 · Åpne dette flashcardet

Which ACR roles grant repository pull or push access when ABAC is enabled?

Container Registry Repository Reader allows pulls. Container Registry Repository Writer allows pushes and pulls. On an ABAC-enabled registry, conditions on these role assignments can limit access to particular repositories.

m-02-2-1 · Åpne dette flashcardet

Are legacy AcrPull, AcrPush and AcrDelete roles honored on an ABAC-enabled registry?

No. In RBAC Registry + ABAC Repository Permissions mode, AcrPull, AcrPush and AcrDelete do not grant repository access. Assign the appropriate Container Registry Repository Reader, Writer or Contributor role instead.

How is a Git repository configured as an ACR Task's build context?

Create a task whose build context is the Git repository, for example in PowerShell: az acr task create --registry myregistry --name build-app --image "myapp:{{.Run.ID}}" --context "https://github.com/example/myapp.git#main" --file Dockerfile --git-access-token $env:GIT_TOKEN Replace the registry/repository names and URL. Store the authorized repository token securely in GIT_TOKEN first. --context selects the repository’s main branch; --file selects its Dockerfile. The image tag includes the run ID. Configure supported Git triggers and token permissions so ACR can register the repository webhook.

What defines an ACR multi-step task?

A task YAML file containing the steps and their dependencies. For example, it can build an image, run tests and push the image only after the tests pass. To run an existing file from the current directory: az acr run --registry myregistry --file task.yaml .

What sequence connects a Git commit to a new ACR image?

A commit reaches the watched branch, the repository webhook starts the ACR task, and the task builds and pushes an image. A tag containing the run ID, such as myapp:{{.Run.ID}}, gives that build its own identifiable version.

How can a GitHub Actions workflow run an existing ACR Task?

Add a workflow step that calls ACR Tasks through Azure CLI. For example, with an existing task and an authenticated Azure CLI session: az acr task run --registry myregistry --name build-app GitHub Actions starts the run, while ACR performs the configured build steps.

How can an ACR tag be protected from later overwrites?

Set the tag attribute write-enabled to false. For example: az acr repository update --name myregistry --image myapp:v1 --write-enabled false This prevents overwriting that tag. Set delete-enabled to false as well if the image must also be protected from deletion.

What does image signature verification add beyond digest pinning?

It verifies that a trusted identity signed the artifact and that its signed content has not changed. A digest identifies content; the signature adds a verifiable signer. Trust depends on the verification policy, and signing alone does not prove that the image has no vulnerabilities.

What can an ACR repository-scoped token restrict?

A token’s scope map specifies which repositories it can access and which operations it may perform, such as reading or writing image content. This can give a client access to one repository without granting access to every repository in the registry.

How can App Service pull from ACR without storing registry credentials?

Enable a managed identity on the App Service app and grant it image-read access to ACR. Configure the app to use that identity for image pulls. Use AcrPull with RBAC Registry Permissions, or the appropriate repository-reader role with an ABAC-enabled registry. The app then authenticates without a stored registry password.

m-05-1-1 · Åpne dette flashcardet

Why is the ACR administrator account unsuitable for a production app identity?

The registry administrator account uses shared, powerful credentials with push and pull access. Sharing them across applications makes access harder to limit and audit. Prefer a separate managed identity for each application, with only the registry permissions it needs.

m-05-3-1 · Åpne dette flashcardet

Does pushing to the same tag automatically refresh an App Service container?

No. The running container continues using its current image until the app pulls again. Restart/update the app to trigger a new pull, or configure App Service’s continuous-deployment webhook.

m-05-4-1 · Åpne dette flashcardet

How do App Service and Functions expose app settings to application code?

As environment variables. For example, an app setting WORKSHOP_MODE=production can be read in Python as os.environ["WORKSHOP_MODE"]. This lets you configure an application without baking each environment’s values into its image.

m-06-1-1 · Åpne dette flashcardet

Why should runtime credentials be kept out of a Dockerfile?

A value placed in a Dockerfile or image can be recovered by someone who can inspect that image or its history. Supply credentials at runtime through an authorized secret mechanism, such as a Key Vault reference, instead of distributing them with every copy of the image.

How should nested .NET configuration keys be named in Linux App Service app settings?

Replace a colon with two underscores and a period with one underscore. For example, Service:Endpoint becomes Service__Endpoint. This lets the environment-variable name represent the nested configuration key expected by .NET.

How do App Service connection strings differ from ordinary app settings?

Connection strings are exposed with a type-specific prefix, such as CUSTOMCONNSTR_ for a custom connection string. Ordinary app settings use their configured names directly. Application code must read the resulting environment-variable name, including any connection-string prefix.

What happens to a slot setting during an App Service slot swap?

A setting marked as a deployment-slot setting stays with its slot during a swap. For example, staging keeps its staging database address while the application code is swapped. Use this for configuration that belongs to the environment rather than to the deployed version.

What is a Container Apps environment?

A shared hosting boundary for Container Apps, with common networking and logging configuration. It can contain several apps. Each app has its own revisions, while the environment supplies their shared infrastructure.

What does a Container Apps revision represent?

A saved version of the app’s deployment configuration, such as its container image and environment variables. That configuration is immutable: changing it creates another revision. App-level settings, such as secret definitions, are managed separately.

How does single-revision mode route Container Apps traffic?

The old revision serves requests until the new revision is ready. Container Apps then sends the app’s traffic to the new revision and deactivates the old one. This is the default mode; it keeps the switch between versions automatic.

What does multiple-revision mode allow in Container Apps?

It lets several revisions run at once. You can split traffic between them, such as 90% to the current version and 10% to a new version, and choose when to deactivate old revisions.

What must the traffic percentages for a Container Apps endpoint add up to?

100%. For example, 90% to v1 and 10% to v2 accounts for all traffic sent to the app’s main endpoint.

How can one Container Apps revision have a stable test URL?

Give the revision a label, such as test, and use that label’s URL. It sends requests to that specific revision even if the revision has no share of the main endpoint’s traffic. You can later move test to another revision without changing the test URL.

How do internal and external Container Apps ingress differ?

Internal ingress accepts direct app traffic only from within the same Container Apps environment. External ingress allows traffic from outside that environment. External does not necessarily mean public internet access: an internal/private environment and network restrictions can still limit who can reach the app.

What information does a custom scaling rule need in Azure Container Apps?

A name, a scaler type, the scaler’s settings and any required authentication. For a Service Bus queue, the settings identify the queue and the target number of messages per replica. The scaler uses that target to decide how many app replicas are needed.

How can Azure CLI configure queue-based scaling for an existing Container App?

For an existing app whose system-assigned identity can read the Service Bus queue: az containerapp update --name myapp --resource-group mygroup --min-replicas 0 --max-replicas 3 --scale-rule-name jobs --scale-rule-type azure-servicebus --scale-rule-metadata namespace=mybus queueName=jobs messageCount=5 --scale-rule-identity system Replace myapp, mygroup and mybus with your resources. The rule watches the jobs queue, targets five messages per replica and allows zero to three replicas.

What is the trade-off of setting Container Apps minReplicas to zero?

It can stop all replicas while idle, reducing Consumption-plan compute costs. The trade-off is startup delay: the next request or event may need to wait for a new replica to start. Other resources can still incur costs.

Why keep at least one Container Apps replica running?

To reduce cold-start delay. With minReplicas set to 1 or more, the app keeps capacity ready instead of starting from zero for the next request. Keeping that capacity available can cost money while the app is idle.

Concurrent HTTP requests: requests being handled at the same time. The target is the desired concurrency per replica, with a default of 10. As concurrency grows, Container Apps can add replicas within the configured minimum and maximum.
