Which KEDA settings select a Storage queue and its scaling target?

For an azure-queue rule, accountName and queueName select the Storage queue, while queueLength sets the target backlog per replica. For example, accountName=mystorage, queueName=jobs and queueLength=5 watch jobs and target about five messages per replica. Configure queue access for the scaler too.

What are the Container Apps min/max replica settings used for?

minReplicas sets the lower bound and maxReplicas the upper bound for scaling. Values of 1 and 5 keep the app between one and five replicas. A minimum of zero permits scaling to zero when the configured trigger supports it.

Which KEDA settings select a Service Bus queue and its scaling target?

For an azure-servicebus rule, namespace and queueName select the queue, while messageCount sets the target messages per replica. For example, queueName=jobs and messageCount=5 target about five queued messages per replica. The rule also needs an authorized identity or secret to inspect the queue.

m-08-1-1 · Åpne dette flashcardet

What is the default polling interval for Container Apps event-driven scaling?

The documented default is 30 seconds for custom KEDA event-source rules. That is how frequently the scaler checks for work, such as a queue backlog. HTTP and TCP scaling use different mechanisms.

m-08-3-1 · Åpne dette flashcardet

When does the default 300-second Container Apps cooldown apply?

It applies when scaling the final replica down to zero after the event source becomes inactive. The documented default cooldown is 300 seconds. Scaling between nonzero replica counts has separate stabilization behavior.

m-08-3-2 · Åpne dette flashcardet

How is the target replica count estimated from a queue-length metric?

A simple estimate is the backlog divided by the target messages per replica, rounded up. With 12 messages and a target of 5, the estimate is 3 replicas. The minimum and maximum replica settings bound the result. Polling, activation and stabilization rules also affect when the running replica count changes.

Rull ut, finn en feil tag og rull tilbake

  1. Opprett namespace ai200-v2. Rediger bare den nye kopien av deployment.yaml: sett image til AI200_IMAGE. Apply er avgrenset til dette namespace-et.
  2. Vent på rollout, kall /health med port-forward, og noter podnavn og image-digest. Skaler til to podder.
  3. Sett en ugyldig image-tag, bruk describe/events og finn ImagePullBackOff. Kjør rollout undo og bekreft at /health virker igjen. Bruk logs --previous bare når en tidligere containerinstans faktisk finnes.

# Bruk manifestet med ditt tilgjengelige image.

# Vent på at utrullingen blir klar.
kubectl rollout status -n ai200-v2 deployment/workshop-api
# Se hendelser og containerstatus.
kubectl describe pods -n ai200-v2

# Bruk Kubernetes-API-et for Deployment-ressurser.
apiVersion: apps/v1
# En Deployment vedlikeholder ønsket antall pod-replikaer.
kind: Deployment
# Metadata identifiserer selve Deployment-ressursen.
metadata:
  # Bruk dette navnet i kubectl rollout, logs og scale.
  name: workshop-api
# Beskriv ønsket tilstand for Deployment-en.
spec:
  # Start med én pod; senere skalerer du til to.
  replicas: 1
  # Velg hvilke pods Deployment-en skal styre.
  selector:
    # Match podenes labels nøyaktig.
    matchLabels:
      # Selectoren må passe med labelen i pod-malen under.
      app: workshop-api
  # Denne malen brukes til å opprette hver pod.
  template:
    # Dette er metadata for podene, ikke for Deployment-en.
    metadata:
      # Sett labels som Deployment og Service kan velge etter.
      labels:
        # Bruk samme app-label som selectoren over.
        app: workshop-api
    # Beskriv innholdet i hver pod.
    spec:
      # Denne poden inneholder én applikasjonscontainer.
      containers:
        # Gi containeren et navn i podens logger og status.
        - name: api
          # Bytt til hele ACR-adressen og taggen du skal teste.
          image: ai200-api:v2
          # Hent imaget hvis noden ikke allerede har denne taggen lokalt.
          imagePullPolicy: IfNotPresent
          # Dokumenter portene containeren lytter på.
          ports:
            # Appen lytter på port 8080 inne i containeren.
            - containerPort: 8080
          # Angi ressursbehov og øvre grenser for containeren.
          resources:
            # Scheduler bruker disse behovene ved plassering på en node.
            requests:
              # Be om 0,1 CPU-kjerne.
              cpu: 100m
              # Be om 64 MiB minne.
              memory: 64Mi
            # Sett øvre grenser for containerens ressursbruk.
            limits:
              # Begrens CPU-bruken til 0,25 kjerne.
              cpu: 250m
              # Minnegrensen er 128 MiB; overskridelse kan avslutte containeren.
              memory: 128Mi
          # Avgjør om poden er klar til å motta tjenestens trafikk.
          readinessProbe:
            # Bruk en HTTP-forespørsel som readiness-kontroll.
            httpGet:
              # Denne stien skal gi et vellykket HTTP-svar.
              path: /health
              # Send kontrollen til appens containerport.
              port: 8080
            # Vent to sekunder før første readiness-kontroll.
            initialDelaySeconds: 2
            # Gjenta kontrollen hvert femte sekund.
            periodSeconds: 5

What does a Kubernetes Deployment manifest describe?

It declares the desired pod template, including image, labels and container settings, together with the desired replica count. The Deployment selector must match its pod-template labels. Controllers use that declaration to create and update the actual pods.

m-15-1-1 · Åpne dette flashcardet

Which kubectl command creates or updates resources from a manifest file?

Use kubectl apply -f followed by the manifest path: kubectl apply -f deployment.yaml Kubernetes creates missing declared resources or updates existing ones. Their controllers then work to make the running state match the declaration.

m-15-2-1 · Åpne dette flashcardet

What is the sequence for a rolling image update in Kubernetes?

Update the Deployment’s image reference and apply the manifest, then watch the rollout: kubectl apply -f deployment.yaml kubectl rollout status deployment/myapp Replace myapp with the Deployment name. With RollingUpdate, old pods are gradually replaced as new ones become ready. Probe settings, rollout limits and available capacity affect whether requests keep succeeding.

m-15-3-1 · Åpne dette flashcardet

Which command rolls a Kubernetes Deployment back?

Use kubectl rollout undo deployment/myapp to restore the previous retained pod-template revision. To select a specific retained revision, add --to-revision=<number>. Check the result with kubectl rollout status deployment/myapp. Application data and external configuration require their own recovery plan.

m-15-4-1 · Åpne dette flashcardet

Which command changes a Deployment's replica count manually?

Use kubectl scale, for example: kubectl scale deployment/myapp --replicas=5 This sets the desired count to five; Kubernetes then reconciles the running pods. An active autoscaler can later change that count again.

m-16-6-1 · Åpne dette flashcardet

Which two kubectl commands are a useful starting point for investigating an unhealthy pod?

Use kubectl describe pod <pod-name> to inspect status and events, then kubectl logs <pod-name> to read application output. Establish whether the failure is scheduling, image startup, probe configuration or application behavior before changing settings.

m-17-1-1 · Åpne dette flashcardet

What does ImagePullBackOff indicate?

The image pull failed, and Kubernetes is waiting before trying again. Inspect the pod events for the actual cause: common examples include an incorrect image name, missing registry permission or failed network/DNS access.

m-17-3-1 · Åpne dette flashcardet

Which kubectl commands show current pod or node CPU and memory usage?

Use kubectl top pods for pod usage or kubectl top nodes for node usage. These commands require a working metrics provider. Compare the measurements with declared requests and limits when investigating resource pressure.

Which Kubernetes Service type is the default?

ClusterIP is the default Service type. It provides a stable address inside the cluster that clients use to reach the Service’s selected backends.

m-09-1-1 · Åpne dette flashcardet

What happens when a Kubernetes readiness probe fails?

The pod becomes not ready and is normally removed from the Service’s ready traffic endpoints. Its container can keep running while it recovers. Readiness failure alone does not request a restart.

m-11-2-1 · Åpne dette flashcardet

What should you check when running pods receive no traffic through their Kubernetes Service?

First check that the Service selector matches the pod labels, the pods are Ready and the Service has endpoints. Then check that targetPort matches the application’s listening port. A running process is only one part of a working route: the Service also needs matching, reachable and ready backends.

What is the purpose of a Kubernetes startup probe?

A startup probe gives a slow-starting container time to initialize. Liveness and readiness probes wait until it succeeds. If startup keeps failing beyond its configured threshold, Kubernetes restarts the container.

m-11-3-1 · Åpne dette flashcardet

What does the Kubernetes Horizontal Pod Autoscaler scale?

The Horizontal Pod Autoscaler, or HPA, changes the number of pod replicas in a workload. It compares configured metrics with their targets and adjusts replicas within the minimum and maximum counts.

m-16-1-1 · Åpne dette flashcardet

What does the Kubernetes Vertical Pod Autoscaler adjust?

The Vertical Pod Autoscaler, or VPA, recommends or changes container resource requests, such as CPU and memory. Depending on its update policy and cluster capabilities, applying a recommendation can involve restarting or replacing pods.

m-16-3-1 · Åpne dette flashcardet

What does a Kubernetes PodDisruptionBudget limit during node maintenance?

A PodDisruptionBudget limits how many matching pods can be unavailable during voluntary disruptions that use the eviction API, such as a node drain. It helps preserve application availability during maintenance; unexpected node failures still require other resilience measures.

prep-aks-015 · Åpne dette flashcardet

What is a Kubernetes StatefulSet used for?

A StatefulSet manages pods that need stable identities and usually separate persistent storage, such as database members. Pods receive predictable names, and the controller supports ordered creation and updates. The application remains responsible for data replication and recovery.

prep-aks-023 · Åpne dette flashcardet

What does a Kubernetes NodePort Service expose?

NodePort exposes a port on the cluster’s nodes and forwards connections through the Service to its backends. The node address and port must be reachable through the network and firewall configuration.

m-09-2-1 · Åpne dette flashcardet

What does a Kubernetes LoadBalancer Service provision?

With a supporting cloud integration, a LoadBalancer Service provisions an external load-balancing frontend for the Service. Configuration determines whether that frontend has a public or private address.

m-09-3-1 · Åpne dette flashcardet

What does a Kubernetes ExternalName Service return?

It returns a DNS CNAME alias for the hostname in externalName. Clients resolve that hostname and connect to the destination themselves; the Service provides the name mapping.

m-09-4-1 · Åpne dette flashcardet

Is Kubernetes Ingress a Service type?

No. Ingress is a separate resource containing HTTP/HTTPS routing rules, such as routing a hostname or path to a Service. A running ingress controller must implement those rules.

m-09-5-1 · Åpne dette flashcardet

How do maxSurge and maxUnavailable control a Kubernetes Deployment rollout?

maxSurge controls how many extra pods may be created above the desired replica count. maxUnavailable controls how many desired pods may be unavailable during the rollout. For RollingUpdate, both default to 25%. Surge percentages round up; unavailable percentages round down. With three replicas, those defaults permit one extra pod and require all three desired replicas to remain available.

m-10-1-1 · Åpne dette flashcardet

How does a DaemonSet rolling update limit disruption to node agents?

Its rolling-update strategy replaces pods gradually rather than stopping all node agents together. The defaults allow one unavailable pod, through maxUnavailable=1, and no extra surge pods, through maxSurge=0. Choose values appropriate for the agent’s availability and resource requirements.

m-10-2-1 · Åpne dette flashcardet

What happens when a Kubernetes liveness probe fails repeatedly?

After the configured failure threshold, the kubelet stops the unhealthy container and applies the pod’s restart policy. Containers managed by a normal Deployment are restarted. Use liveness checks for failures that restarting the process can resolve.

m-11-1-1 · Åpne dette flashcardet

How can a pod consume a Kubernetes Secret without embedding its value in the pod manifest?

Reference a separately created Secret by name. secretKeyRef can populate an environment variable, or a Secret volume can expose values as files. The manifest holds the reference rather than the credential. Restrict access to the Secret and protect its storage; base64 encoding alone does not provide encryption.

m-15-5-1 · Åpne dette flashcardet

What resource setting is needed for CPU-utilization-based HPA scaling?

Set CPU requests for the relevant containers. The HPA calculates CPU utilization relative to those requests, so it needs that baseline. A working resource-metrics provider, normally metrics-server, must also supply the measurements.

m-16-2-1 · Åpne dette flashcardet

Why can KEDA wake a workload from zero replicas when CPU-only scaling cannot?

KEDA can detect external demand, such as a queue backlog, even when no application replica is running. It can therefore request the first replica. CPU-only scaling needs a running container to produce its metric.

m-16-5-1 · Åpne dette flashcardet

How do you inspect logs from a container's previous crashed instance?

Use kubectl logs <pod-name> --previous. Add -c <container-name> for a multi-container pod. It retrieves logs from the previous terminated instance of that container in the pod, when available. This is useful when the current instance has already restarted.

m-17-2-1 · Åpne dette flashcardet

How do you find why a Pending Kubernetes pod cannot be scheduled?

Run kubectl describe pod <pod-name> and read the FailedScheduling events. They identify constraints such as insufficient resources, placement rules, taints or storage that is not ready. Fix the reported constraint rather than repeatedly restarting the pod.

m-17-4-1 · Åpne dette flashcardet

How do ResourceQuota and LimitRange differ in Kubernetes?

ResourceQuota limits total resource consumption or object counts within a namespace. LimitRange sets defaults and allowed ranges for individual objects, such as a container’s CPU request. Think of a quota as the namespace’s overall budget and a limit range as rules for each applicable item.

prep-aks-040 · Åpne dette flashcardet

What does Kubernetes imagePullPolicy: Always check at container startup?

The kubelet checks the registry to resolve the image reference to a digest at container startup. If content for that digest is already cached locally, it can reuse those layers. Always requires a registry check, not necessarily another download of every layer.

Why is a toleration alone insufficient to require GPU placement?

A toleration allows placement on a matching tainted node; it does not require placement there. Use a node selector or affinity to require the intended GPU nodes. A workload using a GPU must also request the appropriate GPU resource.

How does Microsoft Entra Workload ID authenticate an AKS workload?

The pod receives a Kubernetes service-account token. Microsoft Entra validates the configured federation trust and exchanges the token for access as the associated Azure identity. That identity’s Azure permissions determine which services the workload can use.

Which Kubernetes resource controls network traffic into or out of pods?

Which Azure storage service commonly backs a Kubernetes ReadWriteMany file volume?

Azure Files commonly supplies a shared file volume through its CSI driver. A ReadWriteMany volume can be mounted for writing by multiple pods, including pods on different nodes, subject to the storage implementation’s capabilities.
